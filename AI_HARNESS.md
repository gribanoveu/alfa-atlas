# AI Harness

Status of the AI-agent infrastructure in this app: what exists today, what it does, and what is deliberately not built yet.

## Status

**The tool-execution boundary is reachable both from the frontend via one IPC command (`ai_execute_tool`) and from a real LLM chat UI running a genuine multi-turn tool-calling loop; a standalone Repository Index + Chunk Index exist alongside it; and an Embedding Service (local BGE-M3 or a remote OpenAI-compatible API, backed by a `usearch` vector index) turns chunks into searchable vectors and persists both the vectors and the chunk/file metadata needed to reload them.** This started as groundwork for a future AI harness (an agent loop that calls an LLM with tool-calling) — the trust boundary that decides *which files* and *which operations* that harness is allowed to touch, a per-file structural index, a semantic-chunk index, and the embedding layer the `SemanticSearch` tool queries — and that harness is now real: the assistant chat panel calls it on every turn. The Rust side (`src-tauri/src`) is unit-tested throughout; the IPC command is additionally verified end-to-end (see "IPC surface" below) but has no caller anywhere in the app yet. Repository Index and Chunk Index still have no caller at all (not even IPC) beyond `embedding_sync` rebuilding them internally. The Embedding Service is the first layer in this file with real UI: a "Эмбеддинги" tab in Settings and a setup checklist in the RightDock "Ассистент" panel, both driving 11 `embedding_*` IPC commands and a live `embedding:sync-progress` event stream. `embedding_sync` is no longer purely manual: a dedicated file watcher (`services::index_watcher::IndexWatcher`, started as soon as a project opens) now reacts to on-disk changes to already-tracked files and keeps the index incrementally fresh between manual syncs, and a fresh project's very first sync prioritizes whichever files are open in the editor (plus their direct AsciiDoc includes/xrefs, JSON/YAML `$ref`s, and — via a separate, `FileId`-space-only mechanism — Java imports) over the rest of the repo, which is embedded afterward on a low-priority background task — see "Embeddings" below for both. A third tool, `SemanticSearch`, now sits in the harness alongside `ReadFile`/`ListFiles` and does consume the resulting vectors — with a three-tier degradation cascade (exact symbol-name match → semantic vector search when the index is ready → lexical grep fallback when it isn't). **All three tools now have a real caller**: the LLM chat feature runs a genuine multi-turn tool-calling loop (`commands::llm::llm_chat_stream`, entirely server-side) that advertises them to the model and executes whatever it requests via this exact `execute_tool` boundary — see "LLM client" below for the full mechanics (the tool-calling loop, streaming-argument repair, debug logging, and the block-based chat UI that shows every call and its result permanently in the transcript).

**Memory/persistence architecture (added after the initial pass below was written):** `ChunkIndex` no longer holds chunk text resident in memory — only `ChunkMetadata` (byte offsets + hashes); text is read on demand from source files via `services::chunk_text::resolve_text`, and only for chunks a caller actually needs (a sync's pending/changed set, or — once it exists — a search's top-K results). `EmbeddingRecord` no longer duplicates the embedding vector (it only ever lived redundantly alongside `usearch`'s own copy). Both `ChunkIndex` and `EmbeddingIndex` mirror to a SQLite store (`infra::index_store::IndexStore`) plus a `vectors.usearch` file, kept in a **global**, per-repository-identity cache — `~/.atlas/embeddings/{repository_id}/` — rather than inside the repo (`commands::embeddings::resolve_index_paths` computes this; `infra::repository_identity` derives `repository_id` as `SHA-256` of the repo's canonicalized git remote URL, or a random UUID persisted once into `{repoRoot}/.atlas/project.json` for a repo with no remote — see "Embeddings" below for the full scheme). `index_root` (still always `project.root` — `AiAccessMode` no longer selects a subtree at all, the whole repo is indexed unconditionally) is now decoupled from where the store physically lives: the same repo cloned to a second local path, or simply moved on disk, resolves to and reuses the *same* global folder rather than rebuilding from scratch — `services::index_store_ensure::open_for` no longer treats a different `index_root` as staleness for exactly this reason, only an incompatible `chunk_version`/`index_version` does. A restart reloads persisted state instead of re-walking/re-embedding from scratch either way, and `embedding_sync` re-chunks/re-embeds only files whose content hash actually changed since the last sync — see "Chunk Index" and "Embeddings" below for the details.

The product vision for the user-facing feature this unblocks is documented separately in [`doc/business-requirements/02-functional-requirements.md`](doc/business-requirements/02-functional-requirements.md) (BR-4 "AI-ассистент документации", BR-5 "Подсказки AI").

## The two independent axes of restriction

A harness call is constrained along two orthogonal axes, both resolved into a single `ToolScope`:

1. **Root — `AiAccessMode`** ([`domain/ai_access.rs`](src-tauri/src/domain/ai_access.rs)): which part of the filesystem is visible at all.
   - `DocsOnly` (default) — only `docsRoot`, the documentation subtree.
   - `FullRepo` — the entire `repoRoot`, including source code.
2. **Tools — allowlist of `ToolName`** ([`domain/ai_access.rs`](src-tauri/src/domain/ai_access.rs)): which operations are callable at all, independent of the root. A project could be `FullRepo` but still have a given tool disabled.

Both are persisted per-project in `ProjectConfig` ([`domain/project_config.rs`](src-tauri/src/domain/project_config.rs), stored at `{repoRoot}/.atlas/project.json`):

```rust
pub struct ProjectConfig {
    pub docs_root: String,
    pub ai_access_mode: AiAccessMode,          // default: DocsOnly
    pub ai_allowed_tools: Option<Vec<ToolName>>, // None = use the mode's default allowlist
}
```

`ai_allowed_tools: None` means "not customized yet" — the effective set falls back to `default_allowed_tools(mode)`. Once a user sets an explicit list, it is authoritative: **adding a new `ToolName` variant later does not silently widen an already-customized allowlist** — a user has to opt a new tool in explicitly. This mirrors the existing safe-by-default choice of `AiAccessMode::DocsOnly`.

Legacy `project.json` files without these fields deserialize cleanly (`#[serde(default)]`) into the safe defaults — no migration needed.

## The single entry point: `execute_tool`

Every tool call goes through one function in [`services/ai_tools.rs`](src-tauri/src/services/ai_tools.rs):

```rust
pub fn execute_tool(scope: &ToolScope, call: ToolCall, deps: &EmbeddingDeps, todos: &[Task]) -> Result<ToolResult, ToolError>
```

`ToolCall`/`ToolResult` are enums, not separate per-tool functions — this is deliberate: one allowlist check, one place where a call/result gets serialized at the LLM tool-calling boundary, and one place to eventually add logging (not implemented yet, but this is the seam for it — see "What is not built yet"). Adding a new tool means adding one match arm here, not a new public function with its own copy of the allowlist check. `deps: &EmbeddingDeps` (a bundle of `Arc`-cloned repo/chunk/embedding-index state) was added once `SemanticSearch` needed Tauri-managed state to reach (see "Tools implemented today" below) — `ReadFile`/`ListFiles` ignore it. `todos: &[Task]` (added for the `Todo` tool, see below) is the caller's current task checklist — `execute_tool` itself keeps no state between calls, same as everything else in this boundary; `TodoWrite`/`TodoUpdate` are pure functions of `todos` plus the call's args, and the caller (the tool-calling loop, or `ai_execute_tool`) is responsible for round-tripping the returned list back in on the next call.

```rust
pub enum ToolCall {
    ReadFile(ReadFileArgs),
    ListFiles(ListFilesArgs),
    SemanticSearch(SemanticSearchArgs),
    Grep(GrepArgs),
    GitDiff(GitDiffArgs),
    GitBlame(GitBlameArgs),
    Check(CheckArgs),
    WriteFile(WriteFileArgs),
    EditFile(EditFileArgs),
    DeleteFile(DeleteFileArgs),
    CreateDirectory(CreateDirectoryArgs),
    DeleteDirectory(DeleteDirectoryArgs),
    Move(MoveArgs),
    RequestFullRepoAccess(RequestFullRepoAccessArgs),
    TodoWrite(TodoWriteArgs),
    TodoUpdate(TodoUpdateArgs),
}

pub enum ToolResult {
    File { content: String, start_line: u32, end_line: u32, total_lines: u32 },
    FileList(Vec<ToolFileEntry>),
    SemanticSearchResults(SemanticSearchPayload),
    GrepResults { matches: Vec<GrepMatch>, truncated: bool },
    GitDiff { path: String, label: String, diff: FileDiffStats, is_binary: bool },
    GitBlame { path: String, hunks: Vec<GitBlameHunk>, truncated: bool },
    CheckResults { kind: CheckKind, diagnostics: Vec<Diagnostic>, truncated: bool },
    FileWritten { path: String, diff: FileDiffStats },
    FileEdited { path: String, diff: FileDiffStats },
    FileDeleted { path: String, diff: FileDiffStats },
    DirectoryCreated { path: String, template: Option<String>, created_files: Vec<String> },
    DirectoryDeleted { path: String },
    Moved { from: String, to: String, updated_files: Vec<UpdatedReference> },
    AccessModeChanged { mode: AiAccessMode },
    TodoWritten(Vec<Task>),
    TodoUpdated(Vec<Task>),
}
```

`FileDiffStats { lines_added, lines_removed, unified_diff, truncated }` (`domain::ai_tools`, computed by `services::text_diff::diff_stats`) rides along on every settled `FileWritten`/`FileEdited`/`FileDeleted` result — a real `+N -M` line-diff against the file's prior content, not just a bare path. Two independent readers consume it: the chat UI renders a diff badge (`DiffBadge`) plus a colored unified-diff view in the expanded detail (`AssistantToolCallBlock.tsx`'s `DiffLines`), and the model itself reads it back in the `Tool`-role message — previously it only ever saw `{"path": "..."}` and had no way to confirm what actually landed on disk. Separately, and *before* approval rather than after, a pending `writeFile` call's approval card now has its own real diff preview (`WriteFileDiffReview.tsx`, a read-only Monaco `DiffEditor` — current on-disk content vs. proposed `content`, toggled open/closed) — together these close most of what this file used to list under "What is not built yet" as "a real rendered diff/preview view for a pending write is still not built." `editFile`'s pending card still has no rendered diff of its own — expanding it shows the raw `edits: [{old, new}]` arguments, which (per the note that used to live here) doubles as a de facto diff view only because of that argument shape, not because a dedicated one was built for it.

Both derive `serde::Serialize`/`Deserialize` with an adjacently-tagged representation (`#[serde(tag = "tool", content = "args")]` / `content = "result"`), so the wire shape is fixed and tested:

```json
{"tool":"readFile","args":{"path":"intro.adoc","startLine":null,"endLine":null}}
```

`scope_for_config(repo_root, docs_root, config)` is the one place that turns a project's persisted config (or its absence) into a concrete `ToolScope`.

## Tools implemented today

Fifteen tools exist today — the original three read-only ones (`ReadFile`/`ListFiles`/`SemanticSearch`), exact-content `Grep`, two more read-only git tools (`GitDiff`/`GitBlame`), documentation `Check`, then `WriteFile`/`EditFile`/`DeleteFile`/`CreateDirectory`/`DeleteDirectory`/`Move`/`RequestFullRepoAccess` as the harness's only side-effecting operations, gated by `ToolName::requires_confirmation` (see "Tool-calling loop" below for the per-call approval flow this triggers); `Todo` was added later still and is deliberately *not* in that gated set. This section still only fully documents the original three in depth; the newer tools are covered at the level this file has verified, not with the same depth as the rest of this document — a gap worth closing in a future pass.

- **`ReadFile { path, startLine?, endLine? }`** — reads one file's content, relative to the scope root, optionally restricted to a 1-indexed, inclusive line range (`services::ai_tools::slice_lines`). Out-of-range values are clamped, not rejected; omitting both returns the whole file, byte-identical to before this existed. The result always carries `startLine`/`endLine`/`totalLines` alongside `content`, even for a full read, so the model always knows how much of the file it's looking at.
- **`ListFiles { path?, depth?, pattern? }`** — lists files under the scope root (or a subdirectory of it). In `DocsOnly` mode this reuses `services::docs_fs::list_docs_tree_scoped` (a depth-aware sibling of `list_docs_tree`, filtered to documentation formats, same as the sidebar tree); in `FullRepo` mode it uses `infra::workspace_scanner::scan_all_with_depth` (gitignore-aware, no format filter, since source files are not documentation formats). `depth` caps recursion below `path` (`ignore::WalkBuilder`'s own convention: `path` itself is depth 0, direct children are depth 1; omitted = unlimited, unchanged from before). `pattern` is a glob (`globset`) matched against each entry's filename only, never its full path, applied as a post-filter after listing — directory entries are always kept regardless, since `pattern` scopes which files come back, not the navigable structure.
- **`SemanticSearch { query, topK? }`** (`services::ai_tools::semantic_search`) — a three-tier degradation cascade, each match tagged with which tier produced it (`source: "semantic" | "lexical" | "symbol"`, since scores aren't comparable across tiers) and carrying `path`/`snippet`/`score`/`startByte`/`endByte`/`qualifiedName`. Result is `ToolResult::SemanticSearchResults { matches, meta }` where `meta` carries `tiersUsed`, `symbolHits`, `extractedTokens`, `weak`, and an optional Russian `hint` — hard when the search looks weak (empty results, no English identifiers, or only lexical hits), soft (`weak: false` but `hint` set) when hits exist but the query had no camelCase/PascalCase identifiers:
  1. **Token extraction** (`domain::search_query::extract_search_tokens`): pull camelCase/PascalCase identifiers, path-like segments, plain ASCII words (≥ 3 chars), and a small RU→EN root map (`уведомлен`→`Notification`, `патент`→`Patent`, …) out of the free-form query before any tier runs.
  2. **Symbol** (always tried first, cheapest — no I/O beyond a best-effort snippet read): for each extracted token, `RepositoryIndex::find_symbol` exact case-insensitive name match, then **stem/fuzzy** (`notifications` ⊂ `CollectNotificationService`, score `0.95`), **plus** a path-segment match against indexed `relative_path`s (score `0.9`, still `source: "symbol"`). Exact (`1.0`) > stem (`0.95`) > path (`0.9`) for the same file. Hit count is subtracted from the `topK` budget passed to whichever tier runs next.
  3. **Semantic** (when the embedding index is ready): embeds the **whole** query via the configured `EmbeddingProvider`, calls `EmbeddingIndex::search` (cosine distance, converted to a `1 - distance` similarity score), resolves each hit's chunk text via `chunk_text::resolve_text`.
  4. **Lexical** (fallback, no embeddings at all): scans every `ChunkIndex` chunk's resolved text for case-insensitive **token** matches (weighted: camelCase/PascalCase × 2), ranked by weighted occurrence sum. Empty token list falls back to the whole query as a single needle.
  Readiness (semantic vs. lexical) mirrors `embedding_index_status`'s own check (`resolve_index_paths` → `attach_index_store` → stale? → `attach_embedding_index(allow_repair: false)` → `embedded_count > 0`), plus a `try_lock` peek at `EmbeddingSyncGuard` for "a sync is actively running right now" — any failure anywhere in that sequence degrades to the lexical tier rather than erroring out, since this whole tool is a graceful cascade, not a pipeline that should hard-fail on a fast-path hiccup. `execute_tool`'s signature grew a third parameter, `deps: &EmbeddingDeps` (`services::ai_tools::EmbeddingDeps`, a bundle of `Arc`-cloned `RepositoryIndex`/`ChunkIndex`/`EmbeddingIndexSlot`/`IndexStoreSlot`/`EmbeddingProviderSlot`/`EmbeddingSyncGuard`), to reach this state — previously it (and `current_scope()`) were pure functions with zero Tauri-managed-state access.
  5. **Related-file boost**, applied to whichever of tiers 3/4 ran (never to Symbol): when `EmbeddingDeps::active_file` is set (the frontend's currently-open editor tab, converted to `FileId` — see "Repository Index" above), `related_files` unions `RepositoryIndex::java_dependencies` and `WorkspaceIndex::find_includes`/`find_references` for that file; `apply_related_boost` multiplies a matching result's score by `RELATED_FILE_BOOST` (`1.25`) and re-sorts before truncating to `topK`. `active_file: None` (nothing open, or the standalone `ai_execute_tool` command) is a no-op — identical ranking to before this existed.
- **`Grep { pattern, path?, glob?, caseInsensitive?, maxResults? }`** (`services::ai_tools::grep`) — read-only exact regex search over file contents under `scope.root` (gitignore-aware via `workspace_scanner::scan_all_with_depth`). Complementary to `SemanticSearch`: use for precision ("every call site of X"), not conceptual similarity. Default case-sensitive; invalid regex → `ToolError::InvalidPattern`. Skips binaries (NUL sniff) and files > 1 MiB. Result is `ToolResult::GrepResults { matches: [{ path, line, text }], truncated }` with scope-root-relative paths. Not gated by confirmation; `loop_weight` 3.
- **`GitDiff { path, scope?, commit? }`** (`services::ai_tools::git_diff`) — read-only. Path is relative to `scope.root` and must pass `ensure_under` before any `git2` call (then converted to a repo-relative path). Without `commit`, returns the working-tree (`scope: "unstaged"`, default) or staged (`"staged"`) file diff via `git_ops::file_diff`; with `commit`, returns the parent→commit file diff via `git_ops::commit_file_diff` and ignores `scope`. Result is `ToolResult::GitDiff { path, label, diff: FileDiffStats, isBinary }` — unified patch from `text_diff::diff_stats` (same shape write/edit tools already return). Not gated by confirmation; `loop_weight` 2.
- **`GitBlame { path, startLine?, endLine? }`** (`services::ai_tools::git_blame`) — read-only. Same path containment as `GitDiff`. Returns compacted contiguous hunks (`GitBlameHunk`: start/end line, short commit, author, ISO-8601 UTC `authoredAt`, summary) via `git_ops::blame` / `git2::Blame`. Line ranges are 1-indexed inclusive; ranges larger than `MAX_BLAME_LINES` (400) are clamped and flagged `truncated`. Not gated by confirmation; `loop_weight` 2.
- **`Check { kind, path? }`** (`services::ai_tools::check`) — read-only documentation verification. Optional `path` is **access-mode-relative** (same as `readFile`/`writeFile`) and must resolve under `docs_root` via `resolve_mutable_docs_path`. Result `document` fields (and standards folder paths) are rewritten to the access-mode root before returning to the model. Cap 200 + `truncated`. Not gated by confirmation; `loop_weight` 2.
- **`WriteFile { path, content }`** (`services::ai_tools::write_file`) — path is access-mode-relative; `resolve_mutable_docs_path` requires it under `docs_root`, then writes via `docs_fs` with the derived docs-relative path. `FullRepo` widens reads, not write license — paths outside docs return `ToolError::OutsideDocumentation` (preflighted before any approval UI). Requires confirmation.
- **`EditFile { path, edits: [{old, new}] }`** (`services::ai_tools::edit_file`/`apply_edits`) — same path rules as `WriteFile`, search-and-replace alternative to resending a whole file. Exact all-or-nothing matching (or fast-apply fallback); file must already exist. Requires confirmation.
  - **Fast-apply fallback**: if the exact pass fails with a per-edit matching problem (not `EditsOverlap`, which reconciliation can't fix) and a `(provider, model)` pair is available (`EmbeddingDeps::fast_apply` — set by `commands::llm::run_tool_loop` from the same provider/model already resolved for the chat turn; `commands::ai_tools::ai_execute_tool`, which has no chat turn to reuse one from, always leaves it `None`), `apply_edits_sequential_with_fallback` takes over: edits are applied one at a time, each against the result of the previous one (not independently against the original, since a fast-apply call has no fixed byte range to check for overlap against the others). Per edit, an exact match against the current content is still tried first for free; only a genuine mismatch is escalated to `run_fast_apply`, which sends the *whole file* plus the edit's `old`/`new` intent to the model and asks it to return the complete reconciled file. The model's raw output is defensively unwrapped from a markdown code fence (`strip_code_fence`) and then must pass `validate_fast_apply_output`: a longest-common-prefix/-suffix check that rejects any output that changed more of the file than the requested edit plausibly accounts for (`old`/`new`'s length × 3 + 200 bytes of slack), an output identical to the input, or an empty output for non-empty input. A rejected or errored fast-apply call surfaces `ToolError::EditApplyFailed(old, reason)` — still just a string the model sees and can react to, same as every other tool error.
- **`DeleteFile { path }`** (`services::ai_tools::delete_file`) — same access-mode path + docs containment as `WriteFile`. Requires confirmation.
- **`CreateDirectory { path, template? }`** (`services::ai_tools::create_directory`) — same path rules as `WriteFile`. Optional `template: "restEndpoint"` scaffold; `created_files` in the result are access-mode-relative. Requires confirmation.
- **`DeleteDirectory { path, recursive? }`** (`services::ai_tools::delete_directory`) — same path rules as `WriteFile`. `recursive` defaults to `false`. Requires confirmation.
- **`Move { path, newPath }`** (`services::ai_tools::move_path`) — both paths access-mode-relative under docs; reference rewrite still uses docs-/repo-relative internally. Result `from`/`to`/`updated_files` paths are access-mode-relative for the model. Requires confirmation.
- **`RequestFullRepoAccess { reason }`** — calls `services::ai_tools::set_access_mode(FullRepo)`, persisting the escalation to `project.json` (shared with the manual toggle in `AssistantPanel`) and returning `ToolResult::AccessModeChanged`. `reason` is required (not optional) specifically to force the model to self-justify the request, shown verbatim in the approval prompt. Requires confirmation — the user may deny it.
- **`Todo { op: "write" | "update", ... }`** (`services::ai_tools::todo_write`/`todo_update`, `domain::ai_tools::Task`/`TodoStatus`) — one wire tool, two operations, dispatched via `parse_todo_call` (the first tool whose wire name doesn't map 1:1 onto a single `ToolCall` variant — a plain `RawTodoArgs` is deserialized first, then routed on its `op` field). `TodoWrite { titles }` appends new `Pending` tasks to the end of the checklist (`id`s are runtime-assigned, sequential, never chosen by the model; never a replace, capped at `MAX_TODO_TASKS` = 20, rejected outright rather than silently truncated past that). `TodoUpdate { id, status, note? }` can only set `Completed`/`Cancelled` — `TodoUpdateStatus` excludes `Pending`/`InProgress` at the type level, so "pick the next task" is schema-enforced, not a prompt request. `enforce_todo_invariant` (run at the end of both operations) keeps at most one task `InProgress` at a time, auto-promoting the next `Pending` task the instant the current one is completed/cancelled or a fresh list has none yet. The whole list is **never persisted server-side** — `execute_tool` takes it as a `todos: &[Task]` parameter and both operations return the complete new list, which the caller (the tool-calling loop's own `todos` variable, or `ai_execute_tool`'s caller) must round-trip back in on the next call, the same no-server-session-state shape `PendingApproval` already uses (see "Tool-calling loop" below). Deliberately **not** gated by `ToolName::requires_confirmation` — in-memory only, non-destructive, no real-world side effect, same bucket as `ListFiles`/`ReadFile`/`SemanticSearch`. UI: `TodoProgressWidget.tsx` renders the live checklist (with the active task highlighted) in the chat panel; the system prompt always shows the model its current list rather than exposing a `read` operation, so a `todo` call to merely inspect the list is never needed.
- **Permanent memory (harness-only, no tool)** — OptMem dual roots: project `{repo}/.atlas/memory` and global `~/.atlas/memory`. The agent has **no** `memory` tool. **Pre-turn:** combined wake of both scopes is injected each chat turn (`ai_get_memory_wake` / `wake_context`). **Post-turn:** `memory_extract_turn` → `services::memory_pipeline` (extractor LLM → policy → `note` + `drain_pending_naps`). **Viewer:** `memory_log_query` / `memory_log_delete` (Инструменты → Память ассистента). Mutate FS tools hard-deny `.atlas/memory/**`.

## How access is actually enforced

Every path a tool touches is validated with `domain::paths::{join_relative, ensure_under}` — the same containment primitives `services::docs_fs` already uses. Read tools resolve against `scope.root` (access-mode root). Mutate/`check` path args also resolve against `scope.root`, then must pass `ensure_under(scope.docs_root)` (`resolve_mutable_docs_path`); failure is `ToolError::OutsideDocumentation`. The docs-relative path used by `docs_fs` / reference rewrite is `relative_to(docs_root, canonical)` after that check — deterministic subtraction, not string-prefix heuristics on the model argument. `preflight_tool_call` runs the same resolve before `PendingApproval` so impossible writes never show a confirmation card.

`GitDiff`/`GitBlame` close the earlier "git2 can read any tracked path" concern for the harness itself: both tools resolve the caller's path under `scope.root` via `ensure_under` *before* converting to a repo-relative path and calling `git_ops`. In DocsOnly that means only docs files; in FullRepo, the whole repo. The standalone UI git commands in `commands/git.rs` remain a separate surface (editor/Git panel), not reachable from the tool-calling loop.

```rust
    call: ToolCall,
    todos: Vec<Task>,
    repo_index: State<'_, Arc<RepositoryIndex>>,
    chunk_index: State<'_, Arc<ChunkIndex>>,
```

The six `State` params added for `SemanticSearch`, plus a seventh (`workspace_index`) added for `Move`'s reference-rewrite cascade — all already `app.manage()`'d, no new registration needed for either — are cloned into an `EmbeddingDeps` before entering `spawn_blocking`, mirroring exactly how `commands::embeddings::embedding_sync` already receives its own `State<'_, Arc<T>>` params. `todos: Vec<Task>` was added for the `Todo` tool (see "Tools implemented today" above) — this endpoint is stateless between calls, unlike the chat loop's own `todoListRef`, so a caller invoking `todo` through this path must track and resupply the list itself; every other call typically passes an empty `Vec`.

Two smaller sibling commands round out the tool-execution surface: `ai_get_auto_approved_tools() -> Vec<ToolName>` and `ai_set_tool_auto_approved(tool, auto_approved: bool)`, the backend counterpart to the approval card's "Разрешать всегда" button (`services::ai_tools::auto_approved_tools`/`set_tool_auto_approved`, backed by `ProjectConfig::ai_auto_approved_tools`) — see "Tool-calling loop" below for how the frontend uses them.

The frontend passes only `{ tool, args }` — it never passes `docsRoot`/`repoRoot`/an access mode, unlike every other document command in this codebase (`read_project_file(docsRoot, ...)` etc.). The command resolves which project is open itself, via a new `services::ai_tools::current_scope()`:


`current_scope()` reuses `services::project_open::get_project()` (the same backend-authoritative "what's the current project" resolver `commands::project::get_project` uses at startup restore, reading `~/.atlas/settings.json`) to get `(repo_root, docs_root)`, then loads the full `ProjectConfig` via `infra::project_store::load` (for `ai_access_mode`/`ai_allowed_tools`, which `get_project()` alone discards), then calls `scope_for_config`. If no project is open, it returns an error whose message includes `"no project is open"`.

Runs via `spawn_blocking` (like `check_standards`) since `ListFiles` in `FullRepo` mode walks the whole repo.

Frontend wrapper, [`src/lib/aiTools.ts`](src/lib/aiTools.ts):
```ts
export function aiExecuteTool(call: ToolCall): Promise<ToolResult>
```
No `hooks/` layer and no UI wired to it yet — this is boundary-only, per AGENTS.md's `lib/` convention (one typed function per command, no logic). **Still true even now that tool calls are a real, everyday thing**: the LLM chat feature's tool-calling loop (`commands::llm::llm_chat_stream`, see "LLM client" below) calls `services::ai_tools::current_scope()`/`execute_tool()` directly from inside its own `spawn_blocking` closure — it never goes through this `ai_execute_tool` IPC command at all, since it's already running server-side and has no reason to round-trip through the frontend. `ai_execute_tool` and the chat loop are two independent callers of the same underlying `execute_tool` boundary, not one built on top of the other.

What this endpoint is actually *for*: a future non-chat AI feature that runs its own client-side loop instead of going through `llm_chat_stream`. E.g. a "select text in the editor → ask the AI to rewrite it, with tool access" feature — if it wanted the model to check other docs for consistency (`SemanticSearch`) or read a related file before rewriting, the frontend would need its own "model requests a tool → call `ai_execute_tool` → feed the result back to the model → repeat" loop, since `ai_execute_tool` only ever executes one call per invocation and doesn't drive the model itself. A simpler version of the same feature that just wants "text in, rewritten text out" with no tool access at all wouldn't need this boundary either — it'd call `LlmProvider::chat()` directly (the same one-shot, non-streaming path `run_fast_apply` already uses), no `execute_tool` involved.

Verified end-to-end against a running dev build (`bun run tauri dev`) via direct `window.__TAURI__.core.invoke` calls in the webview: `listFiles` returns the real docs tree, `readFile` returns real file content, and a `../`-traversal attempt is rejected with `"path escapes tool root: ..."` — confirming the containment boundary holds across the actual IPC channel, not just in Rust unit tests.

## Repository Index

A separate, standalone layer from the tool-execution boundary above: a structural per-file index — metadata, content hash, detected language, symbols. **No embeddings, no RAG, no chunking** — just an index a future tool/harness will query. Not wired into `ai_tools`/IPC/UI at all yet, and has no `#[tauri::command]` of its own; its only caller today is `commands::embeddings::embedding_sync`, which rebuilds it (a full walk) as the first step of every sync.

```rust
pub struct IndexedFile {
    pub metadata: FileMetadata,   // relative_path, size_bytes, modified_at: SystemTime, hash: blake3::Hash, language
    pub symbols: Vec<Symbol>,     // name, kind, start/end line, start/end byte
    pub imports: Vec<ImportRef>,  // fqn, is_wildcard — Java only, see `RepositoryIndex::java_dependencies`
}
```

Deliberately **does not store file content** — a repo of thousands of files would otherwise duplicate the entire working tree in memory. Content is read separately when actually needed (the `ReadFile` tool, or a plain `fs::read_to_string`); the index describes the project, it doesn't duplicate the filesystem.

**Languages covered**: Java, JSON, YAML, Markdown, AsciiDoc (`domain::repo_index::Language`) — matches the Java/Kotlin-backend-with-JSON/YAML-schemas repos this app documents, minus Kotlin (see below). `detect_language` is extension-based; anything else (including this app's own `.rs`/`.ts`) is skipped entirely.

**Per-language indexing** (`infra/language_indexers/`), registered once and explicitly in `default_indexers() -> HashMap<Language, Arc<dyn LanguageIndexer>>` — no `supports()` self-reporting, so the language↔indexer mapping exists in exactly one place:
- **Java** — real parsing via `tree-sitter`/`tree-sitter-java`: class/interface/enum/method/constructor/field declarations, each with full line+byte ranges straight off the tree-sitter node. This is a documented swap point — a future `JdtLsJavaIndexer: LanguageIndexer` replaces it by changing one line in `default_indexers()`.
- **AsciiDoc** — real parsing via `tree-sitter`/`tree-sitter-asciidoc`: section titles (`document_title`, `title1`..`title5` nodes). Chosen over a hand-written line scan specifically because a line scan can't distinguish a real section title from an `=` that merely starts a line inside a listing block or table — a grammar-aware parser doesn't have that failure mode (see `infra/language_indexers/asciidoc.rs`'s doc comment for the specific test that proves it, `ignores_equals_signs_inside_listing_blocks`).
- **Markdown** — `pulldown-cmark` event walk; every heading becomes a symbol (unlike `infra/parsers/markdown.rs`'s anchor extraction, which only records a heading with an explicit `{ #id }`).
- **JSON / YAML** — deliberately extract **zero symbols**. A regex key-scan produces false positives on quoted values that merely contain a colon (`{"query": "field:value"}`), and `serde_json`/`serde_yaml` carry no position information to do this properly. The file is still indexed (metadata + hash + language); only `.symbols` is empty, on principle, rather than guessing.

**Kotlin was dropped entirely.** `tree-sitter-kotlin` (the only Kotlin grammar crate on crates.io) is capped at `tree-sitter <0.23`. Once AsciiDoc was prioritized and `tree-sitter-asciidoc`'s compiled grammar turned out to need language ABI 15 (unsupported by tree-sitter 0.22's runtime — Cargo's `links = "tree-sitter"` only allows one `tree-sitter` version project-wide), `tree-sitter` was bumped to `0.26.11` and Kotlin support was removed rather than kept on an incompatible pin. Re-add `Language::Kotlin` if a `tree-sitter-kotlin` release ever raises its own upper bound.

**Resilience policy** (`services::repo_index::RepositoryIndex::build`): an unreadable file (I/O error, non-UTF-8) is skipped entirely with a warning. A file that reads fine but is malformed for its language (e.g. broken Java) still gets a full record — `LanguageIndexer::index` is infallible by signature, so a broken file's `symbols` may come back short or empty, but the file never disappears from the index.

`INDEX_VERSION` (currently `1`) — bumped whenever indexer behavior changes in a way that would change output for the same input — is exactly the staleness signal `services::index_store_ensure::open_for` now checks against a persisted store's `index_version` meta row before trusting it (see "Chunk Index" below). `RepositoryIndex` still rebuilds via a full directory walk on every `embedding_sync` (now parallelized — `infra::workspace_scanner::walk` uses `ignore::WalkBuilder::build_parallel()` rather than a single-threaded iterator, same output, just faster; still not skippable — no signal in this codebase can answer "has the file set changed" without physically walking it), but no longer unconditionally re-reads/re-hashes/re-parses every file to do it: a `symbols` table (mirroring `chunks`/`embeddings`) persists each file's `Vec<Symbol>` alongside `files.file_hash`/`size_bytes`/`mtime_secs`, and `RepositoryIndex::build_reusing_symbols(repo_root, persisted)` — fed by `infra::index_store::IndexStore::load_all_files`/`load_all_symbols` — reuses a file's already-known metadata and symbols in two layers, checking a `resident` (this-session) and a `persisted` (SQLite) candidate independently rather than picking whichever exists first: first a cheap `size_bytes`/`modified_at` comparison against `workspace_scanner::ScannedFile`'s own `size`/`modified` (skips the file's content read and hash entirely on a match — the actual "mtime pre-filter"; compared at whole-second precision via `mtime_secs_eq`, matching what `files.mtime_secs` actually persists — a live `fs::metadata` read's sub-second precision would otherwise never match a value round-tripped through SQLite), falling back to reading the content and comparing the real `blake3` hash (a touch that didn't change bytes still skips the tree-sitter/pulldown-cmark parse, just not the read). Either signal's absence (new file, or both mismatched on both candidates) means a real parse. `build()` itself (used directly by tests and anything without persisted data to offer) gets the same two-layer reuse for free against whatever's already resident, via an internal snapshot taken before it clears and rewalks — so even a `persisted`-free caller benefits across repeated calls in one session.

A file's `imports` (Java only — see `java_dependencies` below) round-trips through cold-start reuse the same way `symbols` does: a new `imports` table in `infra::index_store` (same shape/gating as `symbols`, one `replace_imports_for_file`/`load_all_imports` pair) is written alongside every `replace_symbols_for_file` call in `embedding_sync`, and `commands::embeddings::load_persisted_symbols` loads it back into `ReusableFileData` for `build_reusing_symbols` — this used to always hand back an empty `imports: Vec::new()` for a cold-start-reused file, silently emptying `java_dependencies` for every unchanged Java file after an app restart.

## Chunk Index

Built on top of Repository Index: `RepositoryIndex → ChunkBuilder → ChunkIndex`. **Still no embeddings, no BGE-M3, no vector DB** — this layer only splits an already-indexed file into meaningful, addressable text fragments (a method, a doc section, a whole small file). That split is what a future embeddings stage would actually run over.

```rust
pub struct Chunk {
    pub metadata: ChunkMetadata,  // id, file_id, language, kind, byte range, file_hash, hash, qualified_name, ordinal
    pub text: String,             // unlike IndexedFile, a Chunk DOES carry its own text — it's the unit of work
}
```

**Gap ownership** decides which bytes belong to which chunk without a useless `ChunkKind::Other`/`Gap`: for Java, `Method`/`Field` symbols already capture their own full body, so each chunk absorbs the *gap before it* (annotations, Javadoc, blank lines, and for the first chunk — package/imports/class declaration too); the last chunk also absorbs the file's trailing suffix. For Markdown/AsciiDoc, heading symbols only mark their own title line, so each chunk absorbs the content *forward* to the next heading (or EOF). JSON/YAML (no symbols) — and any file whose language has symbols but yields none, e.g. an empty class — become one `ChunkKind::File` chunk. `ChunkKind` is exactly `Method | Field | Section | File`.

**Oversized chunks** (`> DEFAULT_MAX_CHUNK_BYTES`, 16KB) are split as a separate, uniform pass after semantic splitting — never per-language — preferring a blank line, `;`, or `}` boundary within a lookback window over an arbitrary cut, always on a valid UTF-8 char boundary.

**Identity vs. change detection are deliberately separate fields**: `ChunkId` is the human-readable `"{file_id}#{start_byte}-{end_byte}"`; `hash` is `BLAKE3(file_hash || start_byte || end_byte || CHUNK_VERSION)` — derived from position, not from re-hashing `text`, so a later embeddings stage can ask "did this exact chunk change?" cheaply. `file_hash` is copied onto every chunk (not just reachable via `RepositoryIndex`) since a `ChunkIndex` will often outlive or travel separately from the index that built it — e.g. once chunks are written to a Vector DB.

**`ChunkBuilder` and `ChunkIndex` are separate types** — the builder holds only the per-language `ChunkStrategy` registry and produces `Vec<Chunk>` (with text); the index stores only `DashMap<ChunkId, ChunkMetadata>` — `insert_all`/`replace_for_file` take builder output but drop `text` immediately after extracting `metadata`. `build_file`/`build_all` already exist as two entry points (`build_all` just loops `build_file` today) specifically so a future file watcher can call `build_file` + `chunk_index.replace_for_file` for exactly the one changed file without either type needing to change; `commands::embeddings::embedding_sync` already does this today for its own incremental diff (see "Embeddings" below), just not yet driven by a watcher.

A `ChunkStrategy` only returns ranges (`ChunkSpan`) — hashing, `qualified_name` lookup (smallest enclosing `Class`/`Interface`/`Enum` symbol, e.g. `"UserService.save"`), and `ordinal` assignment all happen once in `ChunkBuilder`, not duplicated per language.

**Text is not resident in `ChunkIndex`.** Storing every chunk's text (up to `DEFAULT_MAX_CHUNK_BYTES`, 16KB, each) for a whole indexed tree would make resident memory scale with the total size of the indexed text, not with chunk count — the same duplication `IndexedFile` already avoids one layer down. `services::chunk_text::resolve_text(repo_root, &ChunkMetadata)` reads `[start_byte..end_byte)` straight off the source file instead, first checking that the file's current content still hashes to `metadata.file_hash` (`ChunkTextError::Stale` if not — the file changed or was deleted since indexing) before trusting the byte range. `ChunkIndex::get_with_text` wraps this for callers that need both metadata and text in one call. Transparently cached: a process-wide `moka::sync::Cache<blake3::Hash, Arc<str>>` (a `static OnceLock`, module-private to `chunk_text.rs` — `resolve_text`'s signature and every one of its callers are unaware caching happens) keyed on `ChunkMetadata.hash` — not `ChunkId` — since `hash` already encodes `file_hash`/`start_byte`/`end_byte`/`CHUNK_VERSION`, so a content change, a position shift, or a chunking-version bump all naturally produce a different key; a stale entry under an old `hash` is simply never looked up again, no explicit invalidation needed. Bounded by memory, not entry count (chunks range up to 16KB each): a `weigher` closure reports each entry's byte length, and `max_capacity` (64MiB) is a weighted-size budget, not a count. Only successful resolutions are cached — a `ChunkTextError` is always retried fresh next call. The practical effect: `EmbeddingIndex::sync` only ever reads text for chunks that are new or changed (see "Embeddings"), and the `SemanticSearch` tool's semantic/lexical tiers only read it for a query's top-K results (or every chunk, for the lexical fallback's scan) — never resident for the whole corpus at once.

**Persistence**: `ChunkIndex`'s metadata is mirrored to the `chunks`/`files` tables of a per-repository `infra::index_store::IndexStore` (SQLite, at `~/.atlas/embeddings/{repository_id}/chunks.db` — a **global** location, not inside the repo; see "Embeddings" below for how `repository_id` is derived) — `ChunkMetadata` in, `ChunkMetadata` out (`IndexStore::load_all_chunks`), no text. `ChunkIndex::load_metadata` bulk-repopulates the resident `DashMap` from that on a cold start (a new `index_root` this process hasn't seen yet — first sync since app launch, or switching to a different project), so the metadata a diff needs (`file_hash_for`, `file_ids`) survives a restart without a repo rescan. `services::index_store_ensure::open_for(storage_dir)` is the read-only guard in front of this: it compares the store's persisted `chunk_version`/`index_version` meta rows against the running binary's `CHUNK_VERSION`/`repo_index::INDEX_VERSION`, reporting a mismatch as `stale` rather than repairing it inline — it deliberately does **not** check `index_root` (see "Embeddings" below for why the same repo cloned/worktreed to a second local path must not count as staleness) — repairing (wiping the store and the sibling `vectors.usearch`, then rewriting `chunk_version`/`index_version`/`index_root`/`repository_url`/`revision` meta) only happens via `index_store_ensure::repair_stale`, called from within a real `embedding_sync`, never from a read-only attach/status path (see "Embeddings" below for why: an eager status check must never block on a synchronous wipe).

## Embeddings

Built on top of Chunk Index: `ChunkIndex → EmbeddingBuilder → EmbeddingIndex (usearch)`. This is the layer the `SemanticSearch` tool's semantic tier actually queries (see "Tools implemented today") — everything before it only produces addressable text, nothing before it produces a vector.

```rust
pub trait EmbeddingProvider: Send + Sync {
    fn embed(&self, texts: &[&str]) -> Result<Vec<Embedding>, EmbeddingError>;  // batched
    fn dimensions(&self) -> usize;
}
```

**Two providers, one persisted choice** (`AppSettings.embedding: EmbeddingProviderConfig`, global — not per-project):
- **Local** (default) — `infra::embedding_providers::local::LocalEmbeddingProvider`, wrapping `fastembed`'s BGE-M3 (int8 ONNX, 1024-dim, HF repo `gpahal/bge-m3-onnx-int8`). Chosen for multilingual strength (this app's primary content language is Russian). Not bundled — `~570MB`, downloaded on demand and cached at `~/.atlas/models` on first use, same "fetch once, cache locally" shape as any `hf-hub`-backed tool.
- **Remote** — `infra::embedding_providers::remote::RemoteEmbeddingProvider`, a full (not stub) OpenAI-compatible client: `POST {base_url}/embeddings` with `{"input":[...],"model":...}`, `Authorization: Bearer {key}`, parses `{"data":[{"embedding":[...]}]}` — works against OpenAI, Together, Mistral, or a local Ollama/LM Studio server. The API key is never stored in `settings.json`; it goes through `infra::embedding_credentials_store` (AES-256-GCM, the same encryption key `key_management` already uses for the Git SSH private key).

Both are synchronous (`fastembed` has no Tokio dependency; the remote client uses blocking `ureq` rather than expanding this project's minimal `tokio` feature set) — callers run `embed()` inside `spawn_blocking`, same as `check_standards`/`ai_execute_tool`.

**Storage location & repository identity** (`infra::repository_identity`, `commands::embeddings::resolve_index_paths`): the per-repository `chunks.db`/`vectors.usearch` pair (see "Persistence" above and "Vector storage" below) lives in a **global**, user-level cache — `~/.atlas/embeddings/{repository_id}/` — not inside the repo itself, unlike `project.json`/`workspace.json`/`layout.json`, which stay at `{repoRoot}/.atlas/`. `repository_id` is `SHA-256` hex of the repo's canonical remote URL (`infra::repository_identity::resolve`, via `git2` — picks `origin` if present, else the sole remote, reusing the exact preference `infra::git_repo::default_remote_name` already used for push; normalizes the `https://`/`ssh://`/SCP-like `user@host:path` forms and a trailing `.git`/`/` down to one `host/path` string, so equivalent remotes collapse to the same id). Deliberately **not** the current revision — baking the git commit into the id would turn every commit into a brand-new, empty cache folder; the current HEAD revision is instead written as informational-only metadata (`repository_url`/`revision` meta rows, from `index_store_ensure::repair_stale`) alongside the existing `chunk_version`/`index_version`/`index_root`, so a store can be inspected/compared against the state it was last built from without that comparison driving recompute — the actual "did anything change" signal stays the existing per-file/chunk `blake3` hash diff (see "Incremental sync" below). A repo with no resolvable remote (local-only, or not a git repo at all) falls back to a random UUID, generated once and persisted into that project's `{repoRoot}/.atlas/project.json` (`ProjectConfig.local_repository_id`) so it keeps resolving to the same cache folder across sessions. The practical effect: the same repository cloned to two different local paths, or simply moved on disk, now resolves to and reuses the *same* global cache instead of each getting its own copy — `index_root` (still always `project.root`, used only for walking files and resolving relative `FileId`s) is decoupled from where the store physically lives, which is why `index_store_ensure::open_for` no longer treats a different `index_root` as staleness (see "Chunk Index" above). Existing in-repo `{repoRoot}/.atlas/index/full-repo/` data from before this change is not migrated — it's simply never read again (still harmlessly gitignored), and a fresh index is rebuilt in the new global location via the normal incremental sync described below.

**Model download** (`services::embedding_model`): `model_status()` reports `NotDownloaded | Downloading{progress} | Ready | Error` by checking `hf-hub`'s cache directory without triggering a fetch; `download_model(app_handle)` triggers it and emits `embedding:model-download-progress` events with real, granular progress — not just 0%/100%. `fastembed`'s own `InitOptions` API has no byte-level download callback, but `download_weights_with_progress` sidesteps that entirely: it fetches the big weights file itself, directly via `hf_hub::api::sync::ApiRepo::download_with_progress` (constructing the same cache-layout `ApiBuilder` `fastembed` would use internally, so the file lands exactly where `fastembed`'s own subsequent `try_new` call expects to find it as a cache hit — no redundant download), implementing `hf_hub`'s `Progress` trait as `ProgressReporter` to turn each raw read-chunk callback into a `downloaded/total` fraction, throttled to roughly 1% steps (`should_emit_progress`, unit-tested) so a ~570MB file doesn't flood the frontend with tens of thousands of IPC events. `EmbeddingsTab.tsx` already renders this as a real percentage fill bar.

**Vector storage**: `infra::vector_store::VectorStore` wraps `usearch` (embedded HNSW/ANN, no server process, `MetricKind::Cos`). `usearch` keys entries by `u64`, not `ChunkId`, so `usearch_key(chunk_id)` derives one deterministically (`u64::from_le_bytes(blake3(chunk_id)[..8])`); `EmbeddingIndex` keeps a `key_to_chunk: DashMap<u64, ChunkId>` reverse map so `search()` can translate results back. `RepositoryIndex`/`ChunkIndex` hold every piece of chunk/file metadata a search result needs to be resolved back to a file and byte range.

`VectorStore::save(path)`/`VectorStore::load(dimensions, path)` persist the index to/from a `vectors.usearch` file — `load()`, deliberately not `usearch`'s mmap-backed `view()`, because the index must stay mutable for `upsert`/`remove` across the app's lifetime (a `view()`ed index is read-only by design). A `VectorStore` built via `load()` remembers its path so a later `clear()` also deletes the on-disk file (avoids a stale, wrong-dimension file surviving a rebuild) and so `EmbeddingIndex::sync` knows to `save()` again after mutating.

**Incremental sync** (`EmbeddingIndex::sync`, `services/embedding_index.rs`) does all three rules from the original request in one reconciliation pass over `chunk_index.chunk_ids()` vs. its own `records: DashMap<ChunkId, EmbeddingRecord>`:
- No record for a `ChunkId` → **new chunk**, its text resolved via `chunk_text::resolve_text` and queued.
- Record exists but `record.chunk_hash != chunk.metadata.hash` → **changed**, same treatment (chunk `hash` already encodes "did this span's content or position change" from the Chunk Index stage — `sync` doesn't need its own staleness logic). Unchanged chunks never have their text read at all.
- A `ChunkId` in `records` no longer present in `chunk_index.chunk_ids()` → **deleted**, removed from both `records` and the vector store.

Queued (new/changed) chunks are embedded in batches of `EMBED_PROGRESS_BATCH` (32) — one `provider.embed(...)` call per batch, not one call for the whole pending set — so an optional `on_progress: Option<&dyn Fn(usize, usize)>` callback can report `(embedded_so_far, total_pending)` between batches; `commands::embeddings::embedding_sync` turns that into `embedding:sync-progress` events (see below). An optional `store: Option<&IndexStore>` argument is written through at the same points `records` mutates (`upsert_embedding`/`delete_embedding`), and the vector index is `save()`d back to its `load`ed path once at the end if anything changed — a full-file `usearch` write per `sync()` call, not per chunk.

`EmbeddingIndexSlot` (`Mutex<Option<(PathBuf, usize, EmbeddingIndex)>>`, `commands/embeddings.rs`) is keyed by `(index_root, dimensions)`, not dimensions alone — either a different project (`index_root` changes — `AiAccessMode` no longer affects `index_root` at all, see "Storage location & repository identity" above) or a different provider/model (`dimensions` changes) invalidates the resident index. On a mismatch, `attach_embedding_index` doesn't always rebuild blank: it first checks the store's persisted `embedding_dimensions` meta value — if it matches the now-current `dimensions`, `EmbeddingIndex::load` reloads `vectors.usearch` + the SQLite `chunk_hash` mirror (`IndexStore::load_all_embedding_hashes`) instead of starting empty; if it doesn't (first sync ever, or the provider's dimension changed since last time), whatever's on disk for that mismatched dimension is dropped (`clear_embeddings` + delete `vectors.usearch`) rather than risked.

`IndexStoreSlot` (`Mutex<Option<(PathBuf, Arc<IndexStore>, bool)>>`) is the third such lazily-attached slot — one SQLite connection per `index_root`, shared by `ChunkIndex`'s cold-start reload and `EmbeddingIndex`'s persistence; the `bool` caches whether that attach was `stale` (see below) so later calls in the same session don't need to re-derive it, and `embedding_sync` flips it to `false` in place once it actually repairs a stale store. `commands::embeddings::attach_index_store`/`attach_embedding_index` are the two helpers both `embedding_sync` and `embedding_index_status` build on to reach this state without duplicating the attach-or-reload logic; `attach_embedding_index` takes an `allow_repair` flag so only `embedding_sync` (already mutating) can destructively drop mismatched-dimension `vectors.usearch`/`embeddings` rows — `embedding_index_status`'s read-only call just reports an empty index for that dimension without touching disk.

**Incremental file-watcher sync**: `services::index_watcher::IndexWatcher` (a generic `notify`-based watcher — root, debounce duration, and an injected `is_relevant`/`on_change` closure pair, decoupled from `services::file_watcher::FileWatcher`, which is a separate, older watcher hardcoded to `WorkspaceIndex`) is started for `index_root` by `ensure_incremental_watcher`, called from both `embedding_sync` and the read-only `embedding_index_status` — the latter is what makes watching begin the moment a project opens (`useEmbeddingIndexWarmup`), not only after the user's first manual sync. Its `on_change` reaction, `run_incremental_sync`, re-chunks and re-embeds exactly the one changed file (via `RepositoryIndex::update_file`/`remove_file`, new single-file counterparts to `build()`) — including a brand-new, never-before-tracked file: `IndexWatcher`'s own `is_relevant` filter is extension-only (doesn't know about `.gitignore`), so a genuinely untracked path first passes through `workspace_scanner::is_new_file_indexable(index_root, path)` — a depth-capped walk from the real index root (not the whole tree, and deliberately not just the file's parent directory either — see that function's own doc comment for why a parent-only walk can't correctly honor a whole-directory `.gitignore` rule) — before falling through into the same `update_file`/`build_file` chain already used for tracked files. A genuinely gitignored new file still never reaches it. `EmbeddingSyncGuard` (`Mutex<()>`, `commands/embeddings.rs`) serializes every full sync against every incremental tick (and, see below, the background backlog) so their multi-step read-then-write sequences over `RepositoryIndex`/`ChunkIndex`/`IndexStore`/`EmbeddingIndex` never interleave. `embedding:sync-progress` payloads carry a `trigger: "full" | "incremental" | "background"` field precisely so the UI (`useEmbeddingSetup`) can tell a real user-triggered sync apart from a quiet background tick and never show the wrong current/total numbers. `embedding_index_teardown` stops the watcher when a project closes without a new one opening in the same session (`ensure_incremental_watcher` itself only swaps it when a *different* project's `index_root` shows up).

**Open-files-first prioritization on a fresh project's first sync**: `embedding_sync` detects "first sync" as `chunk_index.chunk_ids().is_empty()` — every other call (routine re-sync, incremental tick) is untiered, exactly as before. On a first sync, `PriorityFilesSlot` (`Mutex<HashSet<FileId>>`, populated by the frontend calling `embedding_set_priority_files` with the currently open editor tabs' paths — `src/hooks/useEmbeddingPriorityFiles.ts`, fired on tab open/close) is expanded one hop via two independent mechanisms to get the priority set: open files plus their direct dependencies. `direct_dependencies` covers AsciiDoc includes/xrefs *and* JSON/YAML `$ref`s via `WorkspaceIndex::find_includes`/`find_references` (`infra/parsers/json.rs`/`yaml.rs` now walk their parsed `Value` tree for `"$ref"` entries and feed them into the exact same include-graph machinery AsciiDoc already used, bridged from `WorkspaceIndex`'s repo-root-relative `DocumentId` space into `FileId`'s `index_root`-relative space by a plain string-prefix helper — no filesystem calls). `RepositoryIndex::java_dependencies` covers Java `import`s separately, entirely in `FileId` space — `.java` is deliberately never a `WorkspaceIndex` document (that layer is scoped to files the editor can open; see `domain::supported_files::SUPPORTED_EXTENSIONS`), so Java's dotted-FQN imports (extracted by `JavaIndexer`, `domain::repo_index::ImportRef`) are resolved with a repo-local suffix-match heuristic instead of `WorkspaceIndex`'s directory-relative path join — no build-system/classpath awareness, an unresolvable (external/library) import silently drops, and a wildcard import (`import foo.bar.*;`) expands to every currently-indexed file in that package directory. That combined set is chunked+embedded inline so the command returns quickly; everything else is handed to `run_background_backlog_sync`, a detached task (`tauri::async_runtime::spawn_blocking`, not awaited by the command) that works through the rest in small batches, acquiring `EmbeddingSyncGuard` per batch (not once for the whole backlog) so a later manual sync or incremental tick can still interleave rather than wait out the entire first-sync backlog. `EmbeddingIndexStatus` gained a `background_pending: usize` field for this — `repo_index.file_ids().len() - chunk_index.file_ids().len()`, i.e. files the repo walk found but hasn't chunked yet — derived from live state rather than a hand-kept counter, so it survives a restart or a panicked background task without drifting; the UI (`AssistantPanel`/`EmbeddingsTab`) shows it as a small non-blocking note, never gating the sync action or the "completed" checklist state on it reaching zero.

**IPC surface** (`commands/embeddings.rs`, 11 commands): `embedding_get_config`/`embedding_set_config`, `embedding_set_remote_api_key`/`embedding_has_remote_api_key` (write-only key, mirrors `git_save_credentials`), `embedding_model_status`, `embedding_download_model` (async, streams `embedding:model-download-progress`), `embedding_cancel_model_download`, `embedding_sync` (async — full `RepositoryIndex.build()` rescan every call, but re-chunks only files whose hash changed since `ChunkIndex` last saw them via `ChunkIndex::file_hash_for`, then `EmbeddingIndex::sync`, tiered into priority/background on a fresh project's first sync (see above); emits `embedding:sync-progress` events — `phase: "chunking"|"embedding"`, `trigger: "full"|"incremental"|"background"` — while running; returns `SyncStats{embedded, skipped_unchanged, removed}` for whichever tier ran inline), **`embedding_index_status`** (async, read-only — attaches/cold-start-reloads the same state `embedding_sync` would use, but never walks the repo, never repairs a stale store, and never constructs a real `EmbeddingProvider`: dimensions come from `embedding_providers::expected_dimensions(&config)`, a plain config read, specifically so this stays cheap for the Local provider too — the naive `provider_for(...).dimensions()` would otherwise load the whole ~570MB ONNX model just to read a constant; also starts the incremental watcher, see above; returns `EmbeddingIndexStatus{synced, embeddedCount, stale, backgroundPending}` derived from the resident/persisted index itself, not from whether a sync happened to run earlier in this process — `stale: true` means a persisted index exists but predates a version bump and needs a real `embedding_sync` to repair, distinct from "never synced"), `embedding_index_teardown`, and `embedding_set_priority_files` (see above). `App.tsx` calls `embedding_index_status` eagerly via `useEmbeddingIndexWarmup` (`src/hooks/useEmbeddingIndexWarmup.ts`) as soon as a project opens — a fire-and-forget call purely so the backend attach happens immediately rather than waiting for the user to open a specific panel; it stores no state of its own. Frontend wrappers in `src/lib/embeddings.ts` (incl. `listenSyncProgress`, `setEmbeddingPriorityFiles`), shared state in `src/hooks/useEmbeddingSetup.ts` (`indexStatus`, refreshed on mount and after every `sync()`, is what lets the UI show real "already built"/"stale"/"background catch-up in progress" state across a component remount instead of resetting to "not yet synced").

**This is the first layer in this file with real UI**: a "Эмбеддинги" tab in Settings (provider choice, model download with a live progress bar, remote base URL/model/API key, manual sync trigger with live chunking/embedding progress) and a setup checklist in the RightDock "Ассистент" panel (`AssistantPanel.tsx`, replacing what had been an empty stub since the very first AI-harness stage) — "Настроить провайдера" / "Загрузить модель" (Local only) / "Синхронизировать индекс", each item clickable, both consuming the same `useEmbeddingSetup` hook so they never disagree about current state. Unlike the other two (genuinely one-time) checklist items, "Синхронизировать индекс" keeps its action button visible even once `completed` (`alwaysShowAction`) — docs keep changing, so re-sync must stay reachable, not permanently hidden behind a "Готово" badge. `AssistantPanel` deliberately does **not** re-`refresh()` `useEmbeddingSetup`'s state on `AiAccessMode` change anymore — one index now covers the whole repo regardless of mode (see "Storage location & repository identity" above), so switching the toggle only changes what the assistant is allowed to read/search, not what's indexed.

## LLM client

The provider layer the assistant chat feature calls into — config, credentials, an OpenAI-compatible HTTP client (streaming and non-streaming), a Settings UI, and a real chat surface in the right dock. Deliberately mirrors the Embeddings layer's own `domain`/`infra`/`services`/`commands` split (see above) rather than inventing new conventions. **`llm_chat_stream` now runs a real multi-turn tool-calling loop entirely server-side**: it advertises the current project's allowed tools (`services::ai_tools::llm_tool_definitions`), and whenever the model requests one or more, executes each via `execute_tool` (the same boundary `ai_execute_tool` uses, called directly rather than through IPC — see "IPC surface" above), feeds the results back, and calls the model again — until a round produces a final answer with no more tool calls. `AiAccessMode`/a customized allowlist gates this exactly like it gates the standalone tool endpoint. The chat UI renders every round's activity as permanent, chronological entries in the message transcript (not transient status), each expandable to show the raw arguments and full result — see "Tool-calling loop" and "Chat UI" below.

`domain/llm.rs`: `LlmProvider` trait (`chat`/`chat_stream`/`list_models`, synchronous — same `spawn_blocking` reasoning as `EmbeddingProvider`, this project's `tokio` has no `net` feature; `chat_stream` takes a caller-supplied `&dyn Fn(&str)` delta callback and returns the full accumulated reply once the stream ends), `ChatRequest`/`ChatResponse`/`LlmMessage`/`LlmToolDefinition`/`LlmToolCall` (protocol-agnostic; `LlmToolCall::arguments` stays a raw JSON string, matching the wire reality — parsing it into concrete tool args is `services::ai_tools::parse_tool_call`'s job, see "Tool-calling loop" below), `ModelLimit` (`context`/`output` token counts — informational only, not enforced anywhere in this client; merges through the same manifest-preset/settings-override layers as `model`), `LlmProviderConfig` (a persisted override or standalone custom entry), `LlmSettings` (`AppSettings.llm` — gained `debug_logging: bool`, see "Debug logging" below), `LlmProviderPreset` (one compiled-in manifest entry), `ResolvedLlmProvider` (the merged view everything else actually uses). Deliberately no `LlmProviderKind` protocol enum — every provider today speaks OpenAI-compatible; `infra::llm_providers::provider_for` is the one dispatch point a second protocol would extend.

`LlmMessage` now also carries `tool_calls: Vec<LlmToolCall>` (non-empty only on an `Assistant` message that requested tool calls, `#[serde(skip_serializing_if = "Vec::is_empty")]` so a plain `{role, content, toolCallId}` message the frontend builds stays byte-identical to before this field existed) and `ChatStreamResult` carries the same field for the same reason — it's both `LlmProvider::chat_stream`'s per-round return (the tool-calling loop reads it to decide whether to continue) and the outer `llm_chat_stream` command's return type, though by construction the command only ever returns once a round's `tool_calls` is empty, so the frontend never actually observes a non-empty value there. `domain::llm::sanitize_tool_call_arguments(calls)` replaces `arguments` with `"{}"` on any call whose JSON isn't a valid object before it's echoed back into the next request's history — real-world observed case: a model streams malformed `arguments` (e.g. `"{}\"\""`, valid JSON followed by trailing garbage), and at least one gateway 500s server-side when that gets echoed back verbatim; the model still sees the *real* (unsanitized) string when the tool call is actually executed, so it still gets an honest error to learn from.

**System providers are build-time data, not code**: `assets/llm/system_llm_providers.json` (loaded by `infra/llm_provider_manifest.rs` via `include_str!`, same embedding-over-Tauri-bundle-resources rationale as `common_spec_assets.rs`/`dictionary_assets.rs`) ships one preset today — `alfagen` (`https://alfagen.moscow.alfaintra.net/continue-dev/v1` — the `/v1` suffix is required by the real endpoint, found the hard way via a `400` until a working `curl` example revealed the missing segment), pinned to `defaultModel: "DeepSeek-V4-Flash"` (avoids a live `/models` round-trip on every chat turn) with `limit: {context: 1000000, output: 30000}` and a real bundled trust cert (see below). A downstream fork/rebrand edits or empties this one file and rebuilds; no `.rs` change needed either way.

**Resolution** (`services/llm_config.rs`, fully unit-tested, zero I/O beyond `settings_store`): `resolve_provider(id, &settings)` merges a manifest preset (if `id` matches one) with its settings-layer override (if any) — override field wins whenever `Some`, `None` means "inherit from the manifest." A non-system id resolves entirely from its settings entry. `effective_model` returns a pin (override or manifest `defaultModel`) without any network call, or falls back to the first result of a live `list_models()` call. Removing a *system* provider (`llm_remove_provider`) only clears its settings-layer override — the manifest preset itself is untouched; true removal is the manifest-edit-and-rebuild path above.

**Credentials**: `infra/llm_credentials_store.rs`, keyed by provider id (one encrypted `HashMap<provider_id, api_key>` blob, reusing `key_management`'s AES-256-GCM primitives exactly like `embedding_credentials_store` does) since more than one provider can be configured at once, unlike the single global embedding-provider choice.

**HTTP client** (`infra/llm_providers/openai_compatible.rs`): blocking `ureq`, same reasoning as `embedding_providers::remote`. One deviation from that sibling: a **per-provider `ureq::Agent`** (not the free `ureq::post`/`ureq::get` functions) built by `build_agent(trusted_cert_pem)`, because TLS trust is per-agent — when a provider has a trust-cert override or manifest cert, `ureq::tls::RootCerts::Specific` *replaces* that agent's trust store with just that certificate (`ureq::tls::Certificate::from_pem`); providers without one keep the default public WebPki root store, and since every provider gets its own agent there's no cross-provider trust interference. `build_agent` also sets `.http_status_as_error(false)` — ureq's default behavior turns a non-2xx status into a bare `Error::StatusCode(code)` *before* the caller can read the response body, which made a provider error like a rejected request or a server-side failure show up as an undiagnosable `"http status: 500"` with no detail. `ok_or_status_error(response)` (called after every `send_json`/`call` in `chat`/`chat_stream`/`list_models`) checks the status itself and, on failure, reads the body and folds it into the `LlmError::Http` message (capped at `ERROR_BODY_MAX_CHARS`, 2000, so a large HTML error page doesn't get dumped whole) — so an opaque gateway error now arrives as e.g. `http status 500: {"error":"Error processing request, traceId:..."}` instead of just the status code.

**Streaming** (`infra/llm_providers/openai_compatible.rs`, `commands/llm.rs`): `chat_stream` posts the same request shape as `chat` plus `"stream": true` (a `#[serde(skip_serializing_if = "std::ops::Not::not")]` bool field, so the non-streaming path's JSON stays byte-identical to before this existed), then reads the response body incrementally — `ureq` 3.3.0's `Body::into_reader()` doesn't buffer the whole body before returning (confirmed against the vendored source: the request/response cycle only drives the state machine through `RecvResponse`, body bytes are pulled lazily) — via `BufReader::lines()`, parsing each Server-Sent-Event `data: {...}` line with a pure, unit-tested `parse_sse_line` (`data: [DONE]` terminates the loop, a blank/non-`data:` line is ignored, a chunk with no `delta.content` contributes no text). Streamed tool calls arrive as fragments (`delta.tool_calls[]`, `id`/`function.name` only on the fragment where a call starts, `function.arguments` appended incrementally across however many further fragments share that `index`) — `ToolCallAccumulator` merges these by `index` (insertion-order `Vec`, not a `HashMap`, so calls finish in the order the model started them) into the final `Vec<LlmToolCall>`. Both `StreamDelta.tool_calls` and the non-streaming `WireResponseMessage.tool_calls` deserialize through a null-tolerant helper (`#[serde(deserialize_with = "deserialize_null_default")]`) — plain `#[serde(default)]` only covers a *missing* key, and several OpenAI-compatible servers explicitly send `"tool_calls":null` on a content-only chunk once `tools` is present on the request, which `Vec<T>`'s own `Deserialize` otherwise rejects outright ("invalid type: null, expected a sequence" — a real regression this app hit the first time `tools` started being sent). `llm_chat_stream` (async + `spawn_blocking`, same skeleton as the other async commands) emits each delta as a global Tauri event, `"llm:chat-stream-delta"` (`{delta: string}` payload) — the same plain `AppHandle::emit`/`@tauri-apps/api/event`'s `listen()` pattern already used by `embedding:sync-progress`/`embedding:model-download-progress` (`tauri::ipc::Channel<T>` has no precedent in this codebase). The command's own promise resolves with the authoritative full reply text of the *final* round once the loop ends; the frontend uses that to correct the trailing text block, a safety net against a dropped delta event rather than the primary path.

**IPC surface** (`commands/llm.rs`, 10 commands): `llm_get_settings`/`llm_set_settings`, `llm_list_providers` (the merged system+custom list the Settings picker renders), `llm_upsert_provider`/`llm_remove_provider`, `llm_set_api_key`/`llm_has_api_key` (write-only key, mirrors the embedding credentials commands), `llm_list_models` (async, live `/models` call), `llm_test_connection` (async — calls `list_models` and reports the count, or the error; deliberately never calls `chat`/`chat_stream`, no completion spent, no dependency on a resolvable model), and `llm_chat_stream` (async — the tool-calling loop, streamed; see "Tool-calling loop" below). `LlmProviderSlot` caches the constructed provider keyed by `(resolved, api_key)`, same shape as `EmbeddingProviderSlot`.

**Settings UI**: a "Провайдеры" tab (`LlmTab.tsx`/`useLlmSetup.ts`, mirroring `EmbeddingsTab.tsx`/`useEmbeddingSetup.ts` — `SectionId` is still `"llm"` internally, only the nav label changed, so `TopBar.tsx`'s "open Settings on the LLM tab" shortcut didn't need touching) — an accordion provider list (green check/warning icon per row for "has an API key saved" readiness, expand to edit), base URL (editable only for custom providers), a model dropdown (populated by `llm_list_models`, with an "Авто (первая доступная)" option), a certificate override textarea with a "сбросить к встроенному" action, API-key input (never pre-filled), the debug-logging checkbox (see "Debug logging" below), and the test-connection button.

A separate, sibling top-level Settings section, **"Разрешения"** (`PermissionsTab.tsx`, `SectionId: "permissions"`, its own nav row — not a sub-tab of the LLM/providers section), surfaces per-project auto-approved tools (`ai_get_auto_approved_tools`/`ai_set_tool_auto_approved`, see "Tool-calling loop" above): a static Russian label per `ToolName` (falling back to the raw wire name for anything unrecognized) with an "Отозвать" button, calling `setToolAutoApproved(name, false)` and removing the row from its own local list on success. Fetched once on mount; a "no project is open" failure renders a plain hint rather than the shared `.settings-error` banner, since that's an expected state here — unlike every other Settings section, this one is scoped to the currently open project, not global `AppSettings`.

**Chat UI** (`AssistantPanel.tsx`/`useLlmChat.ts`, in the right dock): a real, working conversation with real tool use, not a placeholder shell. Gated on **LLM readiness** (an active/first-resolved provider with a saved API key) rather than the embedding provider — an unconfigured embedding provider only shows a non-blocking info note (the `SemanticSearch` tool's lexical/symbol tiers still work with zero embeddings), parallel to the existing "index still building" note. The access-mode toggle (`useAiAccessMode`, `docsOnly`/`fullRepo`) lives right above the chat surface — the one control genuinely specific to talking to the assistant, not to indexing.

`useLlmChat` owns one conversation's state (`messages`/`sending`/`error`/an estimated `contextTokens` count) and does exactly one `streamLlmChat()` call per turn — the entire tool-calling loop above is invisible to it except via three live event listeners (delta / tool-call / tool-result) that build up permanent `MessageBlock`s on the in-flight assistant message (`src/lib/chatBlocks.ts`, a plain, JSON-serializable data model — deliberately, as the foundation a future chat-history-persistence feature would serialize as-is):

```ts
type TextBlock = { type: "text"; id: string; content: string };
type ToolCallBlock = {
  type: "toolCall"; id: string; name: string; argumentsJson: string;
  status: "running" | "done" | "error"; result?: ToolResult; errorMessage?: string;
};
type MessageBlock = TextBlock | ToolCallBlock;
```

A handful of pure transition functions in that same file do all the work: `appendDeltaToBlocks` (extends the trailing text block, or opens a new one if the last block is a tool call — a tool call always closes off whatever text preceded it), `appendToolCallBlock` (always appends a new `"running"` block, on `TOOL_CALL_EVENT`), `settleToolCallBlock` (finds the block by `id` anywhere in the array and flips it to `"done"`/`"error"` on `TOOL_RESULT_EVENT`), `correctTrailingText` (the final round's authoritative text corrects only the trailing text block — every earlier block, text or tool call, is untouched), and `markRunningToolCallsAsInterrupted` (sweeps any still-`"running"` block to `"error"` if the whole command rejects before it settled — a defensive backstop, not a common path). `chatMessageToPlainText`/`flattenBlocksToText` join non-empty text blocks (skipping tool-call blocks) for both the `contextTokens` estimate and replaying prior turns into `wireMessages` — intermediate-round prose (the model "thinking out loud" before invoking a tool) is now kept and replayed, not discarded, since it's genuinely shown to the user.

`AssistantToolCallBlock.tsx` renders one `ToolCallBlock` — a status icon (spinner/check/alert), `describeToolActivity`'s "what is/was being done" line, and once settled, `describeToolResult`'s one-line summary (e.g. `Строк: 42`, or for `semanticSearch`, a per-tier breakdown like `Результатов: 5 (семантика: 3, текст: 2)` — the direct answer to "are embeddings actually being used": any `текст` count means that many results fell back to the lexical tier). Collapsed by default; clicking the header expands the raw arguments (`formatToolArguments`, pretty-printed, or the raw string if unparseable) plus the full result — file content (capped at 4000 displayed characters, a rendering safeguard only, not a change to what the model received), the full file list, or every search match with a source badge (`describeMatchSource`: `семантика`/`имя`/`текст`, with a tooltip explaining which cascade tier answered it) — or the full error text. Nothing here ever disappears once appended, unlike the transient `toolActivity` status list this replaced.

The panel also has its own model picker (the same `.clone-select` dropdown pattern as `LlmTab.tsx`'s, writing through the same `updateProviderConfig` so Settings and the chat panel share one source of truth) and an estimated context-window usage bar under the message list — `estimateTokenCount` (`src/lib/tokens.ts`) is a `~4 chars/token` heuristic, **not** a real per-model tokenizer (none is available client-side, and no provider here returns usage counts), shown only when the active provider's `limit.context` is known. `src/lib/assistantConfig.ts` centralizes the handful of tunable constants and formatters shared across `LlmTab.tsx`/`AssistantPanel.tsx`/`useLlmChat.ts`/`AssistantToolCallBlock.tsx` — `buildAssistantSystemPrompt(mode: AiAccessMode)` (built per-request rather than a frozen string, so the date/timezone line and the current access-mode line never go stale mid-session; also now tells the model plainly that `readFile`/`listFiles`/`semanticSearch` are real callable tools, not implicit repo knowledge), `buildAccessModeChangeNotice(mode)` (inserted as its own message immediately before the next user turn whenever the toggle changed since the previous send — a single line deep in a long system prompt is too easy for a model to under-weight against what it said about itself a few turns ago, so a mid-conversation switch gets a message the model can't skim past), `describeToolActivity`/`describeToolResult`/`describeMatchSource`/`formatToolArguments` (above), the "Авто" model-picker sentinel value/label, the compose box's row count, and the context-bar warning threshold. Deliberate scope limit still standing: no context-window truncation of long histories.

**Persistence** (`infra::chat_store`, `commands::chat_history`, `src/hooks/useChatHistory.ts`): every chat is saved to a **global, cross-project** SQLite database at `~/.atlas/chat.db` — not per-repo, not inside the repo; a `chats` row (`id`/`repo_root`/`title`/`archived`/`todos`/`created_at`/`updated_at`) plus a `messages` table (`chat_id`, `ordinal`, opaque JSON `data`) scoped by a `repo_root` column and index, so chats from different repos share one file without colliding. `save_chat` upserts the `chats` row and replaces `messages` wholesale (delete-then-reinsert in one transaction) every time a turn settles (`useLlmChat`'s `onTurnSettled`, wired to `useChatHistory`'s `saveTurn`) — the full rich transcript, not a flattened summary: `MessageBlock`s (text *and* tool-call blocks, each with its `ToolResult` — including `FileDiffStats`'s real unified diffs) round-trip byte-for-byte, since `infra::chat_store` never parses a message's shape, only stores/returns whatever JSON it was given (the frontend's `ChatMessage`/`MessageBlock` union evolves independently). `useChatHistory`'s mount effect lists a repo's active chats most-recently-updated-first and auto-loads `chats[0]` — this *is* the "resume where I left off" behavior, not a separate feature: it re-runs every time `AssistantPanel` mounts (project open, or the assistant dock re-activated), including across a full app restart. The turn's todo checklist (`domain::ai_tools::Task`) rides along in the same `chats.todos` column, typed (not opaque, unlike messages — `Task` is already a stable shared type) and upserted alongside `title` on every save; `useLlmChat`'s `todoListRef`/`todos` seed from it (`initialTodos`) instead of always starting empty, so — unlike before — a chat's todo list survives a chat switch, a new chat, and an app restart exactly like its messages do.

The `alfagen` preset's `trustedCertPem` is the real internal CA root (`Alfa-Bank ST CA Root`, self-signed) — captured directly from the endpoint's own TLS handshake (`openssl s_client -connect alfagen.moscow.alfaintra.net:443 -showcerts`; the server conveniently sends its full chain — leaf, intermediate `Alfa-Bank ST CA Sub1`, and the root itself — so trusting just the root is sufficient). Not a secret (a CA root is public by design, sent to any TLS client that connects), so baking it into the bundled manifest is safe. `parse_trusted_certs` (`infra/llm_providers/openai_compatible.rs`) parses **every** certificate in a pasted PEM blob, not just the first (`ureq::tls::Certificate::from_pem` alone would only take the first) — so a user overriding this with a full chain (root + intermediate) via Settings gets all of it trusted, not silently just one certificate.

## Tool-calling loop

`commands::llm::run_tool_loop` — shared by `llm_chat_stream` (fresh start) and `llm_chat_stream_resume` (continuing a paused round, see "Confirmation pausing" below) — is the real implementation, a plain Rust `loop`, not a fixed-count `for`. Both callers pass the same 7 `State` params `ai_execute_tool` takes (repo/chunk index, the 3 embedding slots, the sync guard, the workspace index) so the loop can build its own `EmbeddingDeps` and call `services::ai_tools::current_scope()`/`execute_tool()` directly — see "IPC surface: `ai_execute_tool`" above for why this bypasses that command rather than calling through it. One iteration ("round") calls the model once (`ctx.provider.chat_stream`) and, if it requested one or more tool calls, executes every one of them before looping back; a round with no tool calls ends the loop with the final answer (`ChatStreamOutcome::Done`).

**Confirmation pausing**: the instant a *fresh* round (never a resumed one — a resumed round's decisions are already known) contains any call whose `ToolName::requires_confirmation` is `true` (`WriteFile`/`EditFile`/`DeleteFile`/`CreateDirectory`/`DeleteDirectory`/`Move`/`RequestFullRepoAccess` — not `Todo`, see "Tools implemented today"), the loop stops and returns `ChatStreamOutcome::PendingApproval` — nothing in that round has executed, not even other, non-risky calls bundled into the same round. The backend keeps **no server-side session state**: `PendingApproval{history, round, budget_used, calls, todos}` is the entire resumable checkpoint, sent back to `llm_chat_stream_resume` verbatim by the frontend alongside the user's per-call approve/deny decisions (`src/lib/llm.ts`'s `PendingApproval` type mirrors this exactly, round-tripped opaquely — never rendered; `todos` rides along in the same checkpoint for the same reason). The chat UI (`useLlmChat.ts`) shows each pending call inline as a card (`ToolApprovalCard`, `AssistantToolCallBlock.tsx`) with a 30s countdown (`TOOL_APPROVAL_TIMEOUT_MS`, `src/lib/assistantConfig.ts`), a real diff preview for a pending `writeFile` (see "The single entry point: `execute_tool`" above), and a "Разрешать всегда" ("don't ask again for this tool") option; an unanswered card auto-denies on timeout. That "always allow" choice is no longer merely in-memory for the current chat session — it's now persisted per-project via `ProjectConfig.ai_auto_approved_tools` (`ai_get_auto_approved_tools`/`ai_set_tool_auto_approved`, see "IPC surface" above), loaded once when a chat panel mounts and written the moment the user clicks it, so a tool trusted in one conversation stays trusted in every later conversation on the same repo, and across app restarts. Granting is chat-side (`useLlmChat.ts` calls `setToolAutoApproved(name, true)` from the approval card), but revoking now has its own surface too: Settings → "Разрешения" (`PermissionsTab.tsx`, a top-level Settings section of its own — see "LLM client"'s "Settings UI" above) lists every tool the currently open project has auto-approved (a static Russian label per `ToolName`, falling back to the raw wire name for anything unrecognized) with an "Отозвать" button per row, calling `setToolAutoApproved(name, false)` and removing it from the list on success — this closed what used to be a one-directional gap (grant-only, revoke only by hand-editing `project.json`). A denied call is fed back to the model as a `Tool`-role `"Error: denied by user"` message, same as any other recoverable tool error — never a hard failure of the turn.

**Two independent termination limits**, checked together at the top of every round — the loop stops the instant either is hit:
- `MAX_TOOL_ITERATIONS` (20) — a flat cap on the number of rounds: a misbehaving/looping model shouldn't be able to hold the UI in a "thinking" state indefinitely.
- `MAX_TOOL_BUDGET` (100) — a **weighted** cap, since not every tool call costs the same. Each round's cost is `round_cost(calls)`: the sum of `domain::ai_access::ToolName::loop_weight` over every call the round contains (an unrecognized/malformed tool name floors to `1`, the same as the cheapest real tool, so budget always makes forward progress). `loop_weight` approximates relative time/expense, not risk (risk is `requires_confirmation`'s job) — `1` for the local-filesystem-only tools (`ListFiles`/`ReadFile`/`CreateDirectory`/`RequestFullRepoAccess`, the last being just a `project.json` write), `2` for `WriteFile`/`EditFile`/`Move` (the last two can also rewrite content beyond a single file — `EditFile` its own target, `Move` any other document referencing it — so they sit in the same cost class as a bare overwrite, not the cheap-syscall class), `4` for `SemanticSearch` (the one tool that can hit a network embedding-provider API, after cascading through symbol/lexical matching first). `MAX_TOOL_ITERATIONS` is kept as a backstop alongside it (protects against a misconfigured/zero tool weight ever making the loop unstoppable), but `MAX_TOOL_BUDGET` is the more sensitive limit in practice: an all-cheap-tool sequence is still effectively bounded by the unchanged 20-round backstop, while a `SemanticSearch`-heavy sequence now cuts off around 10 calls instead of 20. Both constants live in `commands/llm.rs`, easy to retune.

A round's cost is charged the moment its `tool_calls` are known — for a resumed round that means it's charged **again**, on top of whatever it was already charged when first computed (before pausing): a paused-then-resumed round is billed twice, deliberately mirroring how `round` itself already double-counts that same case (each `run_tool_loop` re-entry unconditionally increments `round` at the top before checking `resume`), so resuming can't be used to dodge the budget by pausing repeatedly.

Exceeding either limit hard-fails the whole `llm_chat_stream`/`llm_chat_stream_resume` call with `"assistant did not produce a final answer within {MAX_TOOL_ITERATIONS} tool-call rounds (budget {budget_used}/{MAX_TOOL_BUDGET})"` — rendered verbatim in the chat UI's generic error path (`AssistantConversation.tsx`), no dedicated UI for this case. The only other hard failure is `current_scope()` failing before the loop starts (no project open — not recoverable by retrying). Every other bad tool call — unknown name, malformed arguments even after the lenient retry below, a `NotAllowed` allowlist hit, a missing file, a user denial — is always fed back to the model as a `Tool`-role error message and the loop continues; it is never a hard failure of the whole turn (the model discovering an access-mode boundary mid-conversation is expected, legitimate behavior).

`services::ai_tools::llm_tool_definitions(scope)` builds one `LlmToolDefinition` (hand-written JSON Schema) per `ToolName` the scope allows, so a customized allowlist only ever advertises tools that will actually succeed — the model never discovers `ToolError::NotAllowed` only at execution time. `parse_tool_call(call)` matches `call.name` against the wire tags (exactly what `ToolCall`'s own `#[serde(tag = "tool")]` produces) and deserializes `call.arguments` into the matching args struct via `lenient_json_object` — a wrapper that, if strict `serde_json::from_str` fails, retries by deserializing only the *leading* JSON value from a `serde_json::Deserializer` (skipping the `end()` check that strict parsing does) and ignoring anything after it. This specifically rescues the "valid value + trailing garbage" corruption pattern real providers have been observed to stream (e.g. `arguments: "{}\"\""`) without masking genuinely broken JSON, which still errors exactly as before.

Two events surface a round's activity to the frontend, both in `commands/llm.rs`: `TOOL_CALL_EVENT` (`"llm:tool-call"`, `{id, name, arguments}` — `id` is the model's own `LlmToolCall::id`, added specifically so the frontend can correlate this with its settling result) fires immediately before executing each call; `TOOL_RESULT_EVENT` (`"llm:tool-result"`, `{id, result: Option<ToolResult>, error: Option<String>}`) fires once it settles, carrying the already-typed `ToolResult` (cloned, not reformatted — summarizing it for display is the frontend's job, see "Chat UI" above) or the error string. An earlier `CHAT_STREAM_RESET_EVENT` (which told the frontend to *discard* a non-final round's streamed prose) was removed once the frontend moved to a block-based transcript — that prose is now kept and shown as its own permanent text block instead of thrown away.

**Cancellation**: `ChatCancelFlag` (`commands::llm`, `Arc<AtomicBool>`, `app.manage()`'d once in `lib.rs`) is one flag for "the user asked the in-flight turn to stop" — this app has exactly one chat panel / one in-flight conversation at a time (same assumption `CHAT_STREAM_DELTA_EVENT` already makes), so no per-turn/per-request id is needed to disambiguate. The `llm_cancel_chat` command just sets it to `true`; `llm_chat_stream` (never `llm_chat_stream_resume`, which continues a turn already in progress and must not lose a cancel that landed while a `PendingApproval` card was showing) resets it to `false` at the start of every fresh turn. `run_tool_loop` polls it at two checkpoints, documented in full on the function's own doc comment: the top of the outer `loop` (catches a stop between rounds, between individual tool calls within one round — the `for call in &tool_calls` loop `break`s as soon as it sees the flag and falls through to this same checkpoint rather than duplicating it — and a stop that landed while a `PendingApproval` card was showing), and immediately after `LlmProvider::chat_stream` returns for a fresh round (catches a stop mid-stream or right as a round finished). Either checkpoint resolves `ChatStreamOutcome::Cancelled(ChatDone)` instead of continuing — critically, **no tool call from the round that was in flight when cancellation landed ever executes**, confirmation-gated or not, which is what lets a stop pre-empt a `WriteFile`/`DeleteFile`/... about to run, not just the model's next sentence. `LlmProvider::chat_stream` itself also takes a `cancelled: &dyn Fn() -> bool` closure, polled once per SSE line in `infra::llm_providers::openai_compatible`'s reading loop, so a long streamed response is cut short within roughly one chunk of the flag being set rather than only once it finishes naturally — the underlying blocking socket read still can't be interrupted mid-chunk without a bigger client rework, so a connection that stalls completely between chunks isn't helped by this.

On the frontend, `useLlmChat.ts`'s `stopChat` (wired to a "Stop" button in `AssistantConversation.tsx`, shown in place of the send button whenever `sending` is `true`) does two things: calls `cancelLlmChat()` (a no-op if nothing is running), and — if a `"pendingApproval"` card is currently showing — immediately denies every pending call via the same `decide` closure `collectDecisions` already exposes to the Approve/Deny buttons (bypassing the countdown), so `sendMessage`'s `while` loop proceeds straight to `streamLlmChatResume`, which then hits the first checkpoint before executing any of those now-denied calls. A `{status: "cancelled"}` outcome is handled almost identically to `{status: "done"}` (`correctTrailingText` still reconciles the trailing text block from `result.text`, empty when cancellation landed between operations rather than mid-stream — the frontend's own trailing block is a settled tool-call block at that point, never an open text block, so an empty string is a safe no-op there), plus two extras: the message gets `cancelled: true` (renders an "Остановлено пользователем" note, `AssistantConversation.tsx`), and `markRunningToolCallsAsInterrupted` sweeps any pending-approval card `stopChat` auto-denied but that never received its `TOOL_CALL_EVENT`/`TOOL_RESULT_EVENT` pair (since `run_tool_loop` returned before reaching it) to a settled `"error"` state instead of spinning forever.

## Debug logging

Optional, off by default (`LlmSettings.debug_logging`, toggled from a checkbox at the top of the "Провайдеры" settings tab) — a conversation can contain sensitive document content the user may not want written to disk. When on, `infra::llm_debug_log::log_request`/`log_response` append one JSON-Lines entry per request and per response/error, for *every* round of the tool-calling loop (not just the final one), to `~/.atlas/logs/llm.jsonl`:

```json
{"ts":1234567890,"providerId":"alfagen","round":1,"direction":"request","payload":{...ChatRequest...}}
{"ts":1234567891,"providerId":"alfagen","round":1,"direction":"error","payload":"http status 500: {\"error\":\"...\"}"}
```

Logs the already-typed `ChatRequest`/`ChatStreamResult` domain values (not raw HTTP bytes) — every field a request/response actually carries, without duplicating wire-format parsing into a second HTTP-client-specific logging path. Writes are best-effort: any failure (disk full, permissions, home dir unavailable) silently drops the entry rather than breaking a real chat turn. This is what turns an opaque provider error (a 500 with only a trace id in its body) into something diagnosable after the fact — the exact `ChatRequest` that produced it is sitting in the log file, round-numbered so a multi-round exchange can be reconstructed.

## Extending this

Adding a new tool touches exactly these spots:
