# Генератор описаний задач для Jira

## Зачем это нужно

Хорошее описание задачи в Jira экономит время на всех последующих этапах: разработчик не переспрашивает скоуп, QA пишет тесты прямо по AC, ревьюер видит риски заранее. Плохое описание — просто абзац текста — создаёт эти вопросы заново в каждом тикете.

Этот скилл — не про «красиво оформить», а про то, чтобы задача была однозначно понятна и проверяема без дополнительных созвонов.

## Как работать

1. **Собери вход.**  
   Пользователь обычно даёт:
   - проблему или контекст;
   - желаемое поведение;
   - что входит и не входит в скоуп;
   - иногда техническое решение, риски, ссылки на дизайн, спеку или документацию.

   Бери только то, что есть. Не выдумывай факты, которых нет.

2. **Проверь, не нужна ли декомпозиция.**  
   Если запрос похож не на одну задачу, а на несколько самостоятельных результатов, сначала предложи декомпозицию по разделу «Декомпозиция задачи» или скилу `jira-task-decomposition`.

   Не надо молча превращать большую фичу в один огромный тикет. Если пользователь явно просит один тикет, оформи один тикет, но кратко укажи, что задача выглядит крупной, и предложи возможные срезы.

3. **Если не хватает критичного — уточни.**  
   Если нет ни одного AC, непонятно, что именно должно измениться, или без этого нельзя написать проверяемые критерии, задай один уточняющий вопрос вместо фантазии.

   Если не хватает второстепенного — риски, ссылки, метрики, документация — просто не включай этот раздел.

4. **Сгенерируй описание строго по структуре ниже.**  
   Не создавай пустые разделы. Пустая секция хуже отсутствующей.

5. **Сохрани результат артефактом.**  
   Если доступен инструмент артефактов, вызови `artifact` с `op: "create"` и `kind: "jiraTicket"`, разложив текст по полям спека. Правки того же тикета делай через `op: "update"` по тому же `id`, а не вторым артефактом.

   Если составляешь несколько тикетов, то делай это последовательно один за другим, а не вызывай несколько тулов параллельно.

   Если артефакты недоступны, выведи результат как структурированный текст по полям спека без ручной wiki-разметки.

## Декомпозиция задачи

Перед генерацией полного описания проверь, является ли запрос одной задачей или набором задач.

### Признаки крупной задачи

Предложи декомпозицию, если есть хотя бы один признак:

- Не получается сформулировать одно «Что должно измениться» без союза «и».
- В запросе несколько самостоятельных результатов.
- Есть несколько ролей с разными сценариями или правами.
- Есть несколько экранов, эндпоинтов, сущностей, состояний или интеграций.
- Предварительных AC больше 7–8.
- Задача явно делится на этапы: минимальный путь, расширения, админка, уведомления, миграции, интеграции.
- Результат нельзя проверить без готовности других частей.
- Для реализации нужно несколько команд или сервисов.

### Что делать, если задача крупная

1. Не генерируй сразу один большой тикет.
2. Предложи 1–3 варианта срезов.
3. Для каждого среза укажи:
   - название;
   - результат: «Пользователь может…», «Клиент получает…», «Сервис умеет…»;
   - что входит;
   - что не входит;
   - 3–6 черновых AC;
   - зависимости;
   - что остаётся на следующие срезы.
4. После выбора среза оформи его как обычную задачу по обязательной структуре.

### Правила среза

- **Один тикет — один наблюдаемый результат.**  
  Если результат описывается через «и», вероятно, внутри несколько задач.

- **Режь по ценности, а не по техническим слоям.**  
  Плохо: «Сделать БД», «Сделать API», «Сделать фронт» без самостоятельного результата.  
  Лучше: «Пользователь может отметить взнос оплаченным», затем «Пользователь может изменить сумму».

- **Каждый срез должен быть проверяемым.**  
  Для выбранного среза можно написать проверяемые AC без ожидания остальных срезов.

- **Минимальный срез сначала.**  
  Сначала выдели самый маленький сценарий, который решает основную боль. Потом добавляй роли, каналы, исключения, массовые операции, админку, уведомления, настройки.

- **Технические срезы формулируй через контракт или возможность.**  
  Не «Сделать миграцию», а «Сервис умеет читать новую модель платежа».  
  Не «Сделать API», а «Клиент может вызывать метод по согласованному контракту».

- **Зависимости должны быть явными.**  
  Если срез зависит от другого среза, это нужно показать явно.

- **Не дробить ради дробления.**  
  Не надо создавать отдельные задачи на каждое поле, кнопку, код ошибки или тест, если это не самостоятельный продукт.

### Анти-паттерны декомпозиции

Не делай так:

- «Сделать таблицу в БД» как отдельная бизнес-задача без проверяемого результата.
- «Сделать API» без описания клиента и сценария использования.
- «Фронтенд» и «Бэкенд» как отдельные задачи, если ни одна из них не даёт самостоятельной проверяемой ценности.
- Отдельная задача на каждый код ошибки, если поведение однотипное.
- Отдельные задачи на каждого разработчика.
- Отдельные задачи на «написать тесты», если это не самостоятельный тестовый продукт.
- Дробить задачу до десятков микро-действий, если они относятся к одному пользовательскому сценарию.

## Обязательная структура вывода

Разделы идут строго в этом порядке. Раздел не создаётся, если для него нет данных.

1. **Почему задача существует**  
   1–3 предложения о проблеме пользователя и её причине. Без решения.

2. **Что должно измениться после задачи**  
   1 предложение целевого состояния от лица того, кто это изменение потребляет:  
   «Пользователь может X», «Клиент может X», «Сервис умеет X».  
   Не «Реализовать X» — это про исполнителя, а не про результат.

3. **Что входит в задачу**  
   Список конкретных, проверяемых пунктов объёма.  
   Каждый пункт — законченная возможность или наблюдаемая часть результата, а не шаг реализации и не абстракция вроде «доработать логику».

4. **Что не входит в задачу**  
   Явные исключения, особенно то, что легко спутать со скоупом.

5. **Техническое решение**  
   Если известно: подход и точка входа, 1–3 предложения. Спецификацию — ссылкой, не пересказом.

   Сюда не попадают:
   - перечни заголовков и полей запроса/ответа;
   - коды ошибок;
   - имена коллекций, таблиц и классов;
   - полная спецификация, если она уже есть во внешнем документе.

   Всё это устареет первым же изменением контракта.

6. **Критерии приёмки (AC)**  
   По одному проверяемому утверждению на сценарий. См. правила ниже.

7. **Критерии выполнения (DoD)**  
   То, что специфично именно для этой задачи: метрики, тесты, документация, деплой, флаг.

   Если в проекте есть общий DoD-шаблон, сослаться на него, а не дублировать.

8. **Риски**  
   Что может пойти не так и с каким последствием.

   Пример риска:  
   «Массовое обновление упрётся в лимит запросов соседнего сервиса».

   Ограничения и договорённости риском не являются:  
   «коды ошибок закреплены контрактом», «менять нельзя без согласования».  
   Им место в «Техническом решении».

   Нет риска — нет раздела.

9. **Ссылки**  
   Сгруппированы по типу: GIT, CONFLUENCE, FIGMA и так далее.

   Используй реальные URL, если они даны. Они попадают в описание задачи, а при публикации те же адреса дополнительно могут прикрепляться к задаче как Web Link. Это не дублирование, а два разных места: текст описания и панель Links.

## Правила для Acceptance Criteria

AC — самый важный раздел. По нему тестируют, поэтому к нему отдельные правила.

### Называй настоящее действующее лицо

Формулировка «Пользователь может / видит / получает» работает, только когда речь действительно о человеке.

У REST-метода потребитель — вызывающий клиент.  
У фоновой джобы — система.  
У внутреннего сервиса — соседний сервис или оператор.

Хорошо:

```text
Клиент получает 400 при невалидном теле запроса.
Сервис пересчитывает сумму оплаты после изменения статуса.
Пользователь видит уведомление об ошибке.
```

Плохо:

```text
Пользователь получает ошибку managerNotFound (500).
```

Если это не видит пользователь, не пиши так в пользовательских терминах.

### Один проверяемый сценарий на пункт

Если в формулировке есть «и», проверь, не стоит ли разбить на два пункта.

### Обязательно покрывай базовые сценарии

Там, где применимо к типу задачи, покрывай:

- happy path;
- граничные значения;
- валидацию;
- поведение при ошибке;
- поведение при успехе;
- обновление UI без reload или лишних действий пользователя.

### Не переноси таблицу ошибок построчно

«Поведение при ошибке» — это класс поведения, а не список кодов.

Хорошо:

```text
Невалидный запрос отклоняется, тело ответа содержит код ошибки.
```

Плохо:

```text
Пункт на каждый код ошибки, если поведение одинаковое.
```

Исчерпывающий перечень кодов живёт в спеке. Отдельный AC заслуживает только ошибка с нетривиальным поведением: идемпотентный повтор, отдельный сценарий восстановления, особый пользовательский ответ.

### Никаких оценочных формулировок

Плохо:

```text
Работает корректно.
Выглядит хорошо.
Обрабатывается правильно.
```

Хорошо:

```text
Система показывает сообщение об ошибке и не сохраняет изменение.
Пользователь видит обновлённый статус без перезагрузки страницы.
Клиент получает HTTP 201 и идентификатор созданной сущности.
```

### Если AC больше 7–8

Проверь, не получилось ли две задачи в одной. Иногда подробность оправдана, но чаще это сигнал к декомпозиции.

## Что не путать: AC и DoD

**AC** — про то, что делает и получает потребитель изменения: человек, вызывающий клиент, соседний сервис. Это функциональность.

**DoD** — про то, что для команды означает «задача точно готова»: метрики, тесты, документация, деплой, мониторинг. Это процесс.

Метрики и тесты не попадают в AC, даже если их «тоже нужно проверить».

## Форматирование для Jira

Ничего не форматируй руками. Разметку производит рендерер артефакта: нумерацию, жирные заголовки разделов, буллеты, группировку ссылок по типу. Он выдаёт wiki markup — формат, в котором Jira Server может хранить поле «Описание».

Из этого следуют правила:

- В поля спека пиши простой текст: одна мысль — один элемент массива.
- Не используй `##`, `- [ ]`, `|---|`, `*жирный*`, если они должны попасть в Jira как разметка.
- Не пиши описание задачи прозой в чат в расчёте, что пользователь сам всё соберёт, если доступен артефакт. Разметка появляется при сохранении в артефакт.
- Если артефакты недоступны, выведи результат как структурированный текст по полям спека без ручной разметки.

## Стиль

- Кратко, без вводных фраз и воды.
- Активный залог, конкретные глаголы: «может отметить», «видит уведомление», «получает ответ».
- Без канцелярита: не «должна быть предусмотрена возможность», а «пользователь может».
- Термины домена, заданные пользователем, использовать последовательно. Не заменять синонимами внутри одного тикета.
- Русский язык, деловой тон.

## Анти-паттерны — не делать

- Не смешивать AC и DoD.
- Не превращать «Что входит» в план работ.
- Не писать абстракции: «доработать логику», «улучшить обработку», «актуализировать данные».
- Не повторять один и тот же факт в нескольких разделах без необходимости.
- Не оставлять пользовательский ввод без негативных сценариев.
- Не создавать раздел «Риски», если для него нет данных.
- Не дублировать спецификацию, если она уже есть по ссылке.
- Не генерировать один огромный тикет, если задача явно требует декомпозиции.

## Примеры заполнения

### Пример 1 — фича с чётким скоупом

**Вход от пользователя:**

> Пользователи не могут отметить фиксированный взнос как оплаченный прямо из календаря, приходится идти в раздел ЕНП. Нужно, чтобы можно было отметить взнос оплаченным из календаря, менять сумму, всё синхронизировалось без reload. Белый список — не в этой задаче. Технически — новый endpoint wlbuh-enp-api/change-payments. Отмечать могут руководитель и бухгалтер.

**Выход** — вызов `artifact` с `op: "create"`, `kind: "jiraTicket"`, `title: "Оплата фиксированного взноса из календаря"` и таким `content`:

```json
{
  "why": "Пользователи не могут отметить фиксированный взнос как оплаченный напрямую из календаря. Из-за этого требуется переход в раздел ЕНП, что увеличивает количество действий.",
  "outcome": "Руководитель или бухгалтер может отметить фиксированный взнос как оплаченный и изменить сумму оплаты напрямую из календаря.",
  "inScope": [
    "Отметка фиксированного взноса оплаченным из календаря",
    "Изменение суммы оплаты из календаря",
    "Исключение взноса из оплаченных",
    "Отображение актуального статуса и сумм в календаре и виджете «К оплате» без перезагрузки"
  ],
  "outOfScope": [
    "Создание белого списка"
  ],
  "solution": "Использовать новый endpoint wlbuh-enp-api/change-payments для изменения суммы уже оплаченных взносов",
  "acceptanceCriteria": [
    "Руководитель или бухгалтер может открыть карточку события оплаты взноса из календаря",
    "Руководитель или бухгалтер может отметить взнос как оплаченный полностью",
    "Руководитель или бухгалтер может изменить сумму оплаты так, чтобы календарь и виджет «К оплате» показали пересчитанный итог",
    "Руководитель или бухгалтер может исключить взнос из оплаченных",
    "После сохранения изменений календарь и виджет «К оплате» обновляются без перезагрузки страницы",
    "Система не принимает отрицательную сумму и показывает сообщение об ошибке валидации",
    "Система не принимает сумму больше начисленной и показывает сообщение об ошибке валидации",
    "При ошибке сохранения пользователь видит уведомление об ошибке"
  ],
  "definitionOfDone": [
    "Добавлены метрики успешных и ошибочных операций изменения оплаты",
    "Добавлены UI-тесты на критический путь отметки и изменения оплаты"
  ]
}
```

Поля `risks` и `links` не заполнены, потому что пользователь не дал для них данных. Пустые разделы не отрисовываются.

Если изменение суммы включает много отдельных правил — уменьшение, увеличение выше зачтённого, частичная оплата, отдельный перерасчёт — лучше вынести изменение суммы в отдельный срез.

### Пример 2 — минимальный вход, часть данных нужно уточнить

**Вход от пользователя:**

> Нужна задача: экспорт отчёта по начислениям в CSV из карточки сотрудника.

**Реакция скилла:**

Входа достаточно для базовой структуры, но неясно, какие поля должны быть в CSV. Это критично для AC.

Нужно уточнить:

> Уточни, пожалуйста: какие поля должны быть в CSV-выгрузке (только начисления или ещё статус выплаты, период, подразделение)? Без этого не смогу корректно написать AC по содержимому файла.

Это предпочтительнее, чем придумать состав полей самостоятельно и выдать неточный AC.

## Когда не применять этот формат буквально

Для мелких технических тасков — рефакторинг, апгрейд зависимости, локальный фикс — полная структура избыточна.

В этом случае используй укороченную версию:

- Почему задача существует.
- Что входит в задачу.
- Критерии приёмки.
- Критерии выполнения.

Не создавай пустые разделы ради галочки.
