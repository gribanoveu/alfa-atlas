# Генератор описаний задач для Jira

## Зачем это нужно

Хорошее описание задачи в Jira экономит время на всех последующих этапах: разработчик не переспрашивает скоуп, QA пишет тесты прямо по AC, ревьюер видит риски заранее. Плохое описание (просто абзац текста) создаёт эти вопросы заново в каждом тикете. Эта скилл — не про "красиво оформить", а про то, чтобы задача была однозначно понятна и проверяема без дополнительных созвонов.

## Как работать

1. **Собери вход.** Пользователь обычно даёт: проблему/контекст, желаемое поведение, что входит/не входит в скоуп, иногда — техническое решение, риски, ссылки на дизайн/апи-спеку. Бери то, что есть; не выдумывай факты, которых нет.
2. **Если не хватает критичного** (нет ни одного AC, непонятно, что именно должно измениться) — задай один уточняющий вопрос вместо того, чтобы фантазировать. Если не хватает второстепенного (риски, ссылки) — просто не включай этот раздел.
3. **Сгенерируй описание** строго по структуре ниже.
4. **Сохрани результат артефактом** — вызови тул `artifact` с `op: "create"` и `kind: "jiraTicket"`, разложив текст по полям спека. Правки того же тикета — `op: "update"` по тому же `id`, а не второй артефакт. Пользователь получает вкладку с редактором и готовое описание, которое целиком вставляется в Jira.

## Обязательная структура вывода

Разделы идут строго в этом порядке. Раздел не создаётся, если для него нет данных — пустая секция хуже отсутствующей.

1. **Почему задача существует** — 1–3 предложения о проблеме пользователя и её причине. Без решения.
2. **Что должно измениться после задачи** — 1 предложение целевого состояния от лица того, кто это изменение потребляет: «Пользователь может X», «Клиент может X». Не «Реализовать X» — это про исполнителя, а не про результат.
3. **Что входит в задачу** — список конкретных, проверяемых пунктов объёма. Каждый пункт — законченная возможность, которая появляется у потребителя, а не шаг реализации и не абстракция вроде «доработать логику». См. анти-паттерны ниже: этот раздел чаще всего и превращают в план работ.
4. **Что не входит в задачу** — явные исключения, особенно то, что легко спутать со скоупом.
5. **Техническое решение** — если известно: подход и точка входа, 1–3 предложения. Спецификацию — ссылкой, не пересказом. Сюда **не** попадают: перечни заголовков и полей запроса/ответа, коды ошибок, имена коллекций, таблиц и классов. Всё это уже есть в спеке, и скопированное сюда устареет первым же изменением контракта.
6. **Критерии приемки (AC)** — по одному проверяемому утверждению на пункт. См. правила ниже.
7. **Критерии выполнения (DoD)** — то, что специфично именно для этой задачи (метрики, тесты, документация). Если в проекте есть общий DoD-шаблон — сослаться на него, а не дублировать.
8. **Риски** — что может пойти не так и с каким последствием. «Массовое обновление упрётся в лимит запросов соседнего сервиса» — риск. Ограничения и договорённости («коды ошибок закреплены контрактом», «менять нельзя без согласования») риском не являются: они ничем не грозят, они просто есть — им место в «Техническом решении». Нет риска — нет раздела.
9. **Ссылки** — сгруппированы по типу (GIT, CONFLUENCE, FIGMA), с реальными URL, если они даны. Они попадают в описание задачи, а при публикации те же адреса дополнительно прикрепляются к задаче как Web Link — так устроены задачи в этом трекере, и это не дублирование, а два разных места: текст описания и панель Links.

### Правила для Acceptance Criteria

Это самый важный раздел — по нему тестируют, поэтому к нему отдельные правила:

- **Назови настоящее действующее лицо.** Формулировка «Пользователь может / видит / получает …» — не заклинание: она работает, только когда речь действительно о человеке. У REST-метода потребитель — вызывающий клиент, у фоновой джобы — система. Пиши «Клиент получает 400 …», «Сервис пересчитывает …». Фраза «Пользователь получает ошибку `managerNotFound` (500)» — неправда дважды: этого не видит ни один пользователь, и внутренний код ошибки — не наблюдаемое им поведение.
- Один проверяемый сценарий на пункт — если в формулировке есть «и», проверь, не стоит ли разбить на два пункта.
- Обязательно покрыть (там, где применимо к типу задачи): happy path, граничные значения и валидацию, поведение при ошибке, поведение при успехе, обновление UI без reload/лишних действий.
- **Не переноси таблицу ошибок построчно.** «Поведение при ошибке» — это класс поведения, а не список кодов: «невалидный запрос отклоняется, тело ответа содержит код ошибки» — один AC, а не одиннадцать. Исчерпывающий перечень кодов живёт в спеке, на которую есть ссылка, и продублированный здесь он разойдётся с ней при первом же изменении. Отдельный AC заслуживает лишь ошибка, у которой своё, нетривиальное поведение (например, идемпотентный повтор вместо отказа).
- Никаких оценочных формулировок («работает корректно», «выглядит хорошо», «обрабатывается правильно») — только конкретное наблюдаемое поведение.
- Если AC перевалило за 7–8, это обычно не подробность, а две задачи в одной — проверь, не пора ли разделить.

### Что не путать: AC vs DoD

AC — про то, что делает и получает потребитель изменения: человек, вызывающий клиент, соседний сервис (функциональность). DoD — про то, что для команды означает «задача точно готова» (процесс: метрики, тесты, документация, деплой). Метрики и тесты никогда не попадают в AC, даже если их «тоже нужно проверить».

## Форматирование для Jira

**Ничего не форматируй руками.** Разметку производит рендерер артефакта: нумерацию и жирные заголовки разделов, буллеты, группировку ссылок по типу. Он выдаёт wiki markup — формат, в котором Jira Server реально хранит поле «Описание».

Из этого следуют два правила:

- В поля спека пиши **простой текст**: одна мысль — один элемент массива. Никаких `##`, `- [ ]`, `|---|` и `*жирного*` — они попадут в задачу буквально.
- Не пиши описание задачи прозой в чат, ожидая, что пользователь его скопирует. Разметка появляется только при сохранении в артефакт.

## Стиль

- Кратко, без вводных фраз и воды.
- Активный залог, конкретные глаголы («может отметить», «видит уведомление»), не канцелярит («должна быть предусмотрена возможность»).
- Термины домена, заданные пользователем (названия фич, продуктов, эндпоинтов), использовать последовательно — не заменять синонимами внутри одного тикета.
- Русский язык, деловой тон.

## Анти-паттерны — не делать

- Не смешивать AC и DoD.
- **Не превращать «Что входит» в план работ.** «Расчёт срока напоминания», «Сохранение пакета в коллекции», «Отправка метрики» — это шаги разработчика, а не объём. Объём — то, что появляется у потребителя: «Отложенная подача уведомления по истёкшему патенту». Как оно устроено внутри, решает исполнитель.
- **Один факт — один раздел.** Если проверка доступа уже названа в AC, её не надо повторять в «Что входит»; если метрика в DoD, её не надо дублировать в объёме. Повтор не усиливает — он создаёт два места, которые разойдутся при правке.
- Не оставлять AC без негативных сценариев, если функциональность подразумевает пользовательский ввод.
- Не создавать раздел «Риски», если для него нет данных.

## Примеры заполнения

### Пример 1 — фича с чётким скоупом

**Вход от пользователя:**
> Пользователи не могут отметить фиксированный взнос как оплаченный прямо из календаря, приходится идти в раздел ЕНП. Нужно, чтобы можно было отметить взнос оплаченным из календаря, менять сумму, всё синхронизировалось без reload. Белый список — не в этой задаче. Технически — новый endpoint wlbuh-enp-api/change-payments. Отмечать могут руководитель и бухгалтер.

**Выход** — вызов `artifact` с `op: "create"`, `kind: "jiraTicket"`, `title: "Оплата фиксированного взноса из календаря"` и таким `content`:

```json
{
  "why": "Пользователи не могут отметить фиксированный взнос как оплаченный напрямую из календаря. Из-за этого требуется переход в раздел ЕНП, что увеличивает количество действий.",
  "outcome": "Пользователь может отметить фиксированный взнос как оплаченный напрямую из календаря.",
  "inScope": [
    "Реализация флоу оплаты взноса из тела календаря",
    "Возможность изменить сумму оплаты",
    "Отображение изменений в связанных разделах",
    "Обновление данных в календаре без перезагрузки страницы",
    "Обновление данных в виджете «К оплате» с пересчётом итоговой суммы"
  ],
  "outOfScope": ["Создание белого списка"],
  "solution": "Использовать новый endpoint wlbuh-enp-api/change-payments для изменения суммы уже оплаченных взносов",
  "acceptanceCriteria": [
    "Пользователь может открыть шторку из календаря для события оплаты взноса",
    "Пользователь может отметить взнос как оплаченный полностью",
    "Пользователь может уменьшить сумму оплаченного взноса",
    "Пользователь может увеличить сумму оплаченного взноса выше значения текущего зачтённого",
    "Пользователь может исключить взнос из оплаченных",
    "Оплаченный взнос полностью переходит в раздел прошедших событий",
    "После сохранения статус обновляется без reload страницы",
    "Ошибка добавления отображается пользователю в виде уведомления",
    "Нельзя указать отрицательную сумму",
    "Нельзя указать сумму больше начисленной"
  ],
  "definitionOfDone": ["Добавлены метрики", "Добавлены UI-тесты на критический путь"]
}
```

Обрати внимание: нигде нет разметки — ни `##`, ни `- [ ]`, ни буллетов. Нумерацию разделов и списки построит рендерер, и в задаче это будет выглядеть так:

```text
*1. Почему задача существует*
Пользователи не могут отметить фиксированный взнос...

*3. Что входит в задачу*
 - Реализация флоу оплаты взноса из тела календаря

*6. Критерии приемки* *- AC* *(функционал работает)*
 - Пользователь может отметить взнос как оплаченный полностью
```

Поля `risks`, `outOfScope`… не заполнены там, где пользователь ничего не сказал, — пустой раздел просто не отрендерится. Это правильно, а не упущение.

### Пример 2 — минимальный вход, часть данных нужно уточнить

**Вход от пользователя:**
> Нужна задача: экспорт отчёта по начислениям в CSV из карточки сотрудника.

**Реакция скилла:** входа достаточно для «Почему»/«Что должно измениться»/базовых AC, но не хватает данных про роли и техническое решение — это не критично (можно опустить), а вот неясно, какие поля должны быть в CSV — это критично для AC, поэтому стоит уточнить:

> Уточни, пожалуйста: какие поля должны быть в CSV-выгрузке (только начисления или ещё и статус выплаты, период)? Без этого не смогу корректно написать AC по содержимому файла.

Это предпочтительнее, чем придумать состав полей самостоятельно и выдать неточный AC.

## Когда НЕ применять этот формат буквально

Для мелких технических тасков (рефакторинг, апгрейд зависимости) полная структура избыточна — раздел «Риски» часто не нужен, а «Acceptance Criteria» может выродиться в 1–2 пункта. В этом случае используй укороченную версию: «Почему» / «Что входит» / AC / DoD, без пустых разделов ради галочки.
