# Генератор описаний задач для Jira

## Зачем это нужно

Хорошее описание задачи в Jira экономит время на всех последующих этапах: разработчик не переспрашивает скоуп, QA пишет тесты прямо по AC, ревьюер видит риски заранее. Плохое описание (просто абзац текста) создаёт эти вопросы заново в каждом тикете. Эта скилл — не про "красиво оформить", а про то, чтобы задача была однозначно понятна и проверяема без дополнительных созвонов.

## Как работать

1. **Собери вход.** Пользователь обычно даёт: проблему/контекст, желаемое поведение, что входит/не входит в скоуп, иногда — техническое решение, роли, риски, ссылки на дизайн/апи-спеку. Бери то, что есть; не выдумывай факты, которых нет.
2. **Если не хватает критичного** (нет ни одного AC, непонятно, что именно должно измениться) — задай один уточняющий вопрос вместо того, чтобы фантазировать. Если не хватает второстепенного (риски, роли) — просто не включай этот раздел.
3. **Сгенерируй описание** строго по структуре ниже.
4. **Отдай результат в Jira-совместимом markdown** (заголовки, чеклисты, таблицы — см. раздел «Форматирование»). Если пользователь работает в чате — оформи как артефакт/файл, который можно скопировать целиком в Jira; ссылки (git/confluence/figma) вынеси отдельным блоком с пометкой, что их нужно добавить как Web Link, а не оставляй текстом внутри описания.

## Обязательная структура вывода

Разделы идут строго в этом порядке. Раздел не создаётся, если для него нет данных — пустая секция хуже отсутствующей.

1. **Почему задача существует** — 1–3 предложения о проблеме пользователя и её причине. Без решения.
2. **Что должно измениться** — 1 предложение целевого состояния в форме «Пользователь может X», не «Реализовать X».
3. **Что входит в задачу** — список конкретных, проверяемых пунктов объёма. Каждый пункт — законченная фича/действие, не абстракция вроде «доработать логику».
4. **Что не входит в задачу** — явные исключения, особенно то, что легко спутать со скоупом.
5. **Техническое решение** — если известно: endpoint/API/архитектурный подход, 1–3 предложения. Спецификацию — ссылкой, не пересказом.
6. **Acceptance Criteria** — чеклист `- [ ]`. См. правила ниже.
7. **Definition of Done** — чеклист того, что специфично именно для этой задачи (метрики, тесты, документация). Если в проекте есть общий DoD-шаблон — сослаться на него, а не дублировать.
8. **Риски** — только содержательные технические/продуктовые риски. Нет риска — нет раздела.
9. **Ролевая модель** — таблица «Роль | Разрешение», только если задача меняет права доступа.
10. **Ссылки** — список того, что добавить как Jira Web Link/Issue Link (GIT/CONFLUENCE/FIGMA и т.п.), с реальными URL, если они даны.

### Правила для Acceptance Criteria

Это самый важный раздел — по нему тестируют, поэтому к нему отдельные правила:

- формулировка «Пользователь может / видит / получает …», а не «система должна обеспечивать …»;
- один проверяемый сценарий на пункт — если в формулировке есть «и», проверь, не стоит ли разбить на два пункта;
- обязательно покрыть (там, где применимо к типу задачи): happy path, граничные значения и валидацию, поведение при ошибке, поведение при успехе, обновление UI без reload/лишних действий;
- никаких оценочных формулировок («работает корректно», «выглядит хорошо», «обрабатывается правильно») — только конкретное наблюдаемое поведение.

### Что не путать: AC vs DoD

AC — про то, что видит и делает пользователь (функциональность). DoD — про то, что для команды означает «задача точно готова» (процесс: метрики, тесты, документация, деплой). Метрики и тесты никогда не попадают в AC, даже если их «тоже нужно проверить».

## Форматирование для Jira

- Заголовки — `##`/`###` (для Jira Server/Data Center с классическим редактором — `h2.`/`h3.`).
- AC и DoD — обязательно чеклист `- [ ]`, не нумерованный и не обычный bullet-список.
- Ролевая модель — markdown-таблица (`| Роль | Разрешение |`) или `||заголовок||` для wiki-markup.
- Ссылки — отдельный блок с пометкой «→ добавить как Web Link», не markdown-ссылками в тексте описания.

## Стиль

- Кратко, без вводных фраз и воды.
- Активный залог, конкретные глаголы («может отметить», «видит уведомление»), не канцелярит («должна быть предусмотрена возможность»).
- Термины домена, заданные пользователем (названия фич, продуктов, эндпоинтов), использовать последовательно — не заменять синонимами внутри одного тикета.
- Русский язык, деловой тон.

## Анти-паттерны — не делать

- Не смешивать AC и DoD.
- Не включать в «Что входит» построчную техническую реализацию — только функциональный объём.
- Не оставлять AC без негативных сценариев, если функциональность подразумевает пользовательский ввод.
- Не дублировать ссылки текстом, если их можно прикрепить как Jira-поле.
- Не создавать раздел «Риски» или «Ролевая модель», если для них нет данных.

## Примеры заполнения

### Пример 1 — фича с чётким скоупом

**Вход от пользователя:**
> Пользователи не могут отметить фиксированный взнос как оплаченный прямо из календаря, приходится идти в раздел ЕНП. Нужно, чтобы можно было отметить взнос оплаченным из календаря, менять сумму, всё синхронизировалось без reload. Белый список — не в этой задаче. Технически — новый endpoint wlbuh-enp-api/change-payments. Отмечать могут руководитель и бухгалтер.

**Выход:**

```markdown
## Почему задача существует
Пользователи не могут отметить фиксированный взнос как оплаченный напрямую из календаря.
Из-за этого требуется переход в раздел ЕНП, что увеличивает количество действий.

## Что должно измениться
Пользователь может отметить фиксированный взнос как оплаченный напрямую из календаря.

## Что входит в задачу
- Реализация флоу оплаты взноса из тела календаря
- Возможность изменить сумму оплаты
- Отображение изменений в связанных разделах
- Обновление данных в календаре без перезагрузки страницы
- Обновление данных в виджете «К оплате» с пересчётом итоговой суммы

## Что не входит в задачу
- Создание белого списка

## Техническое решение
Использовать новый endpoint `wlbuh-enp-api/change-payments` для изменения суммы уже оплаченных взносов.

## Acceptance Criteria
- [ ] Пользователь может открыть шторку из календаря для события оплаты взноса
- [ ] Пользователь может отметить взнос как оплаченный полностью
- [ ] Пользователь может уменьшить сумму оплаченного взноса
- [ ] Пользователь может увеличить сумму оплаченного взноса выше значения текущего зачтённого
- [ ] Пользователь может исключить взнос из оплаченных
- [ ] Оплаченный взнос полностью переходит в раздел прошедших событий
- [ ] После сохранения статус обновляется без reload страницы
- [ ] Ошибка добавления отображается пользователю в виде уведомления
- [ ] Нельзя указать отрицательную сумму
- [ ] Нельзя указать сумму больше начисленной

## Definition of Done
- [ ] Добавлены метрики
- [ ] Добавлены UI-тесты на критический путь

## Ролевая модель
| Роль | Разрешение |
|---|---|
| Руководитель | Может отмечать взносы оплаченными |
| Бухгалтер | Может отмечать взносы оплаченными |
```

Обрати внимание: раздел «Риски» не создан, потому что пользователь его не упомянул — это правильно, а не упущение.

### Пример 2 — минимальный вход, часть данных нужно уточнить

**Вход от пользователя:**
> Нужна задача: экспорт отчёта по начислениям в CSV из карточки сотрудника.

**Реакция скилла:** входа достаточно для «Почему»/«Что должно измениться»/базовых AC, но не хватает данных про роли и техническое решение — это не критично (можно опустить), а вот неясно, какие поля должны быть в CSV — это критично для AC, поэтому стоит уточнить:

> Уточни, пожалуйста: какие поля должны быть в CSV-выгрузке (только начисления или ещё и статус выплаты, период)? Без этого не смогу корректно написать AC по содержимому файла.

Это предпочтительнее, чем придумать состав полей самостоятельно и выдать неточный AC.

## Когда НЕ применять этот формат буквально

Для мелких технических тасков (рефакторинг, апгрейд зависимости) полная структура избыточна — разделы «Ролевая модель» и часто «Риски» не нужны, а «Acceptance Criteria» может выродиться в 1–2 пункта. В этом случае используй укороченную версию: «Почему» / «Что входит» / AC / DoD, без пустых разделов ради галочки.
