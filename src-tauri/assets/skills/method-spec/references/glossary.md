# Язык постановки: термины и типовые формулировки

## Как говорить

| Пишем так | А не так |
|---|---|
| ручка, метод | «API endpoint», «хэндлер», «контроллер» |
| УЛ | «уполномоченное лицо», «пользователь ИБ» |
| ЮЛ, клиент | «организация-юрлицо», «компания-клиент» |
| СОПД | «согласие на обработку персональных данных» в тексте шагов |
| НТ, документы раскрытия налоговой тайны | «tax secret documents» |
| ЭА | «электронный архив» |
| МКС | «мастер-система клиентских данных» |
| оператор (Калуга Астрал) | «внешний ЭДО-провайдер» |
| пакет документов | комплект, набор, batch |
| upin / xpin, PIN EQ ЮЛ / PIN EQ УЛ | «идентификатор организации в системе» |
| коллекция TaxSecretsDocPack | «таблица», «монга», «репозиторий» |
| модуль подписи / SignModule | «сервис подписания» |
| стандартный responseError | «стандартный формат ошибки» |
| шаг 4 | «этап получения XML» |
| ИП | индивидуальный предприниматель |
| УСН | упрощенная система налогообложения |
| АУСН | автоматизированная упрощенная система налогообложения |

Аббревиатуры не расшифровываются — ни в скобках, ни сноской. Расшифровка сигнализирует, что документ писал человек не из контура.

## Что не должно попадать в текст

Имена классов, бинов, интерфейсов, пакетов; названия библиотек и фреймворков; слова «реактивный», «нон-блокинг», «консьюмер», «продюсер», «ретрай» — если это не часть бизнес-требования. Постановка живёт дольше реализации и не должна ломаться при переписывании кода.

Исключение — внешние контракты и системы: их имена как раз обязательны (`customers-api#getByIdsV2`, `/document/tax-secrets-consent`, метод `save` в `SignModule`, коллекция `TaxSecretsDocPack` и её поля).

## Типовые формулировки

**Про заполнение параметра**
- «Заполняется входным параметром A-userId»
- «Заполняется значением CORP-<ПРОЕКТ>»
- «Не заполняется»
- «Использовать значение inn из ответа, полученного на шаге 2»
- «Использовать значение fnsInfo.fnsId коллекции TaxSecretsDocPack»
- «Берётся из входного параметра A-userId»
- «передаем текущую дату» / «не передаем»

**Про вызов соседа**
- «Вызывается метод МКС для проверки прав пользователя.»
- «Для получения данных организации необходимо использовать сервис МКС customers-api#getByIdsV2.»
- «Необходимо получить документ СОПД из ОБИП. Для этого вызывается метод /document/tax-secrets-consent …»
- «В качестве ответа метод возвращает сформированный pdf документ.»

**Про ветвление и ошибки**
- «Если проверка выполнена успешно (resultCode = OK), выполняется следующий шаг.»
- «Если метод вернул ошибку, остановить работу метода и вернуть ошибку (500 ошибка c type = SERVER_ERROR, code = SIGN_ERROR, описание: "не удалось отправить файлы в SignModule").»
- «Если получена ошибка 4ХХ, 5ХХ - вернуть стандартный responseError.»
- «Вернуть исключение с http code 400 (Bad Request), указанием на некорректный параметр - "A-userId не указан", type = VALIDATION_ERROR и code = INCORRECT_CONTRACT»

**Про выходные данные соседа**
- «В ответе возвращается массив со списком компаний. Приведены только параметры, которые используются в методе для формирования СОПД по шаблону.»

**Про ответ ручки**
- «Сформировать ответ следующим образом:»
- «Проставляется по каждому отправленному документу»

## Мелочи оформления, по которым узнают свой документ

- Диапазоны кодов — кириллическими Х: «4ХХ, 5ХХ».
- Перенос строки — ` +` в конце строки, ставится часто.
- Значения enum и константы — как есть, латиницей, без кавычек: KALUGA, ALFA_BANK, BACKEND, NIB, CORP-<ПРОЕКТ>.
- Тексты ошибок — в двойных кавычках внутри предложения.
- Прочерк в пустой ячейке «Варианты значений» — дефис.
- Комментарии-подсказки для следующего автора остаются в документе как есть (`// инклюдим пример ответа…`) — не вычищать их при правке чужой постановки.
