## 1. Шапка документа

```asciidoc
= Rest-метод createSignOperationV2

:sectnums:
:sectnumlevels: 3
:toc: left
:toclevels: 3
:toc-title: Оглавление
```

Заголовок — тип транспорта + имя ручки в camelCase, как она называется в контракте. Без кавычек, без слова «метода API», без описания в скобках. Атрибуты всегда одни и те же, менять их не нужно.

## 2. Назначение

Два-четыре предложения. Что делает ручка, в каком модуле/сервисе живёт, для какой ветки бизнес-процесса используется сейчас.

Формулировка типовая: «Новая версия метода X создания … На текущий момент метод используется для ветки обмена с оператором для обмена с ФНС Калуга Астрал».

Если это новая версия — следом список отличий, каждое отличие одной строкой и по существу:

```asciidoc
*Отличия от метода createSignOperation*

- Реализация метода createSignOperationV2 на REST-API (createSignOperation Thrift Api)
- В методе createSignOperation данные передаются в теле запроса, в createSignOperationV2 - в заголовках и path
- При отправке документов в SignModule в методе createSignOperationV2 передаются 3 файла ...
```

Сравнение идёт по фактам: транспорт, расположение параметров, какие соседние ручки дёргаются, состав и количество файлов/документов, новые обязательные значения.

## 3. Описание входных/выходных параметров

### Входные

Форма таблицы зависит от транспорта метода — REST и Thrift не смешивать в одном документе.

**REST.** Таблица со столбцами: *Тип параметра | Параметр | Формат | Обязательность | Описание | Варианты значений*.

Первыми строками — `Method` (POST/GET/…) и `Endpoint` с полным шаблоном `https://{host}/<сервис>/<путь>/{pathParam}/...`; остальные ячейки в этих двух строках пустые.

Дальше — заголовки, потом path, потом body. Стандартный блок заголовков переносится без изменений:

| Параметр | Формат | Обязательность | Описание | Варианты значений |
|---|---|---|---|---|
| A-userId | string (length 6 or 9) | required | Идентификатор УЛ интернет-банка. Заполняется входным параметром A-userId | XAAAAA |
| A-customerId | string (length 6 or 9) | required | Идентификатор клиента. Заполняется входным параметром A-customerId | UAAAAA |
| A-userIp | string | optional | IP УЛ. | - |
| A-projectId | string | optional | Идентификатор приложения (модуля приложения) потребителя. | |
| A-clientType | string | required | Тип сервиса инициатора запроса. | |
| A-channelId | string | required | Идентификатор вызывающей системы (канала). | |

Во **входных параметрах самой ручки** описание заголовка заканчивается на общей фразе. В **вызовах соседних сервисов** к той же фразе дописывается, чем поле заполняется на этом шаге: «Заполняется значением CORP-<ПРОЕКТ>», «Заполняется значением BACKEND», «Заполняется значением NIB», «Не заполняется».

Обязательность пишется словами `required` / `optional` в таблицах контрактов и `да` / `нет` в таблицах body-структур — так исторически сложилось, оба варианта живые; внутри одной таблицы должен быть один вариант.

Вложенные поля body — через точку: `Agreement.managerName.firstName`. Порядок — как в контракте.

**Thrift.** Таблица со столбцами: *Параметр | Формат | Обязательный | Описание* (без «Тип параметра», обязательность — `да`/`нет`, без колонки «Варианты значений»).

Первой строкой — `Endpoint` с общим транспортным путём вида `{host}/<сервис>/tapi` (в отличие от REST, он не зависит от конкретного метода — методы различаются полем внутри тела запроса, а не путём).

Дальше — минимальный конверт `userData` (все подполя обязательные), переносится без изменений:

| Параметр | Формат | Обязательный | Описание |
|---|---|---|---|
| userData | struct | да | Данные пользователя |
| userData.id | string | да | Идентификатор пользователя (xpin/acus) |
| userData.authorizedApplicationId | string | да | Идентификатор приложения |
| userData.ip | string | да | IP-адрес пользователя |
| userData.customerId | string | да | Идентификатор клиента |

Это минимальный набор — у конкретного метода `userData` может нести дополнительное необязательное поле (например встречается `userData.location`, не всегда используемое). Это не часть стандарта, а особенность метода — сверяться с реальным контрактом, не достраивать по аналогии.

После конверта — собственные поля метода (например `organizationId`, `docPackId`), каждое отдельной строкой той же таблицы. Их состав нельзя изобретать — брать из контракта/вводных, как и любые другие параметры.

### Выходные

Таблица со столбцами *Параметр | Формат | Описание | Варианты значений*. Для структур формат — `struct`, для коллекций — `array`.

В описании поля сразу указывается источник значения: «использовать значение соответствующего documents.documentId коллекции TaxSecretsDocPack», «для документов из шага 4 - kndFile.content».

После каждой таблицы — подраздел `==== Пример запроса` / `==== Пример ответа` с `include::`.

## 4. Схема работы

```asciidoc
[plantuml, "<имяРучки>", png]
----

include::<имяРучки>.puml[]

----

image:<имяРучки>.png[]
```

Сам `.puml` — sequence-диаграмма: участники называются как системы («Клиент», «corp-<текущий-сервис>-api», «МКС», «SignModule», «ОБИП»), стрелки подписаны шагами из раздела «Алгоритм работы». Если исходника диаграммы нет — оставить блок с плейсхолдером и сказать об этом автору, а не выдумывать содержимое.

## 5. Алгоритм работы: валидация

Раздел открывается нумерованным списком шагов — ровно тем, который дальше разворачивается в подразделы:

```asciidoc
. Валидация входных параметров
. Шаг 1. Проверка права подписания
. Шаг 2. Получение информации по организации +
...
. Формирование ответа
```

Дальше `=== Валидация входных параметров` и таблица *Параметр | Условие | Результат*.

Правила:
- у одного параметра может быть несколько условий — они объединяются вертикальным спаном (`.2+|A-userId`, `.3+|docPackId`);
- условие пишется как факт, а не как проверка: «Параметр имеет значение null или пусто», «Длина значения не равна 6 символам либо символы не являются алфавитно-числовыми», «В БД TaxSecretsDocPack у пакета документов operator имеет значение, отличное от KALUGA»;
- результат — целиком: http-код, текст для пользователя, `type` и `code`. Пример: «Вернуть исключение с http code 400 (Bad Request), указанием на некорректный параметр - "A-userId не указан", type = VALIDATION_ERROR и code = INCORRECT_CONTRACT»;
- проверки принадлежности сущности клиенту описываются вместе с валидацией, а не внутри шагов;
- на ненайденную сущность текст ошибки нейтральный («Не найден пакет документов») — не раскрывать, что именно не сошлось.

## 6. Алгоритм работы: шаги

Заголовок: `=== Шаг N. <Что делаем>` — отглагольное существительное: «Проверка права подписания», «Получение информации по организации», «Создание XML форм», «Запрос файла СОПД», «Отправка документов в SignModule».

Внутри — по схеме из SKILL.md. Дополнительно:

- **Мапинги.** Если данные шага нужно сопоставить с сущностями из БД или с полями чужого контракта — отдельный подраздел `==== Маппинг документов` / `==== Маппинг полей метода` с таблицей *слева источник — справа приёмник*. Константы пишутся прямо в ячейке значения («MMB_Common», «Отчетность», «текущая дата и время», «sign», «sendToTheBank»).
- **Ссылки на шаги.** Только по номеру шага: «данные, полученные на шаге 2».
- **Внешняя документация.** Если пример запроса лежит в артефактории или другой вики — вместо `include::` даётся голая ссылка отдельной строкой под `==== Пример запроса`.
- **Пустой ответ.** Так и пишется: «Пустой ответ».
- **Условие перехода.** Каждый шаг заканчивается предложением вида «Если метод не вернул ошибку, перейти к следующему шагу, иначе остановить работу метода и вернуть ошибку (500 ошибка c type = SERVER_ERROR, code = DOCUMENTS_ERROR, описание: "…")».

Перенос строки внутри абзаца — плюс в конце строки (` +`). Это стандартный способ, применяется щедро.

## 7. Формирование ответа

`=== Формирование ответа` и таблица *Параметр | Правило заполнения*. По строке на каждое поле ответа, включая вложенные. Правило — откуда берётся значение, с указанием шага и имени поля источника.

## 8. Работа с include

- Примеры запросов/ответов самой ручки лежат рядом: `include::request.adoc[]`, `include::response.adoc[]`.
- Примеры вызовов соседей — в общей папке: `include::../_external/<домен>/<сервис>/<имяМетода>-request.adoc[]` и `-response.adoc`. Домен — `mks` для платформенных сервисов, иначе имя сервиса верхнего уровня.
- Общее описание формата ошибки — `include::../CompositeException.adoc[]`.
- В примере ответа соседа желательно два кейса: успешный и ошибочный.
- Имена файлов include выводятся из имени вызываемого метода, а не придумываются. Если файла ещё нет — всё равно поставить `include::` по правилу именования и предупредить автора, что его нужно создать.

## 9. Синтаксис таблиц AsciiDoc

Таблица открывается и закрывается `|===`. Первая строка — заголовки со звёздочками: `|*Параметр* |*Формат* |*Описание*`. Дальше каждая ячейка с новой строки, пустая ячейка — просто `|`.

Компактная запись «всё в одну строку» тоже встречается и допустима для длинных body-структур:

```asciidoc
|Body| Agreement.fnsId | string | да | Код налогового органа - использовать значение fnsInfo.fnsId коллекции TaxSecretsDocPack |
```

Внутри ячейки перенос делается пустой строкой — так оформляются перечисления вариантов значений (`OK - …` / `FAILED - …` / `ERROR - …`), где к каждому варианту сразу приписано, что делать методу.
