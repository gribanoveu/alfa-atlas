# Ошибки: коды, типы, формулировки

## Раздел «Обработка ошибок»

Всегда последний раздел документа. Устроен так:

```asciidoc
== Обработка ошибок
Описание приведено по ссылке ниже.

include::../CompositeException.adoc[]

*Коды ошибок*

|===
|*Условие* |*Описание* |*Type* |*Code*
...
|===
```

Таблица — сводка **всех** ошибок документа, по строке на каждую. Условия идут в том же порядке, в каком встречаются в документе: сначала валидация (в порядке параметров), затем шаги по номерам.

Условие для шага начинается с номера и названия шага: «Шаг 5. Запрос файла СОПД. Не удалось получить СОПД».

Описание в этой таблице — тот же текст, что уходит пользователю в ошибке, с заглавной буквы.

Каждая строка таблицы обязана иметь пару в теле документа (в таблице валидации или в завершающем абзаце шага), и наоборот. Расхождение между ними — самая частая претензия к постановке на ревью.

## Стандартные пары type/code

| Ситуация | http | type | code |
|---|---|---|---|
| Не передан или невалиден входной параметр | 400 | VALIDATION_ERROR | INCORRECT_CONTRACT |
| Сущность не найдена / не связана с клиентом | 400 (или 404) | VALIDATION_ERROR | INCORRECT_CONTRACT |
| Нет прав на работу с организацией | 403 | ACCESS_DENIED | PERMISSION_FAILED |
| Техническая ошибка при проверке прав | 403 | ACCESS_DENIED | PERMISSION_ERROR |
| Не получены данные организации | 500 | SERVER_ERROR | CUSTOMER_SERVICE_ERROR |
| Не получены данные пользователя | 500 | SERVER_ERROR | USER_SERVICE_ERROR |
| Не удалось сформировать/получить документ | 500 | SERVER_ERROR | DOCUMENTS_ERROR |
| Не удалось отправить документы на подпись | 500 | SERVER_ERROR | SIGN_ERROR |

`code` именуется по домену сбоя: `<ЧТО>_ERROR` для технических (`DOCUMENTS_ERROR`, `SIGN_ERROR`) и `<СЕРВИС>_SERVICE_ERROR`, когда сбой в конкретном сервисе-соседе. Новый код заводить только если ни один существующий не подходит по смыслу — потребители разбирают ошибки именно по `code`.

Эта таблица — дефолт для **нового** случая, когда точного `type`/`code` ещё нет. Если у ошибки уже есть закреплённый `type`/`code` — из существующей версии документа, контракта или реализации — и он расходится со стандартной парой, не переписывай его под таблицу «для порядка»: код — часть контракта, который разбирают потребители, менять его самовольно нельзя. Оставь как есть и явно скажи о расхождении в ответе, а решение — согласовать код или оставить — за пользователем.

Один `code` может стоять у нескольких условий (так, `DOCUMENTS_ERROR` покрывает и формирование XML, и получение СОПД) — это нормально, дублировать домен ради уникальности не нужно.

## Формулировки текста ошибки

Текст пишется от лица системы, коротко, без «пожалуйста» и без технических подробностей наружу:

- пропущенный параметр: «A-userId не указан»;
- невалидный формат: «A-userId должен содержать 6 алфавитно-цифровых символов»;
- не найдено: «Не найден пакет документов» — одинаковый текст для всех причин ненахождения, чтобы не подсвечивать внутреннюю логику;
- нет прав: «Отсутствуют права на работу с организацией»;
- сбой соседа: «не удалось получить данные организации в customers-api», «не удалось получить НТ запросом downloadAgreementNTV2», «не удалось отправить файлы в SignModule» — с прямым указанием, какой вызов не отработал.

В таблице шага текст даётся в кавычках внутри скобок вместе с кодом; в сводной таблице «Обработка ошибок» — отдельным столбцом без кавычек.

## Обработка ответов соседа

Если сосед возвращает свой enum результата — разобрать в таблице выходных параметров каждое значение и сразу написать реакцию:

```
OK - успешная проверка. При данном результате переход на следующий шаг.

FAILED - Пользователь не имеет прав на работу с организацией. При данном результате сформировать ошибку вида "…" (стандартный responseError, 403 ошибка c type = ACCESS_DENIED, code = PERMISSION_FAILED), завершить работу.

ERROR - Получена техническая ошибка. При данном результате сформировать стандартный responseError (403 ошибка c type = ACCESS_DENIED, code = PERMISSION_ERROR), завершить работу.
```

Транспортные ошибки соседа описываются отдельной строкой: «Если получена ошибка 4ХХ, 5ХХ - вернуть стандартный responseError».

Компенсации и откаты, если они есть, описываются в самом шаге — не в разделе ошибок. Если по бизнесу отката нет, это тоже стоит написать явно одной строкой.
