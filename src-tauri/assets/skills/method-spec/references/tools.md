# Тулы Atlas: что вызывать и как адаптировать результат

> **Цель файла**: точные вызовы тулов приложения и правила правки того, что они возвращают. Читай перед созданием папки, перед первой таблицей и перед финальной проверкой.

## Когда применять

- Создаёшь папку метода.
- Берёшь разметку таблицы.
- Не хватает состава запроса/ответа — нужен артефакт.
- Прогоняешь готовый документ через `check`.

---

## 🛑 Критические правила

1. **Разметку таблиц бери из тула, а не по памяти.** Шаблоны каталога — это разделы постановки в том виде, в каком их описывает этот скилл: правильный уровень заголовка, правильный набор колонок, заполненные ячейки. Вставляй как есть и меняй только содержимое строк.
2. **Расходится с этим скилом — прав скилл.** Каталог и справочники держат синхронно; если шаблон вдруг отличается от `references/structure.md` или `references/errors.md`, следуй справочнику и скажи об этом пользователю.
3. **Пустых ячеек в таблицах от четырёх колонок не бывает** — проверка K.4.2/K.5.2 считает такую таблицу незаполненной. Нечего написать — ставь дефис.

## 1. Создание папки — `createDirectory`

- **Вызов**: `createDirectory` с `path` (путь папки метода) и `template: "restEndpoint"`.
- **Создаёт**: `{methodName}.adoc`, `request.adoc`, `response.adoc`, `{methodName}.puml`, где `{methodName}` — последний сегмент пути. Одна папка — один метод.
- Имена `request.adoc`/`response.adoc` всегда без префикса метода. Не переименовывай и не создавай эти файлы вручную.
- В результате приходит `createdFiles` с точными путями — это авторитетный список, перепроверять его через `listFiles` не нужно.
- Тул падает, если путь уже существует. Значит, это правка существующей постановки, а не создание новой.

> **Про таблицы внутри `request.adoc` / `response.adoc`**: скаффолд кладёт туда свою разметку (пять колонок, без «Тип параметра») — это оформление *примера*, а не описание контракта. Не переоформляй её под форму из каталога шаблонов. Авторитетное описание параметров всегда живёт в `{methodName}.adoc`.

## 2. Шаблоны таблиц — `getAsciidocTemplates`

**Вызов**: `getAsciidocTemplates` с `ids: [...]` — несколько шаблонов за один вызов.

Сначала определи транспорт метода, от него зависит форма таблицы входных параметров.

| id | Что даёт | Готовый раздел |
| --- | --- | --- |
| `http-method` | 6 колонок, строки `Метод`/`Endpoint` через `5+\|`, полный блок заголовков `A-*` | `=== Входные параметры` REST-метода |
| `thrift-method` | 4 колонки, эндпоинт и конверт `userData` | `=== Входные параметры` Thrift-метода |
| `response-fields` | 5 колонок, как у скаффолда и артефакта | `=== Выходные параметры` |
| `validation-fields` | 3 колонки с примером объединения ячеек `.2+\|` | `=== Валидация входных параметров` |
| `error-codes` | `include::../CompositeException.adoc[]`, подпись `*Коды ошибок*` и таблица `Условие \| Описание \| Type \| Code` | `== Обработка ошибок` целиком |
| `job-table` | Пустая таблица для Job | `=== Входные параметры` метода без параметров |

Шаблоны приходят с готовым заголовком нужного уровня — менять его не надо. Строки-примеры заменяй на реальные, дефисы в незаполненных ячейках оставляй.

### Что всё-таки проверить глазами

- **Транспорт.** `http-method` и `thrift-method` не взаимозаменяемы, форма таблицы зависит от транспорта самого метода.
- **Заголовки `A-*`** переносятся без изменений; если в контракте метода их набор другой, это повод спросить, а не молча править стандартный блок.
- **`error-codes`** приносит `include::../CompositeException.adoc[]`. В папке метода этот файл лежит уровнем выше; если его там нет, появится диагностика о битом include — файл нужно создать, а не убирать include.

## 3. Артефакты — `artifact` и `requestArtifact`

Порядок ровно такой:

1. **Проверь блок `[Artifacts]`** в контексте. Если нужный уже есть — `artifact` с `op: "read"` и `id` из блока (`id` обязателен).
2. **Если нет** — `requestArtifact`. Обязательные аргументы: `kind: "httpRequest"`, `title` (обычно имя метода), `purpose` (одно-два предложения на языке пользователя: зачем нужен и какой раздел заполнит). Необязательный `prefill` — только то, что действительно известно (метод, путь, заголовки `A-*`); неверный `prefill` хуже пустой формы.
3. Вызывай `requestArtifact` отдельным ходом, ничего больше в этом раунде.
4. **«Заполню позже»** — продолжай с тем, что есть, и в конце перечисли, каких данных не хватает.

### Что возвращает артефакт и куда это класть

| Поле | Что это | Куда |
| --- | --- | --- |
| `inputParams` | Таблица входных параметров, 6 колонок, с готовым заголовком | `=== Входные параметры` как есть |
| `outputParams` | Таблица выходных параметров | `=== Выходные параметры` |
| `requestAdoc` | Целиком готовый `request.adoc` | В файл целиком |
| `responseAdoc` | Целиком готовый `response.adoc` | В файл целиком |
| `curl` | Блок `[source,bash]` | В пример запроса, если его там ещё нет |
| `responseExamples` | Блоки `[source,json]` по ответам | В пример ответа, если его там ещё нет |
| `errors` | Черновая таблица из двух колонок: `Код`, `Описание` | **Не вставлять как есть**: переложить в формат `errors.md`, дополнив Условием, Type и Code |

**Про `outputParams`**: пять колонок — ровно та же форма, что у шаблона `response-fields` и у скаффолда. Вставляй как есть.

## 4. Проверка — `check`

**Вызов**: `check` с `kind: "standards"` и `path` папки метода. Проверка взвешенная, порог — 80% на папку.

Что проверяется механически и что из этого следует при написании:

| Правило | Требование | Следствие |
| --- | --- | --- |
| K.1.1 / K.1.2 | Есть `{methodName}.adoc`, `request.adoc`, `response.adoc` и диаграмма (`{methodName}.puml` или `diagram.puml`), по одному файлу на роль | Не плоди вторые копии с другими именами |
| K.2.1 | В тексте есть строка `:toc:` или `toc::[]` | Проверка не смотрит, работает ли оглавление: шапка, отбитая от заголовка пустой строкой, её проходит, а оглавление при этом не рендерится. Следи за этим сам |
| K.2.2 | «Назначение» — минимум 50 непробельных символов | Две-четыре осмысленные фразы, не заглушка |
| K.3.1 | `.puml` непустой и упомянут в основном файле | Пустой блок-плейсхолдер эту проверку **не пройдёт** — это ожидаемо, так и скажи автору, диаграмму не выдумывай |
| K.4.1 / K.5.1 | Есть таблица от 4 колонок во входных / выходных | — |
| K.4.2 / K.5.2 | **Все** ячейки таких таблиц непустые | Дефис считается заполненной ячейкой, пустая — нет |
| K.4.3 / K.5.3 | Основной файл ссылается на `request.adoc` / `response.adoc` | Это и есть `include::` в примерах |
| K.4.4 | `request.adoc` непустой и содержит endpoint (`/path` или `${HOST}/path`) | Одной строки вида `POST /api/documents` над примером достаточно |
| K.5.4 | `response.adoc` непустой | — |
| K.6.1 | Раздел «Алгоритм работы» непустой | — |
| K.7.1 | Раздел «Обработка ошибок» непустой | Именно с этим заголовком: `== Коды ошибок` вместо него проверку не пройдёт |

**Чего `check` не делает**: не смотрит стиль и безличность, не проверяет корректность `type`/`code` и не сверяет таблицу ошибок с телом документа. Для этого — чек-листы скила и `references/errors.md`.

## Проблемные ситуации

### Шаблон тула расходится с этим скилом

Каталог и справочники держат синхронно, поэтому расхождение — признак того, что одно из двух устарело. Следуй справочнику, а расхождение назови пользователю: чинить надо каталог, а не документ.

### `check` показывает непройденное правило, которое исправить нечем

K.3.1 без исходника диаграммы и K.4.4 без известного эндпоинта — законные случаи. Не подделывай содержимое ради зелёной проверки: перечисли непройденные правила и скажи, каких данных не хватает.

### Тул недоступен или вернул ошибку

Не воспроизводи разметку по памяти. Скажи об ошибке пользователю и, если разметка нужна прямо сейчас, возьми образец из `assets/template.adoc`, пометив, что он может отставать от каталога приложения.
