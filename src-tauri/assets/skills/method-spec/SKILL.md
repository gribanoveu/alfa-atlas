# Постановка на ручку (AsciiDoc)

Скилл описывает весь путь от пустой папки до готовой постановки на REST/Thrift-метод в принятом внутреннем формате: структура документа, стиль формулировок, обязательные таблицы, работа с `include::`.

## Когда использовать

Используй этот скилл, когда пользователь:

- Просит «описать ручку», «сделать документацию на метод», «оформить постановку» или «расписать флоу».
- Просит добавить шаг, таблицу ошибок или раздел в существующую постановку.
- Упоминает `.adoc`, постановку, ТЗ на эндпоинт, интеграцию или доработку сервиса.
- Просит описать вызовы соседних систем (МКС, модуль подписи, ЭА, ОБИП, оператор ЭДО).

*Применяй скилл даже без слова «постановка», если речь идет про описание метода в вики/репозитории документации.*

## Главные правила стиля

### 🛑 Критичные правила (нарушение = переделывать)

1. **Никаких имён реализации.** В постановке не бывает Java-классов, бинов, сервисов уровня кода (`TaxSecretsServiceImpl`, `WebClient`), пакетов и приватных методов. Пишутся только внешние контракты: имя ручки, эндпоинт, имя сервиса-соседа (`customers-api#getByIdsV2`), коллекция БД (`TaxSecretsDocPack`) и её поля.
2. **Безличный императив.** «Вернуть исключение…», «Сформировать ответ…», «Остановить работу…», «Заполняется входным параметром…». Никаких «мы получаем», «сервис должен будет», «необходимо реализовать логику».
3. **Не выдумывать данные.** Если нет состава запроса/ответа — запросить артефакт, а не генерировать поля и коды ошибок из головы.

### ⚠️ Важные правила (нарушение = править)

1. **Принятый сленг.** УЛ, ЮЛ, СОПД, НТ, ЭА, МКС, ФНС, пакет документов, ручка, флоу, upin/xpin. Аббревиатуры не расшифровываются. Не изобретай синонимы (не пиши «комплект» вместо «пакет документов»).
2. **Ссылки между шагами.** Всегда по номеру, а не по имени ручки: «использовать значение из ответа, полученного на шаге 2».
3. **Разметка таблиц — из тулов.** Не перепечатывай её по памяти: `getAsciidocTemplates` отдаёт разделы постановки уже в нужном виде, менять в них надо только содержимое строк. Какой id за какой раздел отвечает — `references/tools.md`.

Примеры «хорошо / плохо» и словарь принятых терминов — `references/glossary.md`.

## Порядок работы

### Шаг 1: Собрать вводные

Что нужно знать: имя ручки, эндпоинт, метод, бизнес-логика, соседние системы, БД, что возвращает. Если чего-то нет — спроси точечно.

### Шаг 2: Определить тип задачи

- **Новая постановка** → создать папку тулом `createDirectory` (`template: "restEndpoint"`), заполнять с нуля.
- **Правка существующей** → сохранить нумерацию шагов, стиль, `include::`, добавить только запрошенное. Не переформатируй чужие разделы «по дороге».

### Шаг 3: Добыть недостающий контракт

Нет состава запроса/ответа — не выдумывай его: проверь блок `[Artifacts]` в контексте, иначе запроси артефакт. Точный порядок вызовов и раскладка полученного AsciiDoc по разделам — `references/tools.md`, раздел 3.

### Шаг 4: Заполнить документ

Заполняй `{methodName}.adoc` сверху вниз по каркасу ниже. Как заполняется каждый раздел — `references/structure.md`; всё, что касается ошибок, — `references/errors.md`; образец итогового документа — `assets/template.adoc`.

### Шаг 5: Проверить результат

Пройди по чек-листу в конце этого файла и вызови `check` (`kind: "standards"`) на папку метода. Что именно проверяется и какие непройденные правила законны — `references/tools.md`, раздел 4.

## Каркас документа

Порядок разделов фиксирован. Файлы уже созданы `createDirectory`. Для Thrift-метода заголовок начинается со слова `Thrift-метод`. Пустой строки между заголовком и атрибутами нет — она закрывает шапку и ломает оглавление (см. `references/structure.md`, раздел 1).

```asciidoc
= Rest-метод <имяРучки>
:sectnums:
:sectnumlevels: 3
:toc: left
:toclevels: 3
:toc-title: Оглавление

== Назначение
== Описание входных/выходных параметров
   === Входные параметры        (+ ==== Пример запроса → include::request.adoc[])
   === Выходные параметры       (+ ==== Пример ответа  → include::response.adoc[])
== Схема работы                 (plantuml + картинка)
== Алгоритм работы
   === Валидация входных параметров
   === Шаг 1. <название>
        ==== Входные параметры / ==== Выходные параметры
   === Шаг N. <название>
   === Формирование ответа
== Обработка ошибок             (include::../CompositeException.adoc[] + таблица кодов)
```

Шаг — это один поход в соседнюю систему или одно осмысленное действие. Из чего он состоит — `references/structure.md`, раздел 6.

## Справочные материалы (References)

Читаются тулом `skill` (`op: "read"`, `name: "method-spec"`, `path: "<путь ниже>"`):

- `references/structure.md` — подробный разбор каждого раздела документа: заголовок, назначение, таблицы параметров, валидация, шаги, формирование ответа, `include::`, шпаргалка по синтаксису таблиц. **Читать целиком перед новым документом.**
- `references/errors.md` — коды, типы, формулировки, раздел «Обработка ошибок». **Читать всегда, когда в документе есть хоть одна ошибка** (то есть практически всегда).
- `references/glossary.md` — словарь терминов и типовых формулировок. Сверяться, чтобы не изобретать синонимы.
- `references/tools.md` — вызовы тулов Atlas: `createDirectory`, шаблоны таблиц, артефакты, `check`. **Читать перед первой таблицей и перед проверкой.**
- `assets/template.adoc` — образец итоговой структуры документа целиком.

## Чек-лист перед выдачей

- [ ] В тексте нет имён классов, методов реализации и технологий (Spring, WebFlux, Mongo, Kafka).
- [ ] Все формулировки безличные, в инфинитиве; аббревиатуры не расшифрованы.
- [ ] У каждого входного параметра сказано, чем он заполняется; у каждого поля ответа — правило заполнения.
- [ ] Для каждого шага описано поведение при ошибке, и оно совпадает с итоговой таблицей кодов в разделе «Обработка ошибок».
- [ ] В таблицах от четырёх колонок нет ни одной пустой ячейки — вместо пустой стоит дефис.
- [ ] Разделы названы по каркасу: «Входные параметры», «Выходные параметры», «Валидация входных параметров» на третьем уровне, «Обработка ошибок» — на втором и последним.
- [ ] `include::` расставлены на все примеры, у каждого в конце стоят `[]` (`include::response.adoc[]`); пути к чужим сервисам ведут в `../_external/...`.
- [ ] В `request.adoc` есть строка с эндпоинтом (`POST /api/...`), сворачиваемая обёртка примера в `request.adoc` / `response.adoc` сохранена.
- [ ] Пройден `check` (`kind: "standards"`); оставшиеся непройденные правила названы пользователю, а не замазаны выдуманным содержимым.

Подробные чек-листы по структуре, ошибкам и языку — в конце соответствующих справочников.
