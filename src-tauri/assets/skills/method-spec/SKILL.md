# Постановка на ручку (AsciiDoc)

Скилл описывает весь путь от пустой папки до готовой постановки на REST/Thrift-метод в принятом внутреннем формате: структура документа, стиль формулировок, обязательные таблицы, работа с `include::`.

## Когда использовать

Используй этот скилл, когда пользователь:

- Просит «описать ручку», «сделать документацию на метод», «оформить постановку» или «расписать флоу».
- Просит добавить шаг, таблицу ошибок или раздел в существующую постановку.
- Упоминает `.adoc`, постановку, ТЗ на эндпоинт, интеграцию или доработку сервиса.
- Просит описать вызовы соседних систем (МКС, модуль подписи, ЭА, ОБИП, оператор ЭДО).

*Применяй скилл даже без слова «постановка», если речь идет про описание метода в вики/репозитории документации.*

## Главные правила стиля



### 🛑 Критичные правила (нарушение = переделывать)

1. **Никаких имён реализации.** В постановке не бывает Java-классов, бинов, сервисов уровня кода (`TaxSecretsServiceImpl`, `WebClient`), пакетов и приватных методов. Пишутся только внешние контракты: имя ручки, эндпоинт, имя сервиса-соседа (`customers-api#getByIdsV2`), коллекция БД (`TaxSecretsDocPack`) и её поля.
2. **Безличный императив.** «Вернуть исключение…», «Сформировать ответ…», «Остановить работу…», «Заполняется входным параметром…». Никаких «мы получаем», «сервис должен будет», «необходимо реализовать логику».
3. **Не выдумывать данные.** Если нет состава запроса/ответа — запросить артефакт, а не генерировать поля и коды ошибок из головы.



### ⚠️ Важные правила (нарушение = править)

1. **Принятый сленг.** УЛ, ЮЛ, СОПД, НТ, ЭА, МКС, ФНС, пакет документов, ручка, флоу, upin/xpin. Аббревиатуры не расшифровываются. Не изобретай синонимы (не пиши «комплект» вместо «пакет документов»).
2. **Ссылки между шагами.** Всегда по номеру, а не по имени ручки: «использовать значение из ответа, полученного на шаге 2».
3. **Таблицы из тула.** Не перепечатывай разметку таблиц по памяти, всегда получай её через `getAsciidocTemplates`.



### 💡 Примеры стиля

**Хорошо ✓**

> Для получения данных организации использовать сервис МКС `customers-api#getByIdsV2`.
> Вернуть исключение с кодом `CUSTOMER_NOT_FOUND` при отсутствии клиента.
> Заполняется значением `inn` из ответа, полученного на шаге 2.

**Плохо ✗**

> Мы получаем данные организации через сервис МКС.
> Сервис должен будет проверить наличие клиента и бросить исключение, если его нет.
> Используем значение inn, которое получили на предыдущем шаге.

## Порядок работы



### Шаг 1: Собрать вводные

Что нужно знать: имя ручки, эндпоинт, метод, бизнес-логика, соседние системы, БД, что возвращает. Если чего-то нет — спроси точечно.

### Шаг 2: Определить тип задачи

- **Новая постановка** → создать папку через `createDirectory`, заполнять с нуля.
- **Правка существующей** → сохранить нумерацию шагов, стиль, `include::`, добавить только запрошенное. Не переформатируй чужие разделы «по дороге».



### Шаг 3: Проверить наличие артефактов (если нет состава запроса/ответа)

1. Проверь блок `[Artifacts]` в контексте. Если есть — прочитай тулом `artifact` (`op: "read"`).
2. Если нет — вызови `requestArtifact` с `kind: "httpRequest"`, положив в `prefill` то, что известно (метод, путь, заголовки `A-*`).
3. В ответе придут `inputParams` → в `=== Входные параметры`, `outputParams` → в `=== Выходные параметры`, `requestAdoc`/`responseAdoc` → в соответствующие файлы.
4. Если пользователь ответил «Заполню позже» — продолжи без артефакта, но явно укажи в конце, каких данных не хватает.



### Шаг 4: Заполнить документ

Заполняй `{methodName}.adoc` сверху вниз, подтягивая таблицы через тулы и сверяясь с `assets/template.adoc` как с образцом.

### Шаг 5: Проверить результат

Пройди по чек-листу в конце этого файла и вызови `check` (`kind: "standards"`) на папку метода.

## Работа с инструментами Atlas



### 1. Создание папки

- **Тул**: `createDirectory` с `template: "restEndpoint"`.
- **Состав**: `{methodName}.adoc`, `request.adoc`, `response.adoc`, `{methodName}.puml`. Одна папка — один метод.
- **Важно**: Не создавай эти файлы вручную и не переименовывай их. Создание папки — отдельный вызов тула; этот скилл про то, как её **заполнить**.



### 2. Получение шаблонов таблиц

Настоящая форма таблицы зависит от транспорта. **Сначала выясни транспорт**.

- **REST-метод**: `getAsciidocTemplates` с id `"http-method"`. 6 колонок + стандартный блок заголовков (`A-userId`, `A-customerId`, `A-userIp`, `A-projectId`, `A-clientType`, `A-channelId`).
- **Thrift-метод**: `getAsciidocTemplates` с id `"thrift-method"`. 4 колонки (без «Тип параметра», без HTTP-заголовков) + обязательный конверт `userData` (`userData.id`, `userData.authorizedApplicationId`, `userData.ip`, `userData.customerId`). Остальные поля (например `organizationId`) добавляй отдельными строками под конвертом, ориентируясь на реальный контракт.
- **Другие таблицы**: `"validation-fields"`, `"response-fields"`, `"error-codes"`. Получай их одним вызовом `getAsciidocTemplates`.
- **Важно про** `request.adoc`**/**`response.adoc`: Таблицы внутри этих файлов (5 колонок, без «Тип параметра») — это родная разметка скаффолда для *примера*. Не переоформляй её под форму из каталога. Авторитетное описание параметров всегда живет в `{methodName}.adoc`.



### 3. Проверка результата

- **Тул**: `check` с `kind: "standards"` на папку метода.
- **Что делает**: Механическая проверка структурных правил (файлы на месте, оглавление, диаграмма, таблицы, разделы).
- **Чего не делает**: Не проверяет стиль, безличность и корректность `type`/`code`. Для этого используй чек-лист ниже.

## Каркас документа

Порядок разделов фиксирован. Файлы уже созданы `createDirectory`.

```asciidoc
= Rest-метод <имяРучки>  // или "Thrift-метод <имяРучки>"
:sectnums: 
:sectnumlevels: 3 
:toc: left 
:toclevels: 3 
:toc-title: Оглавление

== Назначение
== Описание входных/выходных параметров
   === Входные параметры        (+ ==== Пример запроса → include::request.adoc[])
   === Выходные параметры       (+ ==== Пример ответа  → include::response.adoc[])
== Схема работы                 (plantuml + картинка)
== Алгоритм работы
   === Валидация входных параметров
   === Шаг 1. <название>
        ==== Входные параметры / ==== Выходные параметры
   === Шаг N. <название>
   === Формирование ответа
== Обработка ошибок             (include::../CompositeException.adoc[] + таблица кодов)
```



## Как описывать шаг алгоритма

Шаг — это один поход в соседнюю систему или одно осмысленное действие.

1. Заголовок: Со ссылкой на документацию сервиса в git: === Шаг 1. Вызов link:ссылка[названиеМетода].
2. Проза: 1-2 строки о том, зачем этот шаг («Для получения данных организации необходимо использовать сервис МКС...»).
3. ==== Входные параметры: Таблица. В колонке «Описание» для каждого поля сказано, чем оно заполняется («Заполняется значением CORP-<ПРОЕКТ>», «Использовать значение fnsInfo.fnsId...»).
4. include::: Пример запроса из папки _external.
5. ==== Выходные параметры: Таблица только с теми полями, которые реально используются дальше (оговаривается фразой «Приведены только параметры, которые используются в методе…»).
6. include::: Пример ответа.
7. Завершающий абзац: Условие перехода на следующий шаг и поведение при ошибке (http-код, type, code, текст).



## Справочные материалы (References)

- references/structure.md — Подробное описание каждого раздела документа (как заполнять === Входные параметры, правила для шагов). Читать перед написанием нового документа целиком.
- references/errors.md — Правила по ошибкам, формату type/code, типовым формулировкам. Читать всегда, когда в документе появляется хоть одна ошибка.
- references/glossary.md — Словарь принятых терминов. Сверяться перед написанием, чтобы не изобретать синонимы.



## Проблемные ситуации

- Шаблон тула расходится с assets/template.adoc: Доверяй тулу (getAsciidocTemplates) — это поддерживаемый источник разметки в приложении, файл в скилле может отстать.
- Параллельные вызовы систем: Опиши каждый вызов как отдельный шаг. В таблице ошибок опиши, что происходит, если один из вызовов упал (например, откат транзакции или возврат специфичной ошибки).
- Пользователь не дает данных: Если пользователь отвечает «Заполню позже» на запрос артефакта — продолжи с тем что есть, но в самом конце документа явно оставь комментарий/секцию: // TODO: Отсутствуют данные о [список полей/ошибок].



## Чек-лист перед выдачей

- [ ] В тексте нет имён классов, методов реализации и технологий (Spring, WebFlux, Mongo, Kafka).
- [ ] Все формулировки безличные, в инфинитиве.
- [ ] Каждый входной параметр в таблице имеет строку «чем заполняется».
- [ ] Для каждого шага описано поведение при ошибке, и оно совпадает с итоговой таблицей кодов в разделе «Обработка ошибок».
- [ ] Валидация описана таблицей Параметр | Условие | Результат, каждое условие — отдельная строка (многострочные ячейки через .2+|, .3+|).
- [ ] У ответа описано правило заполнения каждого поля, а не только его тип.
- [ ] include:: расставлены на все примеры; пути к чужим сервисам ведут в ../_external/....
- [ ] в конце у строк с include стоят [] для корректной работы парсера asciidoc, например include::response.adoc[]
- [ ] Аббревиатуры не расшифрованы и не заменены на «понятные» аналоги.
- [ ] Сохранена сворачиваемая обёртка примера () в request.adoc / response.adoc.
- [ ] Пройден check (kind: "standards") по папке метода.
