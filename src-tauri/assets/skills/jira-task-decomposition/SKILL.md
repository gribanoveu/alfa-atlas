# Декомпозиция задач для Jira

## Зачем это нужно

Большую фичу легко превратить либо в один нечитаемый тикет, либо в набор технических подзадач без ценности.

Задача декомпозиции — найти такие срезы, которые можно:

- независимо понять;
- реализовать;
- проверить;
- показать пользователю или потребителю системы.

Хороший срез отвечает на вопрос:

```text
Что станет возможно после этой задачи?
```

Плохой срез отвечает на вопрос:

```text
Какой технический кусок работы нужно выполнить?
```

## Когда использовать

Используй этот скилл, если:

- пользователь просит декомпозировать, разбить, выделить этапы, нарезать фичу;
- пользователь описывает большую фичу, но не говорит, как её делить;
- в задаче несколько самостоятельных результатов;
- есть несколько ролей, экранов, объектов, состояний, интеграций или платформ;
- предварительных AC больше 7–8;
- невозможно сформулировать один целевой результат без «и»;
- нужно выбрать минимальный срез для первой итерации.

## Порядок работы

### 1. Собери контекст

Зафиксируй:

- цель фичи;
- потребителей: пользователь, администратор, клиент, соседний сервис, система;
- сценарии использования;
- объекты и сущности;
- роли и права;
- каналы: UI, API, мобильное приложение, уведомления;
- интеграции и ограничения;
- известные риски.

### 2. Сформулируй самостоятельные результаты

Выпиши результаты в формате:

```text
Пользователь может…
Клиент получает…
Сервис умеет…
Администратор видит…
```

Если результат содержит «и», проверь, можно ли его разбить.

### 3. Найди линии разреза

Попробуй разрезать фичу по:

- шагам пользовательского пути;
- ролям;
- объектам или сущностям;
- состояниям жизненного цикла;
- каналам или платформам;
- вариантам данных или бизнес-правил;
- интеграциям;
- уровню риска, нагрузке или безопасности;
- минимальному срезу и последующим расширениям.

### 4. Собери варианты декомпозиции

Дай 1–3 варианта нарезки.

Не надо сразу давать единственный жёсткий план. Лучше показать варианты и рекомендацию.

### 5. Проверь каждый срез

Проверь каждый срез по чек-листу качества ниже.

### 6. Выдай рекомендацию

После выбора среза передай его в `jira-task-description` или оформи как обычный тикет.

## Правила декомпозиции

### 1. Одна задача — один наблюдаемый результат

Каждый срез должен описываться одним предложением результата.

Хорошо:

```text
Пользователь может отметить фиксированный взнос как оплаченный из календаря.
```

Плохо:

```text
Пользователь может отметить взнос как оплаченный, изменить сумму и получить перерасчёт в виджете.
```

Если внутри есть несколько самостоятельных действий, это кандидаты на разные срезы.

---

### 2. Режь по ценности, а не по техническим слоям

Не надо автоматически делать отдельные задачи:

```text
Сделать БД.
Сделать API.
Сделать фронт.
Написать тесты.
Покрыть метриками.
```

Это шаги реализации, а не ценность.

Если технический срез необходим, формулируй его через проверяемый контракт или возможность:

```text
Клиент может вызывать метод change-payments по согласованному контракту.
```

или:

```text
Сервис умеет сохранять новую сумму оплаты и возвращать её в календарь.
```

---

### 3. Минимальный срез сначала

Первый срез должен решать основную боль минимальными средствами.

Например, для экспорта отчёта минимальный срез может быть таким:

```text
Пользователь может скачать CSV с начислениями сотрудника за текущий месяц и фиксированным набором полей.
```

А уже потом:

```text
Пользователь может выбрать период экспорта.
Пользователь может выбрать состав полей.
Большие отчёты выгружаются асинхронно.
```

---

### 4. Срез должен быть проверяемым

Для среза должны быть проверяемые критерии приёмки.

Проверяемо:

```text
Пользователь нажимает «Скачать CSV», браузер начинает загрузку файла.
```

Непроверяемо:

```text
Экспорт работает корректно.
```

Если срез нельзя проверить без других срезов, его надо переформулировать или объединить с зависимой частью.

---

### 5. Зависимости должны быть явными

Если срез требует другой срез, это надо писать явно.

Например:

```text
Зависит от готовности контракта change-payments.
Требует добавления роли «Бухгалтер».
Работает только после миграции данных по платежам.
```

Если зависимости скрытые, декомпозиция плохая.

---

### 6. Размер среза должен быть управляемым

Признаки слишком большого среза:

- больше 7–8 AC;
- несколько независимых сценариев;
- несколько команд или сервисов;
- невозможно объяснить срез одной фразой;
- для проверки нужно много подготовки;
- внутри есть части, которые можно выложить отдельно.

Но не надо дробить до бессмысленных микрозадач. Если несколько действий относятся к одному пользовательскому сценарию и не создают отдельной ценности, их можно оставить в одном срезе.

---

### 7. Не дробить ради дробления

Плохая декомпозиция:

- отдельная задача на каждое поле формы;
- отдельная задача на каждый код ошибки;
- отдельная задача на кнопку;
- отдельная задача на unit-тесты, если это не самостоятельный продукт;
- отдельная задача на документацию, если она является частью общей поставки;
- отдельная задача под каждого разработчика.

Хорошая декомпозиция выделяет самостоятельные результаты.

## Линии разреза

### По шагам пользовательского пути

Пример:

```text
1. Пользователь может создать черновик отчёта.
2. Пользователь может отправить отчёт на согласование.
3. Пользователь может увидеть статус согласования.
```

---

### По ролям

Пример:

```text
1. Руководитель может отметить взнос как оплаченный.
2. Бухгалтер может изменить сумму оплаты.
```

Но если роли отличаются только правом доступа, а поведение одинаковое, лучше не делить на разные задачи. Тогда достаточно одной задачи с AC на проверку прав.

---

### По объектам или сущностям

Пример:

```text
1. Пользователь может управлять фиксированными взносами.
2. Пользователь может управлять переменными начислениями.
```

---

### По состояниям жизненного цикла

Пример:

```text
1. Задачу можно перевести в статус «Черновик».
2. Задачу можно отправить на проверку.
3. Задачу можно опубликовать.
```

---

### По каналам или платформам

Пример:

```text
1. Пользователь может выполнить действие в web.
2. Пользователь может выполнить действие в мобильном приложении.
```

Дели так, только если канал имеет самостоятельную ценность или отдельный процесс поставки.

---

### По вариантам данных или бизнес-правил

Пример:

```text
1. Экспорт с базовым набором полей.
2. Экспорт с расширенным набором полей.
```

---

### По интеграциям

Пример:

```text
1. Локальное сохранение изменения оплаты.
2. Отправка изменения во внешний сервис платежей.
```

Но если без интеграции функция не имеет смысла, не создавай видимость ценности.

---

## Формат ответа

Если пользователь просит декомпозицию, не начинай сразу оформлять один большой тикет. Сначала выдай варианты.

Используй такой шаблон:

```markdown
### Контекст

Коротко опиши, как ты понял фичу и её цель.

### Рекомендуемый вариант декомпозиции

Коротко: почему выбран такой вариант.

---

### Срез 1. Название

**Результат:**  
Пользователь может ...

**Что входит:**
- ...
- ...

**Что не входит:**
- ...
- ...

**Черновые AC:**
1. ...
2. ...
3. ...

**Зависимости:**
- ...

**Что откладываем на следующие срезы:**
- ...
```

Если вариантов несколько, дай 2–3 варианта и рекомендацию.

---

## Чек-лист качества среза

Перед тем как отдавать срез пользователю, проверь:

- Есть ли у среза один результат?
- Есть ли у результата потребитель?
- Можно ли проверить результат без остальных срезов?
- Есть ли у среза самостоятельная ценность или проверяемый контракт?
- Не является ли срез просто техническим слоем?
- Нет ли скрытых зависимостей?
- Можно ли написать 3–8 проверяемых AC?
- Не слишком ли мелко нарезано?
- Не дублируются ли одинаковые требования в нескольких срезах?

---

## Анти-паттерны

Не делай так:

```text
Сделать таблицу.
Сделать API.
Переделать фронт.
Добавить ошибки.
Написать тесты.
Обновить конфиги.
```

без наблюдаемого результата.

Лучше:

```text
Сервис умеет сохранять отметку об оплате и возвращать обновлённый статус.
Клиент может получить список оплаченных взносов за период.
Пользователь видит ошибку валидации при попытке указать отрицательную сумму.
```

## Пример декомпозиции

### Фича

> Нужен экспорт отчёта по начислениям в CSV из карточки сотрудника.

### Плохая декомпозиция

```text
1. Добавить кнопку экспорта.
2. Сделать сервис генерации файла.
3. Настроить таблицу.
4. Обработать ошибки.
5. Написать тесты.
```

Это план работ, а не ценность.

### Хорошая декомпозиция

#### Срез 1. Базовая выгрузка начислений

**Результат:**  
Пользователь может скачать CSV с начислениями сотрудника за текущий месяц.

**Что входит:**

- кнопка экспорта в карточке сотрудника;
- выгрузка фиксированного набора полей;
- формирование файла за текущий месяц;
- обработка пустого результата;
- уведомление об ошибке генерации.

**Что не входит:**

- выбор периода;
- настройка состава полей;
- асинхронная выгрузка больших файлов.

**Черновые AC:**

1. Пользователь может нажать «Экспорт в CSV» в карточке сотрудника.
2. Браузер начинает загрузку CSV-файла.
3. Файл содержит обязательные поля: ФИО, период, вид начисления, сумму, статус.
4. Если начислений нет, пользователь видит сообщение, что данных для экспорта нет.
5. При ошибке генерации файла пользователь видит уведомление об ошибке.

**Зависимости:**

- Нет.

---

#### Срез 2. Выбор периода выгрузки

**Результат:**  
Пользователь может выбрать месяц или период и скачать отчёт за выбранный период.

**Что входит:**

- выбор периода;
- валидация периода;
- генерация файла за выбранный период.

**Что не входит:**

- настройка состава полей;
- асинхронная выгрузка.

**Черновые AC:**

1. Пользователь может выбрать период выгрузки.
2. Система не позволяет выбрать будущий период.
3. Файл содержит начисления только за выбранный период.
4. При ошибке генерации пользователь видит уведомление об ошибке.

**Зависимости:**

- Требует готовый базовый экспорт.

---

#### Срез 3. Асинхронная выгрузка больших отчётов

**Результат:**  
Пользователь получает уведомление, когда большой отчёт готов к скачиванию.

**Что входит:**

- асинхронная генерация файла;
- статус готовности;
- ссылка на скачивание готового файла;
- уведомление пользователя.

**Что не входит:**

- настройка состава полей;
- экспорт в другие форматы.

**Черновые AC:**

1. Пользователь может запустить экспорт большого отчёта.
2. Система показывает, что отчёт формируется.
3. После готовности пользователь получает уведомление со ссылкой на скачивание.
4. Если файл не сформировался, пользователь видит уведомление об ошибке.

**Зависимости:**

- Требует готовый базовый экспорт.
