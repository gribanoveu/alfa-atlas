# Метрики

Продуктовые метрики Alfa Atlas: куда и что отправляется, как добавить событие,
что осознанно не сделано.

Отправлены: установка, запуск приложения, открытие проекта, конец сессии — первая
волна плана. Всё остальное ниже описывает каркас, на который следующие события
кладутся без переделок.

---

## 1. Почему свой транспорт, а не `sp.js`

Формат событий взят из `alfa-metrics-kit` (репозиторий `corp-wlbuh-ausn-ndfl-ui`,
сам по себе порт `@alfa-bank/common-app-html`). Транспорт — нет.

Kit работает так: вставляет в страницу `<script src="https://metrics.alfabank.ru/metrica/sp.js">`
и складывает команды в очередь `window.sp.q`. Отправка, куки и ретраи живут внутри
удалённого `sp.js`. В Tauri это ломается в трёх местах:

1. **`discoverRootDomain: true`** рассчитан на реальный домен `*.alfabank.ru` — трекер
   идёт вверх по домену документа, чтобы поставить максимально широкую first-party
   куку. В вебвью origin `tauri://localhost`, регистрируемого домена нет.
2. **События теряются молча.** `track.ts` при отсутствии `window.sp` делает ранний
   `return` — ни очереди, ни ошибки. Для десктопа, который регулярно вне
   корпоративной сети, это потеря почти всех событий, причём незаметная.
3. **`initSnowplowClient` не ждёт загрузки** `sp.js` — возвращает `Promise.resolve()`
   сразу, без таймаута и без признака ошибки.

Поэтому payload собирается и отправляется у нас: `infra/snowplow_client.rs`. Плюс
в том, что отправка теперь либо подтверждается, либо честно падает — на этом
построена гарантия «ровно один раз» (см. §5).

**Это решение не стоит пересматривать без нового аргумента** — все три пункта
выше остаются верными для любой версии kit.

### Что взято из kit, а что нет

| Из kit | Судьба |
|---|---|
| `types.ts` (`Metric`, `AdditionalMetricData`) | вендорено в `src/lib/metrics/types.ts` |
| `map-dimensions.ts` | вендорено в `src/lib/metrics/mapDimensions.ts` (значения приводятся к строке) |
| `constants.ts` — iglu-схемы, слоты, домены | значения перенесены в `src/lib/metrics/constants.ts` и `src-tauri/src/domain/metrics.rs` |
| `metrics-catalog.example.ts` | образец для `src/data/metricsCatalog.ts` |
| `snowplow-script.ts`, `snowplow-client-init.ts`, `is-browser.ts`, `track.ts` | **не переносится** — это транспорт через `sp.js` |
| `ssr-page.example.ts`, `use-alfa-metrics.hook.example.ts` | не нужны: нет SSR, нет Redux |

## 2. Контракт события

Событие — Snowplow **struct event** с одним контекстом кастомных размерностей.

```
category  se_ca   "ALFA-ATLAS > App"
action    se_ac   "Install -> First launch"
label     se_la   "App installed"
property  se_pr   опционально
value     se_va   опционально
```

Размерности едут в контексте схемы
`iglu:com.alfabank/custom_dimension/jsonschema/1-0-0` как карта «номер слота →
значение». Каталог метрик оперирует именами (`installId`), а не номерами;
превращение `{installId: 'abc'} + {installId: '2'}` → `{'2': 'abc'}` делает
`mapDimensions` на фронте, поэтому Rust не знает имён полей конкретных событий.

### Реестр слотов

**Слот, однажды занятый, нельзя переиспользовать под другой смысл** — иначе все
исторические запросы по нему становятся неверными задним числом.

| Слот | Значение | Где объявлен |
|---|---|---|
| `1` | `organizationId` — **зарезервирован** во всех корп-приложениях Alfa Metrics. В десктопе организации нет, слот всегда пуст | `ORGANIZATION_DIMENSION_SLOT` |
| `2` | `installId` — анонимный id установки | `DIMENSION_SLOT.installId` |
| `3` | `appVersion` — версия приложения | `DIMENSION_SLOT.appVersion` |
| `4` | `os` — семейство ОС: `macos`, `windows`, `linux` | `DIMENSION_SLOT.os` |
| `5` | `sessionId` — один запуск приложения | `SLOT_SESSION_ID` |
| `6` | `providerId` — провайдер модели, только системный | `SLOT_PROVIDER` |
| `7`–`20` | свободны | |

Слоты `2`–`5` **проставляются автоматически** в `services::metrics` на каждое
событие — вызывающему коду их указывать не нужно и нельзя: попытка занять базовый
слот из каталога перетирается настоящим значением. Это сквозные признаки, по которым
режутся все категории сразу; всё, что специфично для одного события, идёт в
`label` / `property` / `value` и слотов не тратит.

Слот `5` — случайный идентификатор на один запуск, он никогда не пишется на диск.
Поверх id установки он не сообщает ничего нового, но позволяет собирать события
одного запуска в воронку. Без него события остаются несвязанными точками.

Слот `6` **никогда не несёт имя пользовательского провайдера.** Id системного
провайдера берётся из манифеста; всё остальное превращается в `custom`. Проверка
живёт в `services::metrics::sanitize_dimensions`, то есть на границе, а не в местах
вызова: провайдера настраивает пользователь, и его id — свободный текст, в котором
встречаются внутренние хосты и имена людей. Ни один вызывающий код — ни нынешний, ни
будущий — не может это забыть.

Слот `4` называется `os`, а не `platform`: поле `p` самого протокола Snowplow уже
значит «платформа» и во всех событиях равно `web`. Значение берётся из
`std::env::consts::OS` как есть — только семейство ОС, без версии, номера сборки и
архитектуры: для вопроса «на каких платформах этим пользуются» они не нужны, а
каждое такое поле сужает круг, в котором пользователь неразличим.

Реестр продублирован в трёх местах и должен меняться синхронно:
`src/lib/metrics/constants.ts`, `src-tauri/src/domain/metrics.rs` и эта таблица.
Заполнение слота `1` ловится `debug_assert!` в `build_payload`.

## 3. Как добавить событие

1. **Завести запись в каталоге** — `src/data/metricsCatalog.ts`. Категория:
   `ALFA-ATLAS > <Область>`. Действие: `Click -> "<Название>"`, `Show -> <Что>`,
   `Install -> <Что>` — глагол, стрелка, объект.
2. **Занять слоты**, если событию нужны свои размерности: добавить в
   `DIMENSION_SLOT`, в константы Rust и в таблицу §2. Взять следующий свободный
   номер, не переиспользовать.
3. **Проверить событие на соответствие обещанию в настройках.** Текст тумблера
   намеренно написан общо и обещает не за одно событие, а за все — значит каждое
   новое событие обязано ему соответствовать, иначе обещание тихо станет ложным.
   Ни в `label`, ни в `property`, ни в размерностях не должно оказаться:
   - имени пользователя, почты, имени хоста, логина;
   - путей к файлам и имён файлов;
   - названий и адресов репозиториев, имён веток;
   - содержимого документов, запросов и ответов ассистента.

   Если нужен признак «какой это файл» — отправляйте расширение или тип, а не путь.
   Если нужна «величина» — отправляйте число или интервал, а не исходный текст.
4. **Вызвать** из хука или `lib/`-обёртки:
   ```ts
   void trackMetric(METRICS.MY_AREA.MY_EVENT, { myField: "value" });
   ```
   `trackMetric` никогда не реджектится — метрика не должна ломать то, что
   пользователь на самом деле просил. Компоненты его не зовут напрямую: как и
   везде в проекте, обращение идёт через хук или `lib/` (см. `AGENTS.md`).
5. **Описать бизнес-смысл** в §4, «Что каждое событие значит бизнесово»: на какой
   вопрос событие отвечает и какое решение должно менять. Если ответа нет — событие
   заводить не нужно, оно будет только шумом в витрине.
6. **Обновить §6**, если состав отправляемого меняется качественно (появляется
   новый вид данных, а не ещё одно событие того же рода).

Событие установки — исключение: оно собирается в Rust
(`services::metrics::report_install_once`), потому что должно уметь сработать до
появления вебвью и пережить перезапуск. Запись в каталоге для него всё равно есть
и остаётся источником правды о его форме.

## 4. Куда и что уходит

| | |
|---|---|
| Эндпоинт | `https://testjmb.alfabank.ru/metrica/corp/com.snowplowanalytics.snowplow/tp2` |
| `appId` | release-сборка — `alfa-atlas-ui`; debug-сборка — `alfa-atlas-ui_dev` |
| Метод | POST, `Content-Type: application/json; charset=UTF-8` |
| Конверт | `iglu:com.snowplowanalytics.snowplow/payload_data/jsonschema/1-0-4` |
| Успех | только 2xx |

**Коллектор один на все сборки.** `metrics.alfabank.ru` намеренно не используется.
Release и debug различаются исключительно по `appId`, по нему же в витрине
отфильтровывается трафик разработки.

Всё это не захардкожено, а живёт в `assets/llm/system_providers.yaml` в секции
`metrics:` — там же, где пресеты LLM и embedding:

```yaml
metrics:
  appId: alfa-atlas-ui          # release-сборка
  devAppId: alfa-atlas-ui_dev   # debug-сборка
  domain: testjmb.alfabank.ru
  metricsType: corp
  platform: web
  trustedCertPem: |
    -----BEGIN CERTIFICATE-----
    …
```

Форк меняет или отключает метрики правкой этого файла, не трогая ни одного `.rs`.
**Удалить секцию целиком — валидный вариант:** тогда `metrics_preset()` вернёт
`None`, и сборка не отправляет ничего вообще.

`appId` выбирается по `cfg!(debug_assertions)`, поэтому `tauri dev` не может
выдать себя за реальное использование.

Все поля payload — строки: протокол в GET-форме form-encoded, POST-форма сохраняет
ту же строковую типизацию, и числовой `se_va` отвергается на приёме. Это
зафиксировано тестом `every_payload_field_is_a_string`.

`duid` (domain user id), а не `uid`: id установки идентифицирует профиль на машине,
а не человека, и класть его в `uid` значило бы заявить личность, которой у
приложения нет.

### Что отправляется сейчас

| Событие | `label` | `property` | `value` |
|---|---|---|---|
| `Install -> First launch` | `App installed` | — | — |
| `Start -> App` | `App started` | — | — |
| `Open -> Project` | `git` или `plain` | `restore`, `recent`, `dialog`, `clone` | — |
| `End -> Session` | `Session ended` | всего секунд от запуска до выхода | **активных** секунд |

Ассистент (категория `ALFA-ATLAS > Assistant`, все события несут слот `6`):

| Событие | `label` | `property` | `value` |
|---|---|---|---|
| `Settle -> Turn` | `done`, `cancelled`, `error` | режим доступа: `docsOnly` / `fullRepo` | длительность хода, секунды |
| `Fail -> Turn` | класс ошибки | — | — |
| `Decide -> Tool calls` | `approved`, `denied`, `mixed` | — | вызовов в раунде |
| `Run -> Tool` | `ok` или `error` | имя инструмента | сколько таких вызовов за ход |
| `Compact -> Context` | `auto` или `retry` | — | сколько сообщений свёрнуто |
| `Switch -> Access mode` | `user`, `assistant-granted`, `assistant-denied` | `docsOnly` / `fullRepo` | — |
| `Switch -> Conversation mode` | то же | `agent` / `plan` / `question` | — |

#### Переключение режимов: кто инициировал и что ответил пользователь

Режим меняется двумя способами, и это **разные факты о доверии**, которые нельзя
складывать в один счётчик:

- **`user`** — человек сам переключил тумблер или селектор в панели ассистента.
  Снимается на самих контролах, а не в обработчике смены режима: через тот же
  обработчик применяется и одобренный запрос ассистента.
- **`assistant-granted` / `assistant-denied`** — ассистент попросил
  (`requestFullRepoAccess`, `requestModeSwitch`), и пользователь согласился или
  отказал.

Отказ снимается там же, где принимается решение по одобрению вызовов, — это
единственное место, которое знает и что просили, и что ответили. Если считать
только применённые переключения, **каждый отказ потерялся бы бесследно**, а именно
отказы и отвечают на вопрос, доверяют ли ассистенту доступ ко всему репозиторию.

Классы ошибок — закрытый список: `rateLimit`, `contextLength`, `auth`, `network`,
`cancelled`, `provider`, `unknown` (`src/lib/metrics/classifyLlmError.ts`).
**Текст ошибки провайдера не отправляется никогда** — он свободной формы и может
содержать кусок промпта или внутренний URL.

#### Почему `Settle -> Turn` дублирует `Fail -> Turn`

`Settle -> Turn` отправляется на **каждый** завершившийся ход, включая упавший.
Поэтому доля успешных ходов — это просто счёт по `label`, без джойнов. `Fail -> Turn`
добавляет разбивку по причине и живёт отдельно, чтобы воронка оставалась «одно
событие на ход». Дублирование намеренное.

#### Почему вызовы инструментов агрегируются

Один ход ассистента может сделать десятки вызовов. Событие на каждый переполняло бы
очередь доставки: при ретеншене в 1000 событий шумный офлайновый день вытеснил бы
оттуда как раз редкие и ценные события — сессии и ходы. Поэтому вызовы сворачиваются
до одного события на **ход × инструмент × исход** со счётчиком в `value`: ход с
тридцатью `readFile` стоит одного события, а разбивка по инструментам сохраняется
полностью.

Это лучше выборки, которую предполагал исходный план: не нужен масштабирующий
коэффициент и не теряется точность агрегата.

#### Сессия считается по фокусу, а не по времени работы процесса

`value` — это время, которое окно **реально было в фокусе**, а не время жизни
процесса. Инструмент для документации люди держат открытым весь день: время «от
запуска до выхода» отрапортовало бы восьмичасовую сессию для приложения, которое всё
это время простояло за браузером. Активное время накапливается по всем циклам
фокус/расфокус (`WindowEvent::Focused`).

Полное время от запуска до выхода едет рядом, в `property` — их отношение само по
себе отвечает на вопрос «приложением пользуются или оно просто открыто».

Обе величины — целые секунды, не минуты: заметная доля десктопных сессий короткая, и
округление до минуты стёрло бы разницу между «открыл и сразу закрыл» и «поработал».

### Что каждое событие значит бизнесово

Таблицы выше говорят, что лежит в полях. Здесь — зачем событие вообще существует и
какое решение оно должно менять. Событие, которое не отвечает ни на один вопрос из
этого списка, заводить не нужно.

**`Install -> First launch`** — сколько людей вообще поставили приложение. Единственная
метрика, отвечающая на «дошло ли до людей»: раздали ли, поставили ли, на чём. Не
говорит ничего о том, пользуются ли им — для этого есть всё остальное.

**`Start -> App`** — знаменатель для всех остальных метрик. Даёт активных
пользователей за день и за неделю и, в паре с id установки, долю вернувшихся после
установки. Без него любая цифра повисает в воздухе: пятьдесят вызовов ассистента за
неделю — это много или мало, если неизвестно, пятеро это сделали или пятьдесят.

**`Open -> Project`** — приложение открыли или им работают. `label` (`git` / `plain`)
показывает, используют ли его по назначению — с репозиторием документации, а не как
блокнот. `property` отвечает, какой путь входа реально нужен: если почти всё
приходит через `restore`, экраны выбора проекта можно упрощать; если через
`clone` — клонирование стоит вкладывать.

**`End -> Session`** — работают или держат открытым. Ключевое здесь `value`: активные
секунды, время в фокусе. Отношение активного времени к полному (`property`) —
самостоятельный показатель: приложение, открытое восемь часов при десяти минутах в
фокусе, это не восьмичасовая сессия, а фоновая вкладка. Короткие сессии в секундах —
сигнал «открыл и не нашёл, что искал».

**`Settle -> Turn`** — доводит ли ассистент задачи до конца. Доля `done` против
`cancelled` и `error` — главный показатель здоровья главной функции продукта. `value`
даёт распределение длительности хода: если оно ползёт вверх, растёт и вероятность,
что человек не дождётся. `property` (режим доступа) показывает, в каком режиме
ассистентом реально пользуются.

**`Fail -> Turn`** — на что тратить инженерное время. Разбивка по причине отвечает,
что чинить: `rateLimit` — вопрос к квотам провайдера, `contextLength` — к стратегии
сжатия истории, `auth` и `network` — к инфраструктуре и инструкции по настройке,
`provider` — к самому эндпоинту. Без разбивки «ассистент падает» — это жалоба, а не
задача.

**`Decide -> Tool calls`** — доверяют ли ассистенту действовать. Доля `denied` и
`mixed` показывает, где подтверждения работают как защита, а где как раздражитель.
Если раунды почти всегда одобряются целиком, часть подтверждений можно снимать; если
часто отклоняются — проблема в том, что ассистент предлагает не то.

**`Run -> Tool`** — какие инструменты окупают своё существование и какие ломаются.
`property` × `value` даёт частоту по инструментам: редкий инструмент — кандидат на
удаление, частый — на вложение. `label: error` по конкретному инструменту — прямой
список того, что чинить, отранжированный по тому, как часто по этому спотыкаются.

**`Compact -> Context`** — упирается ли продукт в окно контекста. Частое `auto`
означает, что люди ведут длинные диалоги и качество ответов деградирует незаметно
для них; частое `retry` — что они уже столкнулись с ошибкой и нажали «сжать и
повторить». Второе — прямой аргумент за больший контекст или за агрессивнее сжатие.

**`Switch -> Access mode`** — доверяют ли ассистенту весь репозиторий. Разделение
`user` / `assistant-granted` / `assistant-denied` — здесь весь смысл события: если
пользователи сами включают полный доступ, ограничение мешает; если ассистент просит
и ему регулярно отказывают, он просит не по делу; если просит и всегда получает —
подтверждение можно смягчить.

**`Switch -> Conversation mode`** — нужны ли режимы вообще. Если распределение
уходит в один режим, остальные — лишняя сложность в интерфейсе. Запросы от
ассистента отдельно показывают, умеет ли он сам понимать, что задача сменила
характер.

### TLS: сертификат едет в манифесте

Коллектор подписан цепочкой **Russian Trusted Root CA** (Минцифры), а не внутренним
CA Альфы:

```
0  CN=testjmb.alfabank.ru
1  CN=Russian Trusted Sub CA
2  CN=Russian Trusted Root CA   ← самоподписанный корень
```

Этого корня нет в бандле Mozilla, на который `ureq` опирается по умолчанию, поэтому
неподготовленный агент падает с `invalid peer certificate: UnknownIssuer` — при том
что `curl` до того же адреса проходит, потому что берёт корни из системного
хранилища.

Корень зашит в `assets/llm/system_providers.yaml` → `metrics.trustedCertPem`, ровно
как у AlfaGen и embedding-провайдера. Это лучше, чем полагаться на системное
хранилище: работает одинаково на машине, где корень Минцифры никто не устанавливал
(типично для Windows и Linux), и не тянет лишних зависимостей.

`build_agent(Some(pem))` **заменяет** хранилище доверия целиком, а не дополняет
его — то есть запросы метрик доверяют только этому корню и ничему больше.

Сертификат забирается из хендшейка самого эндпоинта:

```bash
openssl s_client -connect testjmb.alfabank.ru:443 -servername testjmb.alfabank.ru -showcerts
```

Нужен сертификат с индексом 2. Срок действия текущего — до 2032-02-27, отпечаток
SHA-256 `D2:6D:…:CF:31` (полностью — в комментарии манифеста). Тест
`bundled_manifest_metrics_trust_cert_is_present_and_parses` прогоняет PEM через
`build_agent`, так что порча при редактировании валит сборку, а не уезжает в релиз.

## 5. Доставка: очередь и «ровно один раз»

Событий больше одного за сессию, поэтому есть **очередь на диске** —
`~/.atlas/metrics_queue.db`, по образцу `infra/tool_call_log.rs`. Без неё всё, что
случилось вне корпоративной сети, терялось бы безвозвратно, причём потери были бы
смещены ровно в сторону тех, кто работает не из офиса.

Как это устроено:

- `track()` кладёт событие в очередь и **сразу возвращает успех** — событие уже на
  диске. Затем оппортунистически пробует слить очередь; неудача слива не считается
  ошибкой трекинга, в этом и смысл очереди.
- Слив отправляет до 50 самых старых событий **одним** запросом (конверт
  `payload_data` принимает массив) и повторяет, пока очередь не опустеет. Строки
  удаляются только после 2xx.
- Цикл «до пустой очереди» — не оптимизация, а необходимость. Слив, который не смог
  взять лок, пропускается, а держащий лок мог забрать свою пачку **до** того, как
  событие поставили в очередь. Без цикла последнее событие каждой сессии зависало до
  следующего запуска.
- `stm` (время отправки) проставляется в момент слива, а не постановки в очередь:
  событие может пролежать сутки, и разрыв между `dtm` и `stm` — это то, чем
  коллектор корректирует задержку.
- Ретеншен: 14 дней и не более 1000 событий, лишнее отбрасывается старейшим вперёд.
  Иначе постоянно офлайновая установка растила бы файл без предела.
- Битая строка выбрасывается, а не блокирует очередь за собой навсегда.
- Одновременные сливы разведены мьютексом: два параллельных слива не должны
  отправить и удалить одни и те же строки дважды.

### Почему установка идёт мимо очереди

Событие установки отправляется **напрямую**, а не через очередь. Гарантия «ровно
один раз» держится на том, что `installReportedAt` пишется только после
подтверждённой доставки, а постановка в очередь не подтверждает ничего.

Состояние — `~/.atlas/metrics.json`:

```json
{ "installId": "…uuid v4…", "installReportedAt": 1756400000000, "enabled": true }
```

Отсюда всё остальное поведение: запуск вне VPN → отправка падает → флаг не
проставлен → следующий запуск повторит попытку. `installId` при этом уже сохранён,
поэтому повтор отправит **ту же** установку, а не выдумает вторую. После успеха
повторный вызов — no-op.

Оговорка: «один раз» — это один раз **на профиль `~/.atlas`**. Переустановка
системы, новая машина или удаление `~/.atlas` дадут новый id и новое событие. Это
ограничение любого клиентского install-id, обойти его нечем.

### Конец сессии

Пишется в очередь **синхронно и без попытки отправки**: процесс вот-вот исчезнет, и
сетевой запрос либо задержал бы выход, либо оборвался бы на половине. Вставка в
SQLite занимает миллисекунды и не теряется — вынесет слив на следующем запуске.

Путей выхода несколько (закрытие окна, команда выхода, на macOS оба), поэтому
длительность сессии выдаётся ровно один раз — иначе счётчик сессий раздувался бы, а
средняя длительность делилась пополам.

Часы активности идут на `Instant`, а не на настенном времени: перевод часов или
засыпание машины не должны давать отрицательную или абсурдную длительность.

## 6. Приватность

Приложение уже даёт пользователю явное обещание в настройках (Логирование:
содержимое документов не сохраняется). Метрики ему соответствуют.

**Не отправляется — и не должно отправляться впредь:** имя пользователя, почта (в
том числе из `git config`), имя хоста, пути к файлам и имена файлов, названия и
адреса репозиториев, имена веток, содержимое документов, переписка с ассистентом.
Это не описание текущего состояния, а ограничение на любое будущее событие — см.
чек-лист в §3.

**Отправляется:** обезличенные факты о действиях в интерфейсе и о сборке. На
сегодня это одно событие установки со слотами из §2 (id установки, версия, ОС);
список слотов и есть исчерпывающий ответ на вопрос «что именно уходит».

`installId` — чистый случайный UUID v4, он ни из чего не выводится и не связан ни с
машиной, ни с пользователем.

**Управление:** Настройки → Логирование → «Продуктовые метрики». По умолчанию
включено. Файл `~/.atlas/metrics.json` лежит в открытом виде, его можно удалить —
тогда сгенерируется новый id.

При выключенном тумблере не отправляется ничего и `installReportedAt` не
проставляется.

## 9. Открытые вопросы

- **`appId` не зарегистрирован в Alfa Metrics.** Коллектор отвечает 200 в любом
  случае, но без регистрации события не появятся в витрине. Нужна заявка на
  `alfa-atlas-ui` и `alfa-atlas-ui_dev`.
- **Проход enrich не проверен.** 200 от коллектора подтверждает приём, но не то,
  что enrich примет контекст схемы `custom_dimension/1-0-0`. Проверяется только по
  факту появления событий в витрине по `aid`.
- **Живая отправка проверялась только на macOS** и только в тестовый коллектор.
  Корень доверия едет в манифесте, а не берётся из системного хранилища, поэтому
  платформенных различий быть не должно — но подтверждено это не было.
- **Дефолт тумблера.** Сейчас включено по умолчанию (иначе метрика установки
  бессмысленна). Решение продуктовое, стоит подтвердить до релиза.

## Как проверить

```bash
cargo test --lib -- metrics snowplow_client
```

```bash
bun test src/__tests__/metrics.test.ts
```

Живые проверки против настоящего коллектора — требуют корпоративной сети, поэтому
отключены по умолчанию:

```bash
cargo test --lib -- --ignored --nocapture live_
```

`live_collector` — форма события установки, `live_flush` — слив реальной очереди,
`live_assistant` — по одному событию каждой формы второй волны, включая проверку, что
пользовательский провайдер приезжает как `custom`.

Сквозная проверка: удалить `~/.atlas/metrics.json`, запустить приложение — файл
появится с `installId` и непустым `installReportedAt`. Перезапустить — значение
`installReportedAt` не должно измениться. Сам запрос в devtools вебвью не виден:
он уходит из Rust, а не из страницы.

Проверка деградации: отключить сеть, удалить `metrics.json`, запустить —
приложение стартует как обычно, `installReportedAt` остаётся `null`, а события
копятся в `metrics_queue.db`:

```bash
sqlite3 ~/.atlas/metrics_queue.db 'SELECT COUNT(*) FROM pending_events;'
```

Вернуть сеть и перезапустить — счётчик должен обнулиться, а события появиться в
витрине.

### Ручная отправка тестового события

Событие `ALFA-ATLAS > Debug / Probe -> Manual check` — не установка, его можно слать
сколько угодно раз, оно не влияет ни на какое состояние приложения. Каждый запуск
генерирует свой `eid`, поэтому события не схлопнутся в одно.

Payload собран тем же `build_payload`, что и в приложении — команду можно
перегенерировать:
`cargo test --lib -- --ignored --nocapture print_probe_curl`.

```bash
EID=$(uuidgen); DTM=$(python3 -c "import time;print(int(time.time()*1000))"); curl -sS -w '\nHTTP %{http_code}\n' -X POST "https://testjmb.alfabank.ru/metrica/corp/com.snowplowanalytics.snowplow/tp2" -H 'Content-Type: application/json; charset=UTF-8' -d "{\"schema\":\"iglu:com.snowplowanalytics.snowplow/payload_data/jsonschema/1-0-4\",\"data\":[{\"e\":\"se\",\"se_ca\":\"ALFA-ATLAS > Debug\",\"se_ac\":\"Probe -> Manual check\",\"se_la\":\"Manual collector probe\",\"aid\":\"alfa-atlas-ui_dev\",\"p\":\"web\",\"tv\":\"atlas-0.3.1\",\"eid\":\"$EID\",\"dtm\":\"$DTM\",\"duid\":\"curl-probe\",\"co\":\"{\\\"schema\\\":\\\"iglu:com.snowplowanalytics.snowplow/contexts/jsonschema/1-0-1\\\",\\\"data\\\":[{\\\"schema\\\":\\\"iglu:com.alfabank/custom_dimension/jsonschema/1-0-0\\\",\\\"data\\\":{\\\"2\\\":\\\"curl-probe\\\",\\\"3\\\":\\\"0.3.1\\\",\\\"4\\\":\\\"macos\\\"}}]}\"}]}"; echo "eid=$EID"
```

Чтобы проверить `aid` release-сборки, замените в команде `alfa-atlas-ui_dev` на
`alfa-atlas-ui` — домен тот же.

Ищите в витрине по `aid` и `eid`, который команда печатает последней строкой.
`200` подтверждает только приём коллектором — если события не появились, значит их
отверг enrich (скорее всего из-за схемы `custom_dimension/1-0-0` или
незарегистрированного `aid`).
