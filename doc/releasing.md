# Как выпустить релиз

Релиз собирается на CI и публикуется автоматически. Единственный триггер —
**push тега вида `v*`**. Вручную на GitHub ничего создавать не нужно.

## Коротко

```bash
git checkout main && git pull
# 1. поднять версию в 5 файлах (см. ниже)
git commit -am "bump version to 0.3.1"
git tag -a v0.3.1 -m "v0.3.1"
git push origin main
git push origin v0.3.1
```

Дальше ~20 минут работает CI, после чего релиз появляется на
[странице релизов](https://github.com/gribanoveu/alfa-atlas/releases).

## Шаг 1. Поднять версию

Версия дублируется в пяти местах, и все должны совпадать. Если забыть —
приложение будет сообщать о себе старую версию, а имена файлов в релизе не
совпадут с тегом.

| Файл | Поле | На что влияет |
|------|------|---------------|
| `src-tauri/Cargo.toml` | `version` в `[package]` | версия крейта |
| `src-tauri/tauri.conf.json` | `version` | метаданные бандла, имена файлов |
| `package.json` | `version` | версия npm-пакета |
| `src-tauri/Cargo.lock` | запись пакета `alfa-atlas` | фиксация сборки |
| `app.config.json` | `version` | **то, что видит пользователь** в меню «О программе» |

Последний легко упустить: `app.config.json` не участвует в сборке и ни одна
проверка на него не ругается, но именно его значение выводят
[`AboutModal.tsx`](../src/components/TopBar/AboutModal.tsx) и пункт меню
«О программе» в [`MenuBar.tsx`](../src/components/TopBar/MenuBar.tsx).

`Cargo.lock` руками править не нужно — обновится сам после любой
cargo-команды:

```bash
cd src-tauri && cargo check
```

Проверить, что везде одно и то же:

```bash
grep -m1 '^version' src-tauri/Cargo.toml
grep -m1 '"version"' package.json src-tauri/tauri.conf.json app.config.json
grep -A1 'name = "alfa-atlas"' src-tauri/Cargo.lock
```

## Шаг 2. Проверки перед тегом

Тег дешевле не поставить, чем потом снимать с уже собранного релиза:

```bash
bun run tsc --noEmit
cd src-tauri && cargo test --lib && cargo clippy --all-targets
```

## Шаг 3. Тег и push

Тег — **аннотированный** (`-a`), имя строго `v` + версия из манифестов.

```bash
git tag -a v0.3.1 -m "v0.3.1"
git push origin main
git push origin v0.3.1
```

> **Не используйте `git push --tags`.** В репозитории лежат старые локальные
> теги (`v0.2.0`, `v0.2.1`), которых нет на GitHub. `--tags` отправит их все
> разом, а поскольку workflow срабатывает на любой тег `v*`, это запустит
> несколько параллельных сборок и создаст лишние релизы. Всегда пушьте тег
> по имени.

## Что делает CI

Файл — [`.github/workflows/build-release.yml`](../.github/workflows/build-release.yml).
Три джобы:

| Джоба | Раннер | Артефакты |
|-------|--------|-----------|
| `build-windows` | `windows-latest` | `.msi`, `.exe` |
| `build-macos` | `macos-latest` | `.dmg` (Apple Silicon) |
| `release` | `ubuntu-latest` | публикует релиз со всеми файлами |

`release` ждёт обе сборки (`needs`), скачивает их артефакты и создаёт
релиз через `softprops/action-gh-release` с автоматически сгенерированными
release notes. Полный проход занимает около 20 минут.

## Наблюдение за сборкой

```bash
gh run list --limit 3
gh run watch <run-id> --exit-status
gh release view v0.3.1
```

Если джоба упала — посмотреть только упавшие шаги:

```bash
gh run view <run-id> --log-failed
```

## Если что-то пошло не так

### Сборка упала, тег уже запушен

Правьте причину и выпускайте следующий патч (`v0.3.2`). Переставлять
существующий тег не стоит: если релиз успел опубликоваться, ссылки на его
артефакты сломаются, и отката у этого нет.

Если релиз ещё **не** опубликовался, тег можно снять:

```bash
git push origin :refs/tags/v0.3.1
git tag -d v0.3.1
```

### Перезапустить сборку на существующем теге

У workflow есть `workflow_dispatch`, поэтому можно собрать заново без нового
тега — например, чтобы дособрать платформу, добавленную уже после релиза:

```bash
gh workflow run "Build and Release" --ref v0.3.1
```

### Кончилась память на этапе `vite build`

Проявляется как `Abort trap: 6` или `exit code 134`. Фронтенд-бандл (monaco,
shiki, mermaid) не влезает в дефолтный heap Node. У обеих сборочных джоб
для этого выставлен `NODE_OPTIONS: --max-old-space-size=8192` — при добавлении
новой платформы не забудьте про эту переменную.

## Подпись

Сборки **не подписаны** сертификатами Apple и Microsoft, поэтому обе системы
показывают предупреждения. Как их обойти — описано в разделе «Установка»
[README](../README.md).

macOS подписывается ad-hoc (`bundle.macOS.signingIdentity: "-"` в
`tauri.conf.json`). Это не делает приложение доверенным, но избавляет от
сообщения «приложение повреждено»: пользователю остаётся один раз
подтвердить запуск в системных настройках. Полностью убрать предупреждения
может только Developer ID с нотаризацией — это платный аккаунт Apple
Developer Program.

## Совместимость сборок

- **macOS** — только Apple Silicon (`aarch64`). На Intel-маках приложение не
  запустится; чтобы это исправить, нужна отдельная джоба с таргетом
  `x86_64-apple-darwin`.
- **Windows** — только x64.
- **Linux** — сборки нет. Пробовали в v0.3.1 и отказались: `fastembed`
  тянет предсобранный ONNX Runtime, требующий glibc 2.38+ и libstdc++ из
  GCC 13+, а `usearch` тянет C-крейт `numkong` с атрибутом `avx512fp16`
  (нужен GCC 12+). На `ubuntu-22.04` не собирается ни то, ни другое; на
  `ubuntu-24.04` собирается, но результат не запустится нигде, кроме
  свежих дистрибутивов — то есть выигрыш от «старого раннера ради
  совместимости» здесь нулевой. Если возвращать Linux, начинать нужно с
  `ubuntu-24.04` и сразу закладывать эту планку.
