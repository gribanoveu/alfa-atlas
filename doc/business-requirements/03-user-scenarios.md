# 3. Пользовательские сценарии

Целевые сценарии продукта. Текущая реализация покрывает только оболочку, Welcome и открытие папки — см. [../implemented-features.md](../implemented-features.md).

## US-1. Дописать метод createOrder

**Актёр:** технический писатель / API-инженер  
**Цель:** закрыть пробелы в описании метода относительно JSON.

### Шаги

1. Открыть дерево «Документация» → `createOrder`.
2. Открыть `description.adoc`, `request.json`, `response.json`.
3. В AI-чате запросить сверку: сравнить `response.json` и текущее описание.
4. Получить предложения:
   - недокументированные поля `errorCode` / `errorMessage`;
   - уточнение единиц измерения для `amount` (копейки vs рубли).
5. Принять вставку раздела «Коды ошибок» (Tab / «Принять» или «Вставить» в diff-карточке).
6. Проверить результат в режиме **Превью**.
7. Исправить проблемы форматирования («Исправить все»).
8. В Git: stage изменённые файлы → commit с сообщением вида `docs: …`.

### Ожидаемый результат

Метод `createOrder` содержит согласованное описание, включая коды ошибок; изменения зафиксированы локальным коммитом.

## US-2. Стандартизировать структуру описания

**Актёр:** технический писатель  
**Цель:** быстро набрать каноничную структуру метода.

### Шаги

1. Открыть целевой `.adoc`.
2. В панели **AsciiDoc** найти и вставить блоки:
   - «Параметры запроса»;
   - «Поля ответа»;
   - «Коды ошибок»;
   - при необходимости — HTTP-метод, `source,json`, NOTE/IMPORTANT.
3. Заполнить таблицы и примеры.

### Ожидаемый результат

Описание соответствует единому шаблону API-документации команды.

### Ограничение

Вставка недоступна, если активен не `.adoc` файл — система сообщает об этом явно.

---

## US-3. Подготовить docs-ветку к коммиту

**Актёр:** maintainer docs  
**Цель:** зафиксировать набор изменений документации на feature-ветке.

### Шаги

1. Убедиться, что в top bar отображаются репозиторий и ветка (например, `payments-service` / `feature/docs-orders`).
2. Открыть панель **Git**.
3. Просмотреть Changes (unstaged) и Staged.
4. Выборочно Stage / Unstage файлы.
5. Ввести commit message.
6. Выполнить Commit (кнопка активна только при сообщении и наличии staged).
7. Проверить появление записи в Recent commits.

### Ожидаемый результат

Изменения документации учтены локальным коммитом без выхода из редактора.

---

## US-4. Перевести / локализовать описание *(заявлено UI)*

**Актёр:** технический писатель  
**Цель:** подготовить EN-версию формулировок.

### Шаги

1. Открыть метод в редакторе.
2. Выбрать быстрое действие AI «Перевести на EN».
3. Просмотреть предложение и принять контролируемую вставку / правки.

### Ожидаемый результат

Получен черновик англоязычных формулировок в едином стиле с исходным RU-описанием.

> В прототипе действие представлено chip’ом; полноценный перевод — целевое поведение.

---

## Эталонный диалог AI (демо)

| Роль | Содержание |
|------|------------|
| **Пользователь** | Сравни `response.json` и текущее описание, допиши недостающие поля. |
| **Ассистент** | В `response.json` есть блок `error` с полями `errorCode` и `errorMessage`, которых нет в описании. Также поле `amount` в примере указано в рублях, а в схеме — в копейках — стоит уточнить формулировку. Предлагает diff раздела «Коды ошибок». |
| **Пользователь** | Хорошо, вставляй. Дальше сделай так же для `getOrderStatus`. |
| **Ассистент** | Подтверждает вставку и переходит к сверке следующего метода в едином стиле. |
