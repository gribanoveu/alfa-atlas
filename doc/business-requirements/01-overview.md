# 1. Обзор продукта

Фактическая реализация в репозитории: [../implemented-features.md](../implemented-features.md). Ниже — целевой обзор продукта.

## 1.1. Наименование и позиционирование

| Аспект | Содержание |
|--------|------------|
| **Название** | docflow (исторически в BR также DocForge) |
| **Тип продукта** | IDE-подобный редактор API-документации с AI-ассистентом |
| **Пакет / идентификатор** | `docflow` / `com.eugene.docflow` |
| **Язык UI** | Русский (основные подписи); Git-термины — смешанные EN |
| **Позиционирование** | Документационный редактор для команд, ведущих API-доки в git-репозитории |

**Не является:** Git-хостингом, платформой code review / PR, issue-трекером.

---

## 1.2. Бизнес-контекст и проблема

| Аспект | Содержание |
|--------|------------|
| **Проблема** | Документация API отстаёт от схем и примеров: поля есть в JSON, но не описаны; формулировки противоречат единицам измерения; оформление нестабильно |
| **Последствие** | Ошибки интеграции у потребителей API, ручной разбор расхождений, долгий цикл «написал → проверил → закоммитил» |
| **Решение** | Единое рабочее место: дерево docs → редактор с превью → AI-сверка с JSON → шаблоны AsciiDoc → проверка форматирования → stage / commit |

---

## 1.3. Цели продукта

1. Сократить время на полное описание API-метода (описание + HTTP + параметры + ошибки + примеры).
2. Снизить долю недокументированных полей относительно `request` / `response`.
3. Обеспечить единый стиль AsciiDoc за счёт библиотеки блоков и AI-уточнения формулировок.
4. Встроить docs-workflow в привычный Git-цикл без переключения в отдельный Git-клиент.
5. *(Направление развития)* Давать метрику покрытия документацией и поддерживать двуязычность (RU → EN).

---

## 1.4. Целевые пользователи

| Персона | Задачи в продукте |
|---------|-------------------|
| **Технический писатель** | Пишет `description.adoc`, использует превью, блоки AsciiDoc, принимает AI-подсказки |
| **Backend / API-инженер** | Актуализирует JSON-примеры, просит AI найти расхождения с описанием |
| **Maintainer docs на feature-ветке** | Stage / commit изменений документации на ветке вроде `feature/docs-orders` |

Роли, SSO, оргструктура и права доступа в текущем объёме **не моделируются**.

---

## 1.5. Предметная модель (демо)

Демо-контекст — платёжный сервис:

| Сущность | Значение в демо |
|----------|-----------------|
| Репозиторий | `payments-service` |
| Ветка | `feature/docs-orders` |
| Методы | `createOrder`, `getOrderStatus`, `cancelOrder`, `refundPayment`, `listTransactions` |

### Каноническая структура метода

```text
docs/<methodName>/
  description.adoc   — человекочитаемое описание (AsciiDoc)
  request.json       — пример / схема запроса
  response.json      — пример / схема ответа
```

### Связи сущностей

```text
Repository
  └── Branch
        └── Documentation tree (docs/)
              └── API Method folder
                    ├── description.adoc
                    ├── request.json
                    └── response.json

File
  ├── content
  ├── optional AI suggestion
  └── optional format issues

AI Chat
  ├── messages (user | assistant)
  ├── context pills (@method, @request.json, @response.json)
  └── optional diff card → insert into .adoc

Git change sets
  ├── staged / unstaged files
  └── commits
```

## 1.6. Карта рабочей области

Одноэкранный workspace (без роутинга). Области интерфейса:

| Область | Назначение |
|---------|------------|
| **Top bar** | Бренд DocForge, меню, репозиторий, ветка |
| **Слева** | Дерево «Документация» |
| **Центр** | Редактор: вкладки, исходник / split / превью |
| **Справа** | AI-ассистент, библиотека AsciiDoc, Git |
| **Снизу** | Подсказки AI, проблемы форматирования |
| **Status bar** | Путь, язык, кодировка, «AI-индекс актуален» |
