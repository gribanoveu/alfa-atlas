# Workspace Index Service (MVP)

## Цель

Разработать сервис `WorkspaceIndex`, отвечающий за индексацию рабочей области документации и предоставление данных для редактора.

Сервис является единым источником информации о документах проекта и используется для:

- диагностики ошибок;
- автодополнения;
- навигации по проекту.

На данном этапе не реализуются поиск использований, рефакторинг и кэширование индекса на диске.

Сервис полностью реализуется на стороне **Rust-бэкенда** (Tauri core). Фронтенд (TypeScript/React, Monaco Editor) не выполняет парсинг и индексацию — он только отображает данные, полученные от бэкенда через Tauri commands/events, и не хранит собственную копию индекса.

---

# Требования

## 1. Индексация рабочей области

После открытия проекта сервис должен выполнить обход файловой системы и построить индекс проекта.

Поддерживаемые типы файлов:

- `*.adoc`, `*.asciidoc`
- `*.md`, `*.markdown`
- `*.json`
- `*.yaml`, `*.yml`
- `*.txt`
- `*.puml`, `*.plantuml`
- `*.mmd`, `*.mermaid`

Архитектура должна позволять легко подключать новые типы документов через `ParserRegistry` (см. раздел 9), без изменения существующей логики индексации.

## 2. Построение индекса

### Для каждого документа необходимо сохранить

- абсолютный путь;
- относительный путь;
- имя файла;
- тип документа;
- дату последнего изменения.

## 3. Модель данных

Все парсеры возвращают унифицированную модель, независимо от исходного формата файла:

```rust
pub struct DocumentId(pub String); // относительный путь, нормализованный как ключ

pub struct Document {
    pub id: DocumentId,
    pub absolute_path: PathBuf,
    pub relative_path: PathBuf,
    pub file_name: String,
    pub doc_type: DocumentType,
    pub modified_at: SystemTime,
}

pub enum DocumentType {
    AsciiDoc,
    Markdown,
    Json,
    Yaml,
    Text,
    PlantUml,
    Mermaid,
}

pub struct Anchor {
    pub id: String,
    pub document: DocumentId,
    pub line: u32,
    pub column: u32,
}

pub struct Include {
    pub path: String,
    pub source_document: DocumentId,
    pub line: u32,
    pub column: u32,
}

pub struct Reference {
    pub target_document: String,
    pub anchor: Option<String>,
    pub source_document: DocumentId,
    pub line: u32,
    pub column: u32,
}

pub struct Attribute {
    pub name: String,
    pub value: String,
    pub document: DocumentId,
    pub line: u32,
}

pub struct Image {
    pub path: String,
    pub document: DocumentId,
    pub line: u32,
}

pub enum Severity { Error, Warning }

pub struct Diagnostic {
    pub kind: DiagnosticKind,
    pub message: String,
    pub document: DocumentId,
    pub line: u32,
    pub column: u32,
    pub severity: Severity,
}

pub enum DiagnosticKind {
    MissingInclude,
    MissingXrefDocument,
    MissingXrefAnchor,
    MissingImage,
    DuplicateAnchor,
    CircularInclude,
}
```

## 4. Инкрементальное обновление

После изменения файла сервис должен:

1. определить изменившийся файл;
2. удалить связанные записи из индекса (anchors, includes, references, attributes, images, принадлежащие этому документу);
3. повторно проиндексировать только данный файл;
4. обновить индекс и пересчитать диагностику, затронутую изменением (как минимум — диагностику самого файла и документов, которые на него ссылаются).

Полная перестройка проекта выполняется только при открытии рабочей области.

### Обработка переименования

При переименовании файла:

1. запись документа в `DocumentRepository` обновляется по новому пути, без полного удаления и повторного создания идентификатора там, где это возможно;
2. все `include`, `xref` и `image`, ссылавшиеся на старый относительный путь, помечаются как битые (`MissingInclude` / `MissingXrefDocument` / `MissingImage`) до тех пор, пока не будут обновлены вручную — автоматическое переписывание путей внутри других документов в MVP **не выполняется**;
3. anchors и attributes переименованного документа переиндексируются с привязкой к новому `DocumentId`.

---

## 5. Мониторинг файловой системы

Сервис должен отслеживать:

- создание файла;
- удаление файла;
- изменение файла;
- переименование файла.

После получения события индекс автоматически обновляется.

---

## 6. Согласованность и конкурентный доступ

Индекс хранится в памяти процесса Rust-бэкенда и может одновременно:

- читаться по запросам от фронтенда (автодополнение, диагностика, навигация);
- обновляться асинхронно по событиям файловой системы.

Требования:

- репозитории (`DocumentRepository`, `AnchorRepository` и т.д.) должны быть потокобезопасны (например, `Arc<RwLock<...>>` или `DashMap` для точечных O(1)-обновлений без блокировки всего индекса);
- обновление одного документа не должно блокировать чтение данных по другим документам дольше, чем на время самой записи;
- в момент обновления документа читатели могут либо дождаться завершения записи, либо получить последнее консистентное состояние (stale-read) — на выбор реализации, но поведение должно быть задокументировано и единообразно для всех методов API;
- события файловой системы, пришедшие во время обработки предыдущего события для того же файла, должны быть сериализованы (обрабатываться по очереди), а не выполняться параллельно, чтобы избежать гонки при повторном быстром сохранении файла.

---

## 7. API сервиса

API реализуется как набор Rust-методов на структуре `WorkspaceIndex`, экспортируемых во фронтенд через Tauri commands (см. раздел 10).

### Работа с документами

```rust
fn get_document(&self, path: &Path) -> Option<Document>;
fn get_documents(&self) -> Vec<Document>;
fn find_document(&self, name: &str) -> Vec<Document>;
```

### Работа с Anchor

```rust
fn find_anchor(&self, id: &str) -> Vec<Anchor>;
fn find_anchors(&self, document: &DocumentId) -> Vec<Anchor>;
```

### Работа с Include

```rust
fn find_includes(&self, document: &DocumentId) -> Vec<Include>;
```

### Работа с XRef

```rust
fn find_references(&self, document: &DocumentId) -> Vec<Reference>;
```

### Работа с атрибутами

```rust
fn find_attribute(&self, name: &str) -> Vec<Attribute>;
fn get_attributes(&self, document: &DocumentId) -> Vec<Attribute>;
```

### Работа с изображениями

```rust
fn find_image(&self, path: &str) -> Vec<Image>;
```

Все методы читают из in-memory индекса и должны выполняться за O(1) или O(log n) относительно количества документов/записей (см. раздел 9).

## 8. Диагностика

Сервис должен выполнять базовую диагностику проекта.

### Ошибки

- отсутствует include-файл;
- отсутствует документ в xref;
- отсутствует anchor в xref;
- отсутствует изображение;
- дублирование anchor внутри проекта;
- циклический include.

### Обнаружение циклического include

Выполняется обходом графа include (DFS) от каждого документа с отслеживанием множества посещённых документов (`visited`) в текущей цепочке. Если во время обхода встречается документ, уже находящийся в `visited` для этой цепочки — фиксируется ошибка `CircularInclude` с указанием всей цепочки документов, образующей цикл.

Результат диагностики должен содержать:

- тип ошибки (`DiagnosticKind`);
- сообщение;
- файл;
- строку;
- колонку;
- уровень (Error / Warning).

---

## 9. Автодополнение Monaco Editor

Сервис на стороне Rust-бэкенда должен предоставлять данные для автодополнения; сам Monaco Editor и логика подписки на его provider'ы остаются на фронтенде.

### include

После ввода

```adoc
include::
```

фронтенд запрашивает у бэкенда список документов проекта (`get_documents`) и передаёт его в completion provider Monaco.

### xref

После ввода

```adoc
xref:
```

фронтенд запрашивает список документов. После выбора документа, содержащего anchor, фронтенд запрашивает `find_anchors(document)` для этого документа.

### image

После ввода

```adoc
image::
```

фронтенд запрашивает список изображений, найденных в проекте.

### Атрибуты

После ввода

```adoc
{
```

фронтенд запрашивает список известных атрибутов проекта.

## 10. Интеграция с фронтендом (Tauri)

Так как индексация, парсинг и диагностика полностью выполняются в Rust, взаимодействие с TS/React-фронтендом и Monaco Editor строится так:

- **Команды (request/response)**: методы из раздела 7 экспортируются как `#[tauri::command]` и вызываются из фронтенда через `invoke(...)`. Возвращаемые типы (`Document`, `Anchor`, `Reference` и т.д.) должны быть `Serialize`/`Deserialize` (serde) и сериализоваться в JSON для передачи через Tauri IPC.
- **События (push)**: сервис публикует события (раздел 12) через `app_handle.emit(...)`, фронтенд подписывается через `listen(...)` и обновляет Status Bar, список ошибок, дерево проекта и провайдеры автодополнения Monaco без поллинга.

---

## 11. Производительность

Требования

- индекс строится один раз при открытии проекта;
- изменение одного файла не должно приводить к полной перестройке;
- поиск данных осуществляется за O(1) или O(log n);
- хранение индекса выполняется в памяти;
- обновление индекса одного документа должно занимать менее 100 мс для файлов среднего размера (до ~50 КБ);
- время полной первичной индексации проекта — **требует уточнения** (в документе не задан целевой показатель; ориентир для проекта из ~500 документов нужно согласовать отдельно, прежде чем закладывать его в критерии приёмки).

# Критерии приемки

Сервис считается реализованным, если:

- открытие проекта автоматически строит индекс;
- изменения файлов автоматически обновляют индекс;
- Monaco Editor получает автодополнение для `include`, `xref`, `image` и атрибутов через Tauri-команды;
- сервис обнаруживает битые ссылки, отсутствующие include, изображения и дубли anchor;
- индекс полностью хранится в памяти и обновляется без полной перестройки проекта;
- переименование файла корректно обновляет путь документа и помечает ссылавшиеся на старый путь include/xref/image как битые.

## Зависимости (Rust crates)

| Формат | Крейт | Назначение |
|---------|------------|------------|
| `*.adoc`, `*.asciidoc` | собственный парсер (built-in) | Готовых зрелых Rust-крейтов уровня `@asciidoctor/core` нет. Реализуется облегчённый line/regex-based парсер под нужный набор конструкций: `include`, `xref`, anchor, атрибуты, image — без полного AST AsciiDoc |
| `*.md`, `*.markdown` | `pulldown-cmark` + `gray_matter` | Парсинг Markdown, построение событийного потока/AST, поддержка Front Matter |
| `*.json` | `serde_json` (+ `jsonschema` при необходимости валидации по схеме) | Парсинг и валидация JSON |
| `*.yaml`, `*.yml` | `serde_yaml` (или `yaml-rust2`) | Парсинг и диагностика YAML |
| `*.txt` | — | Индексация содержимого как обычного текста без синтаксического анализа |
| `*.puml`, `*.plantuml` | собственный парсер (built-in) | Зрелых Rust-крейтов нет; реализуется минимальный парсер для извлечения зависимостей и базовой проверки синтаксиса |
| `*.mmd`, `*.mermaid` | собственный парсер (built-in) | Аналогично — минимальная проверка синтаксиса без полноценного рендеринга (рендер диаграмм, если нужен, выполняется на фронтенде через `mermaid.js`) |

### Общие зависимости

| Крейт | Назначение |
|------------|------------|
| `ignore` | Быстрое сканирование рабочей области + поддержка `.gitignore` и пользовательских правил исключения (объединяет функции `fast-glob` и `ignore` из npm-версии) |
| `notify` | Мониторинг изменений файловой системы (создание/удаление/изменение/переименование) |
| `tokio` | Асинхронный рантайм для файлового наблюдателя и неблокирующей обработки событий |
| `dashmap` (или `parking_lot::RwLock` вокруг `HashMap`) | Потокобезопасные O(1)-репозитории для конкурентного чтения/обновления индекса |
| `serde`, `serde_json` | Сериализация моделей данных для передачи через Tauri IPC |

### Требования

- Каждый поддерживаемый формат реализуется в виде отдельного парсера, зарегистрированного в `ParserRegistry`.
- Добавление нового типа документа не должно требовать изменения существующей логики индексации.
- При отсутствии специализированного крейта (AsciiDoc, PlantUML, Mermaid) используется собственный парсер при условии поддержки функций, необходимых для построения индекса и диагностики.
- Все парсеры возвращают унифицированную модель документа (раздел 3), используемую сервисом `WorkspaceIndex`, независимо от исходного формата файла.

Архитектура должна позволять заменять или добавлять парсер для нового типа документа без изменения остальных компонентов системы.

## Отображение состояния индексации

Во время построения или обновления индекса пользователь должен видеть текущее состояние процесса.

Статус отображается в нижней панели приложения (Status Bar) рядом с информацией о положении курсора (строка, столбец).

Возможные состояния:

- `$(sync~spin) Building workspace index...`
- `$(sync~spin) Updating index...`
- `$(check) Index ready`
- `$(warning) Index completed with warnings`
- `$(error) Index failed`

Дополнительно рекомендуется отображать прогресс:

```text
Building workspace index... (128 / 523)
```

или

```text
Updating index... (install.adoc)
```

После завершения индексирования отображается краткая статистика:

```text
Indexed 523 documents • 1348 anchors • 287 xref • 96 include • 2 warnings
```

Сервис `WorkspaceIndex` должен публиковать события изменения состояния, чтобы пользовательский интерфейс мог обновлять Status Bar без постоянного опроса.

## События WorkspaceIndex

Сервис публикует следующие события (через Tauri `emit`):

- `IndexBuildingStarted`
- `IndexBuildingProgress`
- `IndexBuildingFinished`
- `IndexUpdated`
- `DiagnosticsUpdated`

Фронтенд подписывается на данные события через Tauri `listen` для обновления:

- Status Bar;
- списка ошибок;
- дерева проекта;
- автодополнения Monaco Editor.

## Тестовое покрытие

Не менее 80% Rust-кода сервиса (сканирование, парсеры, репозитории, диагностика, Tauri-команды) должно быть покрыто юнит-тестами.
